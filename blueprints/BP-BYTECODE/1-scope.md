# 1. Scope

This blueprint specifies the execution of one method's code array: the state an instruction operates on, how an instruction is encoded and fetched, what an implementation is allowed to do to the array between reading it and running it, and what an observer is guaranteed to see. An implementation built from this document can take a `Code` attribute that has already been parsed and verified and execute it, and can say for any observable difference from HotSpot whether that difference is conforming.

It covers three things a reader is likely to expect somewhere else. The first is the frame, because the local variable array and the operand stack are what almost every instruction reads and writes, and an instruction set table with no frame under it is a list of names. The second is the boundary of undefined behaviour, which the specification draws exactly once and in one sentence, and which is the reason an interpreter is allowed to be as fast as it is. The third is rewriting, meaning the fact that the bytes an implementation executes are permitted to differ from the bytes the class file contained, which is the largest single surprise in this subject and is where a reader's tools stop agreeing with each other.

It deliberately excludes five things. Reading and checking the class file that carries the code array belongs to BP-CLASSFILE. Deciding that a code array is well typed belongs to BP-VERIFY, and the `StackMapTable` attribute it consults belongs to BP-STACKMAP. Turning a constant pool index into a class, a field or a method belongs to BP-CONSTPOOL, so an instruction's operand is specified here as an index and its resolution is not. Everything about when a class is loaded, linked and initialized belongs to BP-LOAD, and this blueprint takes a method that is ready to run as given.

Two further exclusions look as though they belong here. The meaning of each individual instruction is not restated: section 3 is a generated table of every opcode with its length and its stack effect, and the prose describing what each one does is JVMS chapter 6, which is a document this one has no reason to copy and every reason not to. And compiled execution is out of scope, so nothing here says what a compiler that translates a method to machine code while the program runs does with it, beyond the one guarantee that whatever it does is unobservable except through timing. What a compiler may do to make this code faster is M6's subject.
