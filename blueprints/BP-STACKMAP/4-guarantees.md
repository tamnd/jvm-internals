# 4. Guarantees

## 4a. What the specification mandates

- **4a.1** There may be at most one `StackMapTable` attribute in the attributes table of a `Code` attribute, and it lives on the `Code` attribute rather than on the method, so a method with no code has nowhere to put one {[JVMS §4.7.4@SE25]}.
- **4a.2** In a class file of version 50.0 or above, a `Code` attribute with no `StackMapTable` has an implicit stack map attribute equivalent to one whose `number_of_entries` is zero, so the absence of the attribute is a claim that the method needs no frames rather than a claim that it was not checked {[JVMS §4.7.4@SE25]}.
- **4a.3** The order of the frames in the `entries` table is significant and each frame relies on the previous one for some of its semantics, so no entry can be read, moved, inserted or removed on its own {[JVMS §4.7.4@SE25]}.
- **4a.4** The first stack map frame of a method is implicit and computed from the method descriptor by the type checker, so the entry at index 0 describes the second frame of the method and the attribute never contains the state at bytecode offset 0 {[JVMS §4.7.4@SE25]} {[JVMS §4.10.1.5@SE25]}.
- **4a.5** The bytecode offset at which a frame applies is the previous frame's offset plus `offset_delta` plus 1, unless the previous frame is the method's initial frame, in which case it is `offset_delta` exactly {[JVMS §4.7.4@SE25]}.
- **4a.6** The delta encoding is what makes the frames sorted by definition and the `+ 1` is what makes duplicates impossible to write, so a reader obtains both properties from the arithmetic and neither has to be checked separately {[JVMS §4.7.4@SE25]}.
- **4a.7** Every frame's offset has to be the offset at which an instruction starts, because merging the frames with the instructions is undefined unless every frame offset has a corresponding instruction offset and the offsets are monotonically increasing {[JVMS §4.10.1.5@SE25]}.
- **4a.8** A verification type is a one byte tag followed by zero or more bytes, and two of the nine carry anything at all: an `Object_variable_info` carries a `u2` index that has to name a `CONSTANT_Class_info`, and an `Uninitialized_variable_info` carries a `u2` offset that has to be the offset of the `new` instruction that created the object {[JVMS §4.7.4@SE25]}.
- **4a.9** A `Long_variable_info` or a `Double_variable_info` describes the first of two locations, the second location has verification type `top` and is not written down anywhere, and the first location may not be the highest numbered local variable or the topmost operand stack entry {[JVMS §4.7.4@SE25]}.
- **4a.10** The first byte of a frame decides its kind, and for the two commonest kinds it also carries the offset delta: `frame_type` for a `same_frame` and `frame_type - 64` for a `same_locals_1_stack_item_frame`, with no further bytes read in either case {[JVMS §4.7.4@SE25]}.
- **4a.11** Tags in the range 128 to 246 are reserved for future use, which is 119 of the 256 values a first byte can hold, and a reserved tag cannot be skipped because a frame carries no length of its own {[JVMS §4.7.4@SE25]}.
- **4a.12** A `chop_frame` drops the last k local variables of the previous frame, k is `251 - frame_type` and is therefore 1, 2 or 3, and it is an error if k is larger than the number of local variables the previous frame has {[JVMS §4.7.4@SE25]}.
- **4a.13** An `append_frame` adds k local variables, k is `frame_type - 251` and is therefore 1, 2 or 3, the item at index 0 is the first additional local variable, and an item that is a `Long_variable_info` or a `Double_variable_info` advances the local variable index by two rather than one {[JVMS §4.7.4@SE25]}.
- **4a.14** It is an error for any entry of `locals` to represent a local variable whose index exceeds the method's maximum, or for any entry of `stack` to represent a stack entry beyond the method's maximum operand stack size, and the rule is stated separately for `append_frame` and for `full_frame` in the same words {[JVMS §4.7.4@SE25]}.
- **4a.15** The initial frame's locals are the `this` type where there is one, followed by the argument types with every two location type followed by `top`, padded with `top` to the method's declared width, and its operand stack is empty {[JVMS §4.10.1.5@SE25]}.
- **4a.16** Nothing requires a frame to be written in the smallest kind that could express it. A `full_frame` may appear anywhere, a `same_frame_extended` may be used wherever a `same_frame` would do, there is no canonical form and no shortest form rule, and a class file that takes the longer option everywhere is legal {[JVMS §4.7.4@SE25]}.

## 4b. What HotSpot chose

- **4b.1** The reserved range has a name in HotSpot and none in the specification: `RESERVED_START` and `RESERVED_END` sit in the same enum as the seven frame kinds, and that enum is the only place either boundary of the range is a constant rather than a sentence {[HOTSPOT src/hotspot/share/classfile/stackMapTable.hpp:156@jdk-27+35]} {[HOTSPOT src/hotspot/share/classfile/stackMapTable.hpp:157@jdk-27+35]}.
- **4b.2** The attribute is not decoded while the class file is read. Its bytes are bounds checked against `attribute_length` and copied verbatim, and nothing inside it is looked at until the verifier asks for a frame {[HOTSPOT src/hotspot/share/classfile/classFileParser.cpp:1760@jdk-27+35]}.
- **4b.3** A `StackMapTable` whose `attribute_length` is zero is dropped where it is found and the method records no attribute, so a file that declares the attribute and gives it no `number_of_entries` field is accepted and behaves as one with no attribute at all {[HOTSPOT src/hotspot/share/classfile/classFileParser.cpp:1752@jdk-27+35]} {[HOTSPOT src/hotspot/share/classfile/stackMapTable.cpp:179@jdk-27+35]}.
- **4b.4** A `StackMapTable` in a class file below major version 50 is not recognised as one: the test that matches the attribute name is guarded by the version, so those bytes fall through to the branch that skips attributes nobody knows and are never read again {[HOTSPOT src/hotspot/share/classfile/classFileParser.cpp:2408@jdk-27+35]} {[HOTSPOT src/hotspot/share/classfile/classFileParser.cpp:2420@jdk-27+35]}.
- **4b.5** Two `StackMapTable` attributes in one `Code` attribute end the parse with a message that names the class file and does not name the method or the attribute index {[HOTSPOT src/hotspot/share/classfile/classFileParser.cpp:2412@jdk-27+35]}.
- **4b.6** The decoder reads the `u2 offset_delta` before it decides whether the frame type is reserved, so on a reserved first byte it has consumed two bytes it had no business reading, and what saves it is that the next thing it does is throw {[HOTSPOT src/hotspot/share/classfile/stackMapTable.cpp:310@jdk-27+35]} {[HOTSPOT src/hotspot/share/classfile/stackMapTable.cpp:312@jdk-27+35]}.
- **4b.7** There is a second reserved frame type error at the bottom of the same function and it is unreachable, because the branches above it cover 0 to 63, 64 to 127, everything below 247, 247, 248 to 251, 252 to 254 and 255, which is every value a `u1` can hold {[HOTSPOT src/hotspot/share/classfile/stackMapTable.cpp:474@jdk-27+35]}.
- **4b.8** The exception for the first entry is not written once. Each of the five branches that can decode the first entry carries its own pair of assignments, one for the first frame and one for every other, selected by a flag the branch then clears {[HOTSPOT src/hotspot/share/classfile/stackMapTable.cpp:258@jdk-27+35]} {[HOTSPOT src/hotspot/share/classfile/stackMapTable.cpp:265@jdk-27+35]}.
- **4b.9** The first entry copies the initial frame's locals rather than aliasing them, on the stated grounds that the verifier updates that array in place, so the frame the type checker computed survives being read past {[HOTSPOT src/hotspot/share/classfile/stackMapTable.cpp:261@jdk-27+35]} {[HOTSPOT src/hotspot/share/classfile/stackMapTable.cpp:272@jdk-27+35]}.
- **4b.10** A frame whose offset is past the end of the code, or which does not land on the first byte of an instruction, is reported as a verify error rather than a format error, and the test is a lookup in a byte array the verifier filled in while walking the code {[HOTSPOT src/hotspot/share/classfile/stackMapTable.cpp:51@jdk-27+35]}.
- **4b.11** `number_of_entries` is compared against the number of frames actually decoded twice, once before each frame as a floor and once at the end for equality, and the two failures give the same message, so a count that is too small and a count that is too large are indistinguishable in a log {[HOTSPOT src/hotspot/share/classfile/stackMapTable.cpp:58@jdk-27+35]} {[HOTSPOT src/hotspot/share/classfile/stackMapTable.cpp:65@jdk-27+35]}.
- **4b.12** A chop counts local variables and not locations. It walks backwards through the previous frame's expanded array and steps two positions rather than one whenever it lands on the second half of a category 2 value {[HOTSPOT src/hotspot/share/classfile/stackMapTable.cpp:188@jdk-27+35]}.
- **4b.13** A chop that would run off the front of the locals array returns a negative length, which is caught by the same bounds check that catches a frame wider than the method's maximum, so the specification's separate error for chopping too far arrives with the message for an array of the wrong size {[HOTSPOT src/hotspot/share/classfile/stackMapTable.cpp:193@jdk-27+35]} {[HOTSPOT src/hotspot/share/classfile/stackMapTable.hpp:141@jdk-27+35]}.
- **4b.14** After a chop the frame's flags are recomputed from the surviving locals rather than inherited from the previous frame, because the local variable holding `uninitializedThis` may be one of the ones that was dropped {[HOTSPOT src/hotspot/share/classfile/stackMapTable.cpp:364@jdk-27+35]}.
- **4b.15** An append frame's locals array is allocated at two positions per appended item before any item is read, and a full frame's arrays the same way, because the decoder cannot know which items are category 2 until it has read them {[HOTSPOT src/hotspot/share/classfile/stackMapTable.cpp:397@jdk-27+35]} {[HOTSPOT src/hotspot/share/classfile/stackMapTable.cpp:432@jdk-27+35]}.
- **4b.16** The second location of a category 2 value is materialised as a verification type of its own, under two names from an enum whose comment says these are not found in class files, and the six values that enum holds begin at 9, above the eight the format defines, so a verifier type can never be mistaken for a file type {[HOTSPOT src/hotspot/share/classfile/verificationType.hpp:64@jdk-27+35]} {[HOTSPOT src/hotspot/share/classfile/verificationType.hpp:65@jdk-27+35]}.
- **4b.17** A tag below 6 becomes a verification type by table lookup with no range check of its own, which is safe because the table covers every value below 6, and only a tag above the largest defined one reaches the error {[HOTSPOT src/hotspot/share/classfile/stackMapTable.cpp:202@jdk-27+35]} {[HOTSPOT src/hotspot/share/classfile/stackMapTable.cpp:232@jdk-27+35]}.
- **4b.18** An `Object_variable_info` whose index is out of range, or which names an entry that is neither a resolved nor an unresolved class, is a stack map format error, while an `Uninitialized_variable_info` whose offset does not point at a `new` instruction is a class format error raised through the verifier rather than through the stream, so two malformations of the same kind arrive by two different routes {[HOTSPOT src/hotspot/share/classfile/stackMapTable.cpp:208@jdk-27+35]} {[HOTSPOT src/hotspot/share/classfile/stackMapTable.cpp:226@jdk-27+35]}.
- **4b.19** Whether the attribute is read at all is decided per class from the defining loader, by the same pair of flags that decides the rest of verification, so a class from the boot loader in a default configuration has its stack map copied into memory and never decoded {[HOTSPOT src/hotspot/share/classfile/verifier.cpp:117@jdk-27+35]}.
- **4b.20** At major version 50 exactly, a class the type checking verifier rejected with a verify error or a class format error is handed to the inference verifier, which ignores the attribute entirely, so an attribute that fails every check in section 3 can still produce a class that loads and runs {[HOTSPOT src/hotspot/share/classfile/verifier.cpp:219@jdk-27+35]} {[HOTSPOT src/hotspot/share/classfile/verifier.cpp:228@jdk-27+35]} {[HOTSPOT src/hotspot/share/classfile/verifier.cpp:230@jdk-27+35]}.

## 4c. Ordering obligations

- **4c.1** The class file version is known before the attribute is recognised, because below major version 50 these bytes are an attribute nobody knows and at 50 and above they are a stack map, and nothing but the version field distinguishes the two {[HOTSPOT src/hotspot/share/classfile/classFileParser.cpp:2408@jdk-27+35]}.
- **4c.2** The method's maximum locals and maximum operand stack size are known before the first frame is decoded, because every frame is checked against both as it is built and neither can be inferred from the attribute {[JVMS §4.7.4@SE25]}.
- **4c.3** The code array has been walked before the frames are decoded, because a frame's offset is checked against the set of instruction starts and an `Uninitialized_variable_info`'s offset against the presence of a `new` at that offset, and neither question can be answered from the bytes of the attribute {[HOTSPOT src/hotspot/share/classfile/stackMapTable.cpp:224@jdk-27+35]}.
- **4c.4** The initial frame is computed before the first entry is read, and the first entry is a delta against it, so a reader that starts at the first entry with an empty frame is wrong for every method that takes an argument and right for every method that takes none {[JVMS §4.10.1.5@SE25]}.
- **4c.5** Each frame is complete before the next one begins, because the next frame's locals, its operand stack and its offset are all expressed relative to it, so there is no order in which the entries can be decoded other than the order they are written in {[JVMS §4.7.4@SE25]}.
- **4c.6** A failure inside the attribute does not necessarily end the load where it is raised. It is reported through the verifier's error mechanism rather than by throwing, and that mechanism may return so that the class can be offered to a second verifier, which is a possibility every step of section 3 has to tolerate {[HOTSPOT src/hotspot/share/classfile/stackMapTable.hpp:146@jdk-27+35]}.
