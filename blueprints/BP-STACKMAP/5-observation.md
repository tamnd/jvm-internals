# 5. Observation

Every item below is a procedure rather than a result. The tool named in it is the one that answers the question with the least machinery, and where two tools disagree that disagreement is itself the observation.

Six tools carry this section. `java.lang.classfile`, on the pinned JDK, assembles a class frame by frame from a Java program, which is the only practical way to produce a stack map no compiler would emit. `javap -v` prints the frames as the platform's own reader understands them, with the offsets already resolved, which is what makes an argument about the arithmetic settleable. `xxd` is what settles an argument about a byte, because every other tool on this list is showing an interpretation and this attribute's whole subject is which byte was written. `probes/classfile-fuzz` breaks one valid class file and records where the machine stopped and in what words. `probes/stackmap` walks every class file of `java.base` twice, once through the class file API and once as raw bytes, and it is the only item here that produces a number rather than an outcome. And `java -Xlog:verification=info` says which verifier ran, which is the one question none of the others can answer.

- **5.1** 4a.1, 4b.5: build a `Code` attribute carrying two `StackMapTable` attributes, the second of them empty, and load it, with `java.lang.classfile` and `xxd`. The parse ends with a message that names the class file and nothing inside it, so a person reading the failure knows the file has two and not which method they are in.
- **5.2** 4a.2, 4b.3: take a method with branches, delete its `StackMapTable` attribute, and separately keep the attribute and set its `attribute_length` to zero, with `xxd` and `javap -v`. The first is refused, because the method needs frames it no longer has. The second is accepted, and the attribute that declares itself and gives no `number_of_entries` at all behaves exactly as though it had been deleted.
- **5.3** 4a.3, 4c.5: take a method with four frames, exchange the first two entries, and separately delete the first entry and lower `number_of_entries` by one, with `probes/classfile-fuzz` and `xxd`. Neither file loads, and neither failure mentions the entry that was moved, because every offset after it is now a different number and the first thing that fails is whichever one falls off an instruction boundary first.
- **5.4** 4a.4, 4a.15, 4c.4: print the frames of an instance method taking a `long` and an `Object` and compare the first entry's resolved offset against its `offset_delta`, with `javap -v`. The two are equal, which they are for no other entry, and the locals the first frame inherits are four wide before any entry has been read: `this`, the `long`, its `top`, and the `Object`.
- **5.5** 4a.5, 4a.6, 4b.8: apply the arithmetic to the 122,906 frames of `java.base` that carry their own delta in the first byte, and compare against the offsets the pinned JDK resolved, with `probes/stackmap/run.py`. They agree on every one, no two frames of any method share an offset, and every method's frames come out sorted without anything sorting them.
- **5.6** 4a.7, 4b.10: move one frame's offset one byte forward, into the middle of the instruction it used to point at, with `xxd` and `probes/classfile-fuzz`. The failure is a verify error rather than a format error, which is the one place in this blueprint where a malformed attribute is reported as though the code were wrong.
- **5.7** 4a.8, 4b.18: build an `Object_variable_info` whose index is past the end of the pool, then one naming a `CONSTANT_Utf8_info`, then an `Uninitialized_variable_info` whose offset is past the end of the code, then one pointing at an instruction that is not a `new`, with `java.lang.classfile`. All four are refused and they do not all arrive as the same class of error, because two of them go through the stream and two through the verifier.
- **5.8** 4a.9, 4b.12, 4b.15, 4b.16: count the `Long` and `Double` items in locals arrays against the `Top` items across `java.base`, then chop a frame whose last local is a `long`, with `probes/stackmap/run.py` and `javap -v`. There are 41,507 of the first and 26,349 of the second, which a format writing the implied second half could not produce, and chopping one local variable off a `long` removes both of its locations.
- **5.9** 4a.10, 4a.16: work out, for every frame in `java.base`, the smallest first byte that could have expressed it given the frame before, and compare against what was written, with `probes/stackmap/run.py` and `javap -v`. The answer differs for none of the 205,580 frames, and nothing in the specification asks for that. This is the observation the rest of the section is arranged around and it is written up on [the probe's page](../../docs/probes/stackmap.md).
- **5.10** 4a.11, 4b.1, 4b.6, 4b.7: overwrite one frame's first byte with 128, then with 200, then with 246, and load each, with `xxd` and `probes/classfile-fuzz`. All three give one message. Watching where the stream stopped shows two bytes consumed past the offending one, which is the read that happens before the rejection.
- **5.11** 4a.12, 4a.13, 4b.13: build a frame chopping one, two and three locals, an append frame adding one, two and three, and a chop of three from a frame that has two, with `java.lang.classfile` and `javap -v`. The six legal ones behave as the formulas say. The seventh is refused with a message about an array size, which names neither the chop nor the count that was too large.
- **5.12** 4a.14: build a `full_frame` whose locals array is one location wider than the method's declared maximum, then one whose operand stack is one deeper, with `java.lang.classfile`. Both are refused, and the wider case is worth building with a `long` in it, since a locals array that is legal by item count and illegal by location count is the shape an implementation counting items rather than locations will accept.
- **5.13** 4b.2, 4b.19: define a class whose `StackMapTable` is filled with random bytes but whose `attribute_length` is right, without linking it, then link it, then load the same bytes through a loader for which verification is off, with `java.lang.classfile` and `java -XX:-BytecodeVerificationRemote`. Defining it succeeds in every case, linking fails in the first and not the third, and the bytes were copied into memory in all of them.
- **5.14** 4b.4, 4c.1: take one class file with a `StackMapTable` and write its major version to 50 and then to 49, changing nothing else, with `xxd` and `java -Xlog:verification=info`. At 50 the attribute is a stack map and at 49 the same bytes are an attribute nobody knows, and the log names a different verifier in the two runs.
- **5.15** 4b.9: unobservable. The choice to copy the initial frame's locals rather than alias them is invisible from outside the machine, because the only difference it makes is whether a later in place update by the verifier reaches an array the reader still holds, and a machine that got it wrong would produce a wrong verification result rather than a distinguishable one.
- **5.16** 4b.11: set `number_of_entries` one lower than the frames present, then one higher, with `probes/classfile-fuzz` and `xxd`. Both are refused, both give the same sentence, and the sentence does not say in which direction the count was wrong.
- **5.17** 4b.14: build a constructor that holds `uninitializedThis` in a local variable, chops it away at a branch target, and then attempts to chain a constructor, with `java.lang.classfile`. The class is refused, and it is refused for chaining on something that is not uninitialized rather than for anything about the chop.
- **5.18** 4b.17: build one frame for each verification type tag from 0 to 8 and then one with tag 9, with `java.lang.classfile` and `javap -v`. The nine are accepted, the tenth is refused, and there is no tag below 9 for which the reader has to consult anything but a table.
- **5.19** 4b.20, 4c.6: take a class whose `StackMapTable` has been corrupted so that the type checking verifier refuses it, and load it at major version 50 and then at 51, with `xxd` and `java -Xlog:verification=info`. At 51 it fails. At 50 the log says the class failed over to the old verifier, the attribute is never looked at again, and the class loads.
- **5.20** 4c.2: lower a method's `max_locals` by one without touching its frames, with `xxd` and `probes/classfile-fuzz`. The failure names the array size rather than the frame, which is the check of 3.8 firing on a number that came from outside this attribute.
- **5.21** 4c.3: build an `Uninitialized_variable_info` whose offset is a valid instruction offset holding something other than `new`, with `java.lang.classfile` and `javap -v`. It is refused, and the only way to reach that decision is to have walked the code first, since the attribute contains nothing that says what is at that offset.
