# 1. Scope

This blueprint specifies the `StackMapTable` attribute: the nine verification types, the seven kinds of frame, the 119 first bytes that mean nothing, the arithmetic that turns a chain of deltas into bytecode offsets, and the checks a machine performs while turning those bytes into frames. An implementation built from this document can take the bytes of one attribute together with the method's `max_locals`, `max_stack` and code array, produce the sequence of frames a type checker consumes, and refuse the attributes a conforming machine refuses.

It covers three things a reader is likely to expect somewhere else. The first is the first frame, which is not in the attribute: it is computed from the method descriptor, and `entries[0]` describes the second frame of the method, so 4a.4 and 4a.5 keep the arithmetic for the first entry apart from the arithmetic for every other one. The second is what the absence of the attribute means, which is not that the method was unchecked but that it needs no frames, and which changed meaning at class file version 50.0. The third is the second half of a `long` or a `double`, which the format never writes down and which every reader has to invent, and which HotSpot invents under two names of its own.

It deliberately excludes four things. The surrounding structure belongs to BP-CLASSFILE: this document begins at the attribute's `number_of_entries` and assumes `attribute_length`, `max_locals`, `max_stack` and the code array have already been read. The verification algorithm belongs to BP-VERIFY, so what it means for one frame to be assignable to another, what happens at a branch target and how an exception handler is checked are all out of scope, and this document specifies only what a frame says rather than what is done with it. The instructions the offsets point at belong to BP-BYTECODE. And the `CONSTANT_Class_info` an `Object_variable_info` names belongs to BP-CONSTPOOL, of which only 4a.8 is in scope here, that the index has to name one.

Two further boundaries are worth naming because they look like exclusions and are not. The attribute is inert until something verifies the method, so everything a class file parser does with it is bounds checking, and 4b.2 says so; an implementation that decodes frames during parsing is doing work no conforming machine has to do and is reporting errors at a point where a conforming machine reports none. And what a compiler chooses to emit is out of scope: 14,911 class files were measured to write section 2, the most useful thing found in them is that every frame is written in the smallest form the encoding allows, and 4a.16 records that nothing requires this of anybody.
