# 5. Observation

Every item below is a procedure rather than a result. The tool named in it is the one that answers the question with the least machinery, and where two tools disagree that disagreement is itself the observation.

Four tools carry most of this section. `javap -v` prints the structure of a class file as the platform's own reader understands it. `java.lang.classfile`, on the pinned JDK, builds and rewrites class files from a Java program, which is what makes a broken one cheap to produce. `probes/classfile-fuzz` breaks one valid class file 27 named ways and 256 random ways and records where the machine stopped and in what words. And `xxd` is what settles an argument about a byte, because every other tool on this list is showing an interpretation.

- **5.1** 4a.1, 4b.1: patch the first four bytes to anything else and load the file, with `probes/classfile-fuzz` and `xxd`. The error class is the specification's answer and the wording of the message is HotSpot's.
- **5.2** 4a.2, 4b.2, 4b.3, 4b.4: write the major version field down to 44 and up to one past what this runtime writes, then set the minor version to 65535 with and without `--enable-preview`, with `probes/classfile-fuzz` and `java --enable-preview`. Four inputs, four different messages, and one of them is the only check that survives every flag in section 7.
- **5.3** 4a.3, 4c.2: raise `constant_pool_count` by one without adding an entry, then lower it by one, with `java.lang.classfile` and `javap -v`. Any class file javac produced already contains a forward reference from one pool entry to a later one, so the fact that it loads at all is the observation for the ordering half.
- **5.4** 4a.4, 4c.6: append one byte to a class file that loads, and separately cut one byte off the end, with `xxd` and `probes/classfile-fuzz`. Both are refused and the two messages are not the same message.
- **5.5** 4a.5, 4b.12: add an attribute with an invented name and a correct length to a class, a field and a method, and load it, with `java.lang.classfile` and `javap -v`. Nothing happens, which is the whole of the observation, and `javap` shows the attribute is still there.
- **5.6** 4a.6, 4c.3: rename the class in `this_class` without renaming the file, then set `ACC_MODULE` on an ordinary class, with `java.lang.classfile`. Two different error classes for two files that differ in two bytes.
- **5.7** 4a.7, 4b.5: set a reserved access flag bit and load the class, then read the flags back with `Class.getModifiers` and with `javap -v`. The class loads, and the platform's own reader and the reflection API do not agree about what the flags now are.
- **5.8** 4a.8: set `ACC_FINAL` and `ACC_ABSTRACT` together on a class, `ACC_INTERFACE` without `ACC_ABSTRACT`, and `ACC_FINAL` with `ACC_VOLATILE` on a field, with `probes/classfile-fuzz`. All three are refused, and all three messages print the flag word in hexadecimal rather than naming the pair.
- **5.9** 4a.9: put a zero byte inside a `CONSTANT_Utf8_info`, then a byte of `0xf8`, with `probes/classfile-fuzz` and `xxd`. Both are refused, and the same two byte sequences inside a string constant in a source file are not, because what is stored is modified UTF-8 rather than the text.
- **5.10** 4a.10, 4b.9, 4b.14: generate a class with 65535 methods, one with a method body over 65535 bytes, and one whose declared `constant_pool_count` is 65535 with nothing behind it, with `java.lang.classfile` and `java -Xlog:class+load=info`. The first is accepted, the second is refused, and the third is the one that shows what an implementation allocates before it has read anything.
- **5.11** 4a.11, 4b.8, 4b.15: set `max_stack` to zero under a body that pushes two values, and set `max_locals` below the argument count, with `probes/classfile-fuzz`. The specification names `VerifyError` for both and neither one is a `VerifyError`, which is the finding recorded on [the fuzzer's page](../../docs/generated/classfile-fuzz.md).
- **5.12** 4b.6, 4b.7: load the same malformed class file twice, once through the boot class path and once through an ordinary class loader, then load it again under `-javaagent:` with a transformer that returns its input unchanged, with `java -Xbootclasspath/a` and `-XX:+BytecodeVerificationLocal`. The same bytes produce a class in one run and an error in another.
- **5.13** 4b.10, 4b.11: define a class from a `byte[]` while a second thread overwrites the array, then do the same with a direct `ByteBuffer` from a class loader that is not a platform one, with `jshell` and `java.lang.classfile`. The first is a class derived from the array as it was; the second is a copy taken by the platform, so reaching the racing path from Java means going through a loader that the platform trusts.
- **5.14** 4b.13, 4c.1: truncate a class file at eight different offsets, one inside each top level item, with `xxd` and `probes/classfile-fuzz`. Every one of them produces the same sentence, which is what it costs to have one bounds check instead of a check at every read.
- **5.15** 4c.4: define the same class twice through one loader, and write a loader whose `loadClass` asks for the class it is currently defining, with `jshell`. The two errors are different and neither of them is about the bytes.
- **5.16** 4c.5: define a class whose bytes are well formed and whose code does not verify, then wait before using it, with `jshell` and `javap -v`. `defineClass` returns a `Class` object and the `VerifyError` arrives later, which is the observable difference between parsing and verifying.
