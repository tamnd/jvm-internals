# 1. Scope

This blueprint specifies the class file as an input: a finite sequence of bytes handed to a Java Virtual Machine, and everything the machine does to it between receiving it and having a class it can link. It covers the structure those bytes must have, the checks performed while reading them, which error each failed check produces, and the order the checks happen in. An implementation built from this document can take a byte array and either produce an internal class or refuse it with the error a conforming machine would produce.

It covers three things a reader is likely to expect somewhere else. The first is the split between what the specification requires of every implementation and what HotSpot decided on its own, which is section 4 and is the reason the document exists. The second is the error taxonomy: `ClassFormatError`, `UnsupportedClassVersionError` and `NoClassDefFoundError` are all outcomes of parsing, and which one a given broken file produces is a specified fact for some breakages and an implementation choice for others. The third is the boundary between format checking and verification, which the specification draws in one place and HotSpot draws in another, and where those two lines differ is stated here rather than left for somebody to discover.

It deliberately excludes five things. The meaning of each instruction in the code array belongs to BP-BYTECODE. The individual constant pool entry kinds, their tags and the constraints between them belong to BP-CONSTPOOL. The `StackMapTable` attribute's frames and their inference belong to BP-STACKMAP. The type checking of a method body belongs to BP-VERIFY. Everything that happens after a class exists, meaning loading, linking, preparation, resolution and initialization, belongs to BP-LOAD.

Two further exclusions are worth naming because they look as though they belong here. What a compiler chooses to emit is out of scope: this specifies what a machine must accept, and the set of files a compiler happens to produce is a much smaller set. And the on disk container is out of scope as well, so nothing here says anything about jar files, module images or the class path. The input is a byte sequence and where it came from changes nothing about the answer, with the single exception recorded in 4b.10 and 4b.11, where the route into the machine decides whether the bytes are copied first.
