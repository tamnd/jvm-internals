# 7. Configuration

Nothing in section 4a is configurable, and almost everything in 4b is. Which of the two a given behaviour belongs to is the question this section exists to make answerable, because a guarantee that holds under one flag and not another is two facts and both of them are here.

**How much is checked at all.** `BytecodeVerificationLocal` is off by default and `BytecodeVerificationRemote` is on, and the pair decides, per class, from the defining loader, whether the format checks that section 4b marks as conditional run {[HOTSPOT src/hotspot/share/runtime/globals.hpp:455@jdk-27+35]} {[HOTSPOT src/hotspot/share/runtime/globals.hpp:458@jdk-27+35]}. A class loaded by the boot loader in a default configuration is therefore checked less thoroughly than the same bytes loaded by an application loader. Both flags are diagnostic, which means turning them on takes `-XX:+UnlockDiagnosticVMOptions`, and the supported way to move them is `-Xverify`. The full list of what those flags are and where they came from is in [the flag reference](../../docs/generated/flags.md).

**What an agent does to it.** A JVMTI agent registered for the class file load hook forces checking to full for every class it can see {[HOTSPOT src/hotspot/share/classfile/classFileParser.cpp:5392@jdk-27+35]}. This is the configuration change most likely to surprise somebody, because it is not a flag, it is the presence of a `-javaagent` or a native agent, and it can make a class that has loaded in production for years stop loading in a profiling run.

**Preview features.** `--enable-preview` is what makes a minor version of 65535 acceptable, and it is accepted only at this runtime's own major version, so a preview class file cannot be carried forward to the next release the way an ordinary one can {[HOTSPOT src/hotspot/share/classfile/classFileParser.cpp:4387@jdk-27+35]}.

**Which version this runtime writes and reads.** The pinned JDK writes class file major version 71 and reads everything from 45 up to 71. The pinned specification edition describes versions up to 69. Every clause in 4a is quoted from a document that does not describe the file this JDK produces, because no published edition describes it yet, and both numbers are recorded in `docs/pin.json` so the gap is a fact rather than a surprise.

**The cached class.** A class taken from the AOT cache was parsed and verified when the cache was written, and linking it checks the constraints recorded at that time rather than parsing it again {[HOTSPOT src/hotspot/share/oops/instanceKlass.cpp:1075@jdk-27+35]}. An implementation with a cache of its own inherits the obligation that goes with it, which is that the cached form has to be a form only its own parser could have produced, because nothing downstream will check it again.

Two things that look like configuration are not. `-Xlog:class+load` changes what is printed and nothing about what is accepted. And the `java.lang.classfile` API's own validation is a property of the library that writes a class file rather than of the machine that reads one, so a file it refuses to write may still be a file this specification requires a machine to accept.
