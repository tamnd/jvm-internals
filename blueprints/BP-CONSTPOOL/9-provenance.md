# 9. Provenance

Section 2 is generated from [the constant pool page](../../docs/generated/constpool.md), which `tools/gen_constpool.py` builds by joining four sources: the pinned specification edition, the JDK's own `classfile_constants.h.template` for the tag numbers, `constantTag.hpp` and `constantTag.cpp` for the byte as HotSpot holds it, and the pinned JDK's `java.lang.classfile` for the two kinds too rare to find an example of. It is not written here and editing it here has no effect. The generator stops rather than writes when any two of the four disagree, and `tools/test_gen_constpool.py` holds twenty tests, one for each way they can drift.

Every clause in 4a quotes JVMS SE25 and every clause in 4b names a file and a line in `jdk-27+35`. `tools/refcheck.py` resolves both against `docs/citations.json` and fails the build when a line has moved, so a clause that has drifted off its evidence is a broken build rather than a stale sentence.

Four things here are measured rather than read. The 1,216,114 Utf8 entries and their thirty roles, the 127 duplicate entries in 89 class files, the 2,675,920 uses against 1,216,114 entries, and the arithmetic that ties the entry counts to the sum of every `constant_pool_count` field come from `probes/constpool` over `java.base` on two platforms. A different module would give different numbers and none of them is a requirement on anybody. The write up is [the probe's page](../../docs/probes/constpool.md).

The finding in 4b.5 and 4b.6 was read out of four files and has not been demonstrated by running anything. It says that the version dependent loadability rule is enforced in exactly one place, that the place is reachable only below class file version 50, and that this is correct because the lowest threshold in the rule is 49. Producing a class file at version 48 with an `ldc` of a `CONSTANT_Class` would settle it, which is 5.4, and it is the observation in this section most worth doing before anybody relies on the clause.

Three questions this blueprint raises are open. 5.17 is the only unobservable item and it covers the three clauses about memory ordering, which means 8.2.18 is currently a reading of the source rather than a tested property, and closing it needs a `jcstress` test on weakly ordered hardware that has not been written. The pinned JDK reads class file version 71 and the pinned specification edition stops at 69, so a version threshold added between them would be missing from 4a.3 and 4a.4 and nothing here would notice. And 4a.6 is stated as an obligation on an implementation without a clause in the specification that says it in those words, because the specification establishes it by defining every referring structure rather than by prohibiting anything, so it is the clause in 4a most likely to be wrong about what is mandated.

The reviews field in the front matter is null. Nothing in this blueprint has been read by anybody with production experience of a constant pool implementation, and until it has, the conformance list is one person's reading of the specification and not a standard.
