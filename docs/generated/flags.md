# BP-FLAGS. Every flag a product JVM has, and who set it

Generated by `tools/gen_flags.py`. Do not edit it, edit a source. There are two: the 22 HotSpot globals headers at `jdk-27+35` for what is declared, and `probes/vmflags/results` for what a running VM reports. Neither one answers the question on its own.

Measured on java 27+35-2325: darwin-arm64 on 2026-09-06 with 10 processors, linux-aarch64 on 2026-09-06 with 4 processors.

## 1. How a flag is declared

A flag is one line of a macro list in a header. The macro name says which builds have it, the first two arguments are its type and its name, and what follows is the default, any attribute that restricts who may set it, the documentation string the VM prints for `-XX:+PrintFlagsFinal`, and sometimes a range and a constraint function.

| macro | which builds | declared |
|---|---|---:|
| `product` | in every build, and settable on the command line | 856 |
| `product_pd` | in every build, with a default that each platform supplies | 53 |
| `develop` | in a debug build only, and a compile time constant otherwise | 343 |
| `develop_pd` | in a debug build only, with a per platform default | 10 |
| `notproduct` | in a debug build only, and absent rather than constant otherwise | 0 |

One declaration with every optional part in it, at src/hotspot/share/runtime/globals.hpp:134@jdk-27+35

```
product(int, ObjectAlignmentInBytes, 8,
        "Default object alignment in bytes, 8 is minimum")
        range(8, 256)
        constraint(ObjectAlignmentInBytesConstraintFunc, AtParse)
```

The range is checked before the VM starts and the constraint is checked after, which is why setting this flag to a number inside its range can still be refused. Both refusals are measured in section 4.

## 2. What survives into a product build

A header is not a build. These are the same flags counted twice: once as the source declares them for a platform, and once as a JVM on that platform reports them.

| platform | declared for it | reported by it | declared and absent | reported and undeclared |
|---|---:|---:|---:|---:|
| `darwin-arm64` | 1,248 | 805 | 443 | 0 |
| `linux-aarch64` | 1,259 | 816 | 443 | 0 |

The last column is zero and that is a check rather than a claim. Every flag every measured VM reports is declared in one of the headers listed in section 9, and a flag that was not would stop this generator, because it would mean the list is missing a header and every other number here is counted over the wrong set.

Why the declared ones are not in it:

| reason | `darwin-arm64` | `linux-aarch64` | for example |
|---|---:|---:|---|
| a develop flag, which a product build does not compile in | 351 | 351 | `AOTInitTestClass` |
| in a header for a component this build does not contain | 75 | 75 | `ShenandoahAdaptiveInitialConfidence` |
| declared in the `#else` of `#ifndef ASSERT` | 9 | 9 | `DummyManageableStringFlag` |
| declared inside `#if ALLOCATION_FAILURE_INJECTOR` | 8 | 8 | `G1GCAllocationFailureALot` |

The develop flags are the group nobody expects to be able to use. The other groups are the interesting ones, because a header that this build did compile can declare a flag for a component that it did not, and the VM will report that flag as though it were usable. Section 4 has the case where that happens.

## 4. What you are allowed to set

Three of the words the VM prints in its kind column are gates. A `diagnostic` flag needs `-XX:+UnlockDiagnosticVMOptions` before it on the command line, an `experimental` flag needs `-XX:+UnlockExperimentalVMOptions`, and a `manageable` flag is the opposite of a gate: it can be changed while the VM is running. The rest of the words say which compiler or which architecture the flag belongs to.

| kind word | `darwin-arm64` | `linux-aarch64` |
|---|---:|---:|
| `ARCH` | 21 | 21 |
| `C1` | 16 | 16 |
| `C2` | 149 | 149 |
| `diagnostic` | 258 | 264 |
| `experimental` | 73 | 74 |
| `lp64_product` | 4 | 4 |
| `manageable` | 14 | 14 |
| `pd` | 53 | 53 |
| `product` | 460 | 464 |

Unlocking changes nothing about what is listed. The same VM reports 805 flags with no unlock option and 805 with both of them, so a flag being invisible is not what the gate does. What it does is refuse to start.

| what was on the command line | exit | what the VM said |
|---|---:|---|
| `-XX:+NoSuchFlagHere` | 1 | Unrecognized VM option 'NoSuchFlagHere' |
| `-XX:+TraceBytecodes` | 1 | Error: VM option 'TraceBytecodes' is develop and is available only in debug version of VM. |
| `-XX:+PrintInlining` | 1 | Error: VM option 'PrintInlining' is diagnostic and must be enabled via -XX:+UnlockDiagnosticVMOptions. |
| `-XX:+AlwaysSafeConstructors` | 1 | Error: VM option 'AlwaysSafeConstructors' is experimental and must be enabled via -XX:+UnlockExperimentalVMOptions. |
| `-XX:ObjectAlignmentInBytes=7` | 1 | int ObjectAlignmentInBytes=7 is outside the allowed range [ 8 ... 256 ] |
| `-XX:ObjectAlignmentInBytes=9` | 1 | ObjectAlignmentInBytes (9) must be power of 2 |
| `-XX:+UseShenandoahGC` | 1 | Option -XX:+UseShenandoahGC not supported |
| `-XX:+UnlockDiagnosticVMOptions -XX:-PrintInlining` | 0 | nothing, the VM started |

7 refusals and 7 different sentences, which is more than most tools manage. The one worth reading twice is the refusal for a collector. `UseShenandoahGC` is a `product` flag, it is in the table this page counts, `-XX:+PrintFlagsFinal` prints it with a default of false, and the VM will not start with it on. The flag is declared in the shared collector header, which every build compiles, and the collector it turns on is in a header this build left out. That is the difference between the two smaller groups in section 2 made visible from the command line.

## 7. Ranges and constraints

A declared range is checked before the VM starts. A constraint is a function, checked at a named point in startup, and a flag can have either, both or neither.

| | `darwin-arm64` | `linux-aarch64` |
|---|---:|---:|
| reported flags with a range in the header | 295 | 295 |
| reported flags with a constraint in the header | 61 | 61 |
| flags the VM prints bounds for | 325 | 325 |
| declared bounds compared against enforced bounds | 248 | 248 |
| declared bounds written as code this cannot evaluate | 47 | 47 |

Every bound that could be compared matched, which is the check that says the header is being read the way the compiler reads it. A single disagreement stops this generator.
