## 2.1 The ClassFile structure

Every class file is one of these, in this order, with nothing between the items and no padding. `u1`, `u2` and `u4` are unsigned big endian integers of one, two and four bytes. The structure itself is [§4.1](https://docs.oracle.com/javase/specs/jvms/se25/html/jvms-4.html#jvms-4.1).

| item | type | how many | what it is |
|---|---|---|---|
| `magic` | `u4` | 1 | 0xCAFEBABE, and nothing else |
| `minor_version` | `u2` | 1 | 0, except for a preview build, where it is 65535 |
| `major_version` | `u2` | 1 | the class file version, which decides what the rest may contain |
| `constant_pool_count` | `u2` | 1 | one more than the number of usable pool slots |
| `constant_pool` | `cp_info` | `constant_pool_count-1` | indexed from 1, and slot 0 does not exist |
| `access_flags` | `u2` | 1 | the class's own flags, which are not the ones InnerClasses records |
| `this_class` | `u2` | 1 | a CONSTANT_Class index naming this class |
| `super_class` | `u2` | 1 | a CONSTANT_Class index, or 0, which only Object may use |
| `interfaces_count` | `u2` | 1 | how many direct superinterfaces |
| `interfaces` | `u2` | `interfaces_count` | CONSTANT_Class indices, in declaration order |
| `fields_count` | `u2` | 1 | how many fields this class declares, inherited ones excluded |
| `fields` | `field_info` | `fields_count` | one field_info each |
| `methods_count` | `u2` | 1 | how many methods this class declares |
| `methods` | `method_info` | `methods_count` | one method_info each, constructors and the static initialiser included |
| `attributes_count` | `u2` | 1 | how many attributes are attached to the class itself |
| `attributes` | `attribute_info` | `attributes_count` | one attribute_info each, and an unrecognised one must be skipped |

The scanned code answers the first question a reader has about that table, which is what real values look like. 14,909 of the 14,911 class files declare version 71.0, which is what this JDK's own compiler emits.

The rest are worth naming, because a module built entirely by one compiler in one release is what a reader would assume and it is not what is there. Two of them are at version 52.0, which is `jdk/internal/module/SystemModulesMap`.

The pinned JDK's class file API models every one of the 30 attributes the specification defines. Everything else it hands back as an `UnknownAttribute`, which is the correct behaviour rather than a gap: an attribute a reader does not recognise has to survive a round trip untouched, and a library that parsed one it did not understand could not promise that.

It also models six more that the specification does not define, `CharacterRangeTable`, `CompilationID`, `ModuleHashes`, `ModuleResolution`, `ModuleTarget`, `SourceID`. Those are the extension mechanism being used rather than described: anybody may define an attribute, the JDK's own tools have, and a reader who meets one in a class file has met somebody else's convention rather than a corrupt file.

Six of the 36 may appear more than once on the same element: `CharacterRangeTable`, `Deprecated`, `LineNumberTable`, `LocalVariableTable`, `LocalVariableTypeTable`, `Synthetic`. Every other one is at most one per element, so a parser that keeps the last of each is right about the rest of the format and wrong about these.

Each one also says what happens to it when a class file is rewritten, which is the question a reader hits the moment they stop reading class files and start producing them. 25 of them hold constant pool references, which a transform has to remap. Five of them hold offsets into a method body, which a transform has to move. Four of them can be copied byte for byte. Two of them cannot be copied safely, so a transform that changes the class drops them.

The unstable ones are `RuntimeInvisibleTypeAnnotations`, `RuntimeVisibleTypeAnnotations`. They carry both constant pool references and offsets into code, so there is no rule that keeps them correct across an edit, and the library says so rather than preserving them and hoping.

Nothing in the scanned code came back as an unknown attribute, so every attribute the JDK's own compiler emitted into its own runtime image is one the JDK's own class file library models.

## 2.4 The access flags

There are four separate flag tables in the specification and they assign different meanings to the same bits, which is the single most common way a hand written class file parser goes wrong. 0x0020 is `ACC_SUPER` on a class and `ACC_SYNCHRONIZED` on a method. 0x0040 is `ACC_VOLATILE` on a field and `ACC_BRIDGE` on a method. 0x0080 is `ACC_TRANSIENT` on a field and `ACC_VARARGS` on a method. A bit means nothing until you know which structure you are reading it out of.

### Bits that are set and should not be

JVMS [§4.1](https://docs.oracle.com/javase/specs/jvms/se25/html/jvms-4.html#jvms-4.1) says the flag bits it does not assign are reserved, should be zero in a generated class file, and should be ignored by a JVM. The scanned code does not obey the first half of that, and finding out took a count rather than an argument.

| where | bit | how many | for example |
|---|---|---:|---|
| `ClassFile` | `0x0002` | 8 | `java/lang/invoke/DelegatingMethodHandle$Holder`, `java/lang/invoke/DirectMethodHandle$Holder`, `java/lang/invoke/Invokers$Holder`, `java/lang/invoke/LambdaForm$Holder` |

That is the specification's own advice working as intended. A JVM that rejected these would reject its own runtime image, and a parser somebody writes while reading section 2 will meet them on its first real input.
