`wide` has no constant in the class file API, which folds the prefix into the opcode value of the twelve instructions that can take it.

The three numbers differ for two reasons and neither is a mistake. HotSpot defines 36 codes above the last one the specification names, which it writes into a method's bytecode after the class file has been parsed, so they exist in memory and can never exist in a file. The class file API drops `wide` and `breakpoint` and adds twelve wide forms, which is a different way of modelling the same bytes.

## 3.2 Every opcode a class file may contain

Length is the whole instruction in bytes, opcode included. Stack is what the instruction does to the depth of the operand stack, as HotSpot's own table records it. Seen is how many times it occurs in the scanned code above, which is the column that says which of these a reader will actually meet.

The operands column is HotSpot's format string put into words, and it describes a method already loaded into a VM rather than the bytes on disk. That is why nine of these say native order: HotSpot rewrites those operands when it links the method, replacing the constant pool index the file carries with an index into its own resolved cache, in the byte order of the machine. In the class file itself every one of them is a big endian constant pool index, which is what to write when building one by hand and what `javap` shows. The ones that differ are `getfield`, `getstatic`, `invokedynamic`, `invokeinterface`, `invokespecial`, `invokestatic`, `invokevirtual`, `putfield`, `putstatic`.

## 3.3 The twelve instructions `wide` can be applied to

`wide` is a prefix rather than an instruction. It takes the one byte operand of the instruction after it and makes it two, and for `iinc` it makes both operands two. Never once, in 3,902,996 instructions:

`aload_w`, `astore_w`, `dload_w`, `dstore_w`, `fload_w`, `frem`, `fstore_0`, `fstore_w`, `goto_w`, `iload_w`, `istore_w`, `jsr`, `jsr_w`, `lload_w`, `lstore_w`, `nop`, `ret`, `ret_w`, `swap`

That list is the useful half of this section. `jsr`, `jsr_w`, `ret` and `ret_w` are the four no compiler has emitted since 1.4 and the four the verifier's type checking rules were rewritten so as not to need. `goto_w` never occurs, which means no method body in the scanned code branches further than a two byte offset reaches. The highest local variable slot any instruction anywhere in it names is 142, which is why eleven of the twelve wide forms never occur.

The exception is worth its own sentence, because it is the thing a table of opcode lengths will not tell you. The wide form that does occur is `iinc_w`, whose highest slot is 16. `wide` widens both operands of `iinc`, and the increments in the scanned code run from -1,075 to 2,000, so what needed the extra bytes was the constant rather than the slot.

The remaining four, `frem`, `fstore_0`, `nop`, `swap`, are ordinary instructions that are legal, that the class file API will write, and that nothing in the scanned code happens to contain. That is a fact about one compiler's output for one module rather than a fact about the instruction set, and it is the reason this section counts rather than asserts.
