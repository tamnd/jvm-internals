The specification prints twelve structures for those seventeen kinds, because `CONSTANT_Integer` and `CONSTANT_Float` are one shape; `CONSTANT_Long` and `CONSTANT_Double` are one shape; `CONSTANT_Fieldref`, `CONSTANT_Methodref` and `CONSTANT_InterfaceMethodref` are one shape; `CONSTANT_Dynamic` and `CONSTANT_InvokeDynamic` are one shape. That is the first thing a reader of a hex dump has to hold on to: the tag is not a hint about the payload, it is the only thing that distinguishes two entries that are byte for byte the same length and shape.

The numbering has three holes in it, at 2, 13, 14. Tag 2 is `CONSTANT_Unicode` in `src/java.base/share/native/include/classfile_constants.h.template`, marked unused, which is the JDK remembering a kind the format never shipped. Tags 13 and 14 were never assigned at all. A parser that switches on the tag needs a default branch for them rather than an array indexed by tag, which is the mistake the holes exist to catch.

One of the seventeen kinds does not occur anywhere in the scanned code: `CONSTANT_Dynamic`. The row above is still measured rather than retyped, because the probe builds one entry of every kind through `java.lang.classfile` and reads the platform's own answer back. A table that could only describe the kinds that happened to be in `java.base` would be a table about `java.base`.

## 2.2 Why constant_pool_count is one more than the number of entries

There is no entry at index 0, and a `CONSTANT_Long` or a `CONSTANT_Double` takes two slots with nothing usable in the second one. Both of those are in the count, and the arithmetic is checkable rather than quotable: over the scanned code, 2,139,699 entries plus 14,951 second slots plus 14,911 missing slot zeroes is 2,169,561, and the sum of every `constant_pool_count` field is 2,169,561. This generator refuses to write the page if those two numbers differ.

The largest pool in the scanned code has 6,022 slots and belongs to `sun/util/resources/cldr/LocaleNames_en`. The 16 bit count is a real limit rather than a theoretical one: a class needs 59,513 more entries than that one has before it stops being expressible, and a generated class or a very large switch gets there.

## 2.3 Which of them `ldc` can load

A loadable constant is one that `ldc`, `ldc_w` or `ldc2_w` can push onto the stack, which is nine of the seventeen kinds. The specification lists them in table 4.4-C with a class file version against each, the class file API marks them with a `LoadableConstantEntry` supertype, and HotSpot has a predicate. All three agree about which kinds, and this generator refuses to write the page if they stop agreeing.

|---:|---|---:|---:|---|---:|
| 3 | `CONSTANT_Integer` | 45.3 | 1.0.2 | an `int` | 23,607 |
| 4 | `CONSTANT_Float` | 45.3 | 1.0.2 | a `float` | 189 |
| 5 | `CONSTANT_Long` | 45.3 | 1.0.2 | a `long` | 12,088 |
| 6 | `CONSTANT_Double` | 45.3 | 1.0.2 | a `double` | 2,863 |
| 7 | `CONSTANT_Class` | 49.0 | 5.0 | a reference | 172,787 |
| 8 | `CONSTANT_String` | 45.3 | 1.0.2 | a reference | 109,113 |
| 15 | `CONSTANT_MethodHandle` | 51.0 | 7 | a reference | 5,542 |
| 16 | `CONSTANT_MethodType` | 51.0 | 7 | a reference | 3,620 |
| 17 | `CONSTANT_Dynamic` | 55.0 | 11 | whatever the bootstrap method returns | 0 |

The last column but one is HotSpot's, from `constantTag::basic_type`, which is the function that decides what an `ldc` of an entry leaves on the stack. `CONSTANT_Dynamic` is the one it will not answer for, because a dynamic constant has whatever type its bootstrap method produced and there is nothing in the entry to read it off.

The version column is the disagreement worth knowing about. The specification makes loadability depend on the class file version, and the nine kinds became loadable across four different versions: five of them at 45.3, `CONSTANT_Class` at 49.0, `CONSTANT_MethodHandle` and `CONSTANT_MethodType` at 51.0, `CONSTANT_Dynamic` at 55.0. HotSpot's `is_loadable_constant` is a comparison against the tag byte and nothing else, so it answers the same way for a version 45 class file as for a version 71 one. The check that a class file older than version 49 may not `ldc` a `CONSTANT_Class` lives in the verifier and in the class file parser rather than here, which is worth knowing before reading either.

The other eight cannot be pushed at all: `CONSTANT_Utf8`, `CONSTANT_Fieldref`, `CONSTANT_Methodref`, `CONSTANT_InterfaceMethodref`, `CONSTANT_NameAndType`, `CONSTANT_InvokeDynamic`, `CONSTANT_Module`, `CONSTANT_Package`. Some of them are structure rather than value, and `CONSTANT_InvokeDynamic` is the interesting exclusion, because it names a call site rather than a constant and `invokedynamic` is the only instruction that may refer to one.

## 2.4 What HotSpot puts in the tag byte

The tag byte in a class file has seventeen legal values. The tag byte in memory has more, because HotSpot reuses the field to record where the entry is in its own life cycle. A class is parsed with its class references unresolved, they become resolved as the code that needs them runs, and a resolution that threw keeps the exception rather than being retried. All three of those states are the same byte.

| value | name | what HotSpot calls it | what it is |
|---:|---|---|---|
| 0 | `Invalid` | `Invalid index` | For bad value initialization |
| 100 | `UnresolvedClass` | `Unresolved Class` | Temporary tag until actual use |
| 101 | `ClassIndex` | `Unresolved Class Index` | Temporary tag while constructing constant pool |
| 102 | `StringIndex` | `Unresolved String Index` | Temporary tag while constructing constant pool |
| 103 | `UnresolvedClassInError` | `Unresolved Class Error` | Error tag due to resolution error |
| 104 | `MethodHandleInError` | `MethodHandle Error` | Error tag due to resolution error |
| 105 | `MethodTypeInError` | `MethodType Error` | Error tag due to resolution error |
| 106 | `DynamicInError` | `Dynamic Error` | Error tag due to resolution error |

Every one of those except `Invalid` is at 100 or above and none is past 106, and the format's own tags stop at 20, so a value HotSpot invented can never be mistaken for a tag a class file may contain. `Invalid` is the value a freshly constructed tag has, which is how a partly built pool is distinguishable from a finished one.

Four kinds can fail to resolve, and each one has its own error tag rather than a shared one, so the failure that is remembered is a failure of the right kind: `Dynamic` becomes `DynamicInError`, `MethodHandle` becomes `MethodHandleInError`, `MethodType` becomes `MethodTypeInError`, `UnresolvedClass` becomes `UnresolvedClassInError`. A second attempt to use the entry throws the same exception it threw the first time rather than running the resolution again, which is the behaviour the specification requires and the reason the tag has to carry the error at all.

The predicates that accept more than one tag are the ones worth reading, because each is a question the rest of the VM asks about an entry, and together they are the vocabulary HotSpot has for talking about a pool.

| predicate | accepts |
|---|---|
| `has_bootstrap` | `Dynamic`, `InvokeDynamic`, `DynamicInError` |
| `is_field_or_method` | `Fieldref`, `Methodref`, `InterfaceMethodref` |
| `is_in_error` | `UnresolvedClassInError`, `MethodHandleInError`, `MethodTypeInError`, `DynamicInError` |
| `is_klass_or_reference` | `Class`, `UnresolvedClass`, `ClassIndex`, `UnresolvedClassInError` |
| `is_klass_reference` | `UnresolvedClass`, `ClassIndex`, `UnresolvedClassInError` |
| `is_loadable_constant` | `Integer`, `Float`, `Long`, `Double`, `Class`, `String`, `MethodHandle`, `MethodType`, `Dynamic`, `UnresolvedClass`, `UnresolvedClassInError` |

## 2.6 Method handles

A `CONSTANT_MethodHandle` is a reference kind and an index, and the reference kind decides both what the handle does and what kind of entry the index is allowed to point at. [§4.4.8](https://docs.oracle.com/javase/specs/jvms/se25/html/jvms-4.html#jvms-4.4.8) states that as a constraint per kind, and it is the constraint a hand written class file gets wrong first.

|---:|---|---|---|---|
| 1 | `JVM_REF_getField` | reads an instance field | `FieldRefEntry` | 844 at `FieldRefEntry` |
| 2 | `JVM_REF_getStatic` | reads a static field | `FieldRefEntry` |  |
| 3 | `JVM_REF_putField` | writes an instance field | `FieldRefEntry` |  |
| 4 | `JVM_REF_putStatic` | writes a static field | `FieldRefEntry` |  |
| 5 | `JVM_REF_invokeVirtual` | calls a virtual method | `MethodRefEntry` | 771 at `MethodRefEntry` |
| 6 | `JVM_REF_invokeStatic` | calls a static method | `InterfaceMethodRefEntry` or `MethodRefEntry` | 137 at `InterfaceMethodRefEntry`, 3,376 at `MethodRefEntry` |
| 7 | `JVM_REF_invokeSpecial` | calls a private or a superclass method | `InterfaceMethodRefEntry` or `MethodRefEntry` |  |
| 8 | `JVM_REF_newInvokeSpecial` | calls a constructor | `MethodRefEntry` | 112 at `MethodRefEntry` |
| 9 | `JVM_REF_invokeInterface` | calls an interface method | `InterfaceMethodRefEntry` | 302 at `InterfaceMethodRefEntry` |

Only five of the nine occur in the scanned code, at 1, 5, 6, 8, 9. Reference kind 6 is the one to look at: it points at a `MethodRefEntry` and at an `InterfaceMethodRefEntry`, both of which are legal, because class file version 52 allowed a static or private interface method to be the target of a handle and the specification states that as a version condition on this one row. A reader who takes the constraint as `Methodref` alone will reject a class file that every JVM accepts.

The other two kinds that name a bootstrap method are counted the same way, and they are lopsided: 4,500 `CONSTANT_InvokeDynamic` call sites against 0 `CONSTANT_Dynamic` constants. Both hand a name and a type to a bootstrap method, and the difference is what comes back. A call site is linked once and then keeps calling a target that may change, while a dynamic constant is computed once and then is a value forever. The compiler that built the scanned code emits the first and not the second, which is worth knowing before reading a class file looking for one.

## 2.7 The same constant twice

A pool is supposed to be a set. Nothing in the format requires it to be, and a class file with two entries that mean exactly the same thing is legal, loads, and runs. In the scanned code 89 classes hold at least one repeat, 127 entries in total, which is <0.01% of the pool. The probe finds them by rendering each entry to the thing it means and looking for two that render the same, which is a different test from comparing bytes.

| tag | kind | repeats | for example |
|---:|---|---:|---|
| 10 | `CONSTANT_Methodref` | 28 | `java/lang/invoke/VarHandle.weakCompareAndSet:(Ljava/util/concurrent/ConcurrentLinkedDeque;Ljava/util/concurrent/ConcurrentLinkedDeque$Node;Ljava/util/concurrent/ConcurrentLinkedDeque$Node;)Z` in `java/util/concurrent/ConcurrentLinkedDeque` |
| 11 | `CONSTANT_InterfaceMethodref` | 99 | `java/util/List.toString:()Ljava/lang/String;` in `apple/security/KeychainStore` |

Every repeat in the scanned code is one of two things, and both are the compiler being unable to see that two references are the same. The first is a method `java.lang.Object` declares, called on a receiver whose static type is an interface: `equals`, `getClass`, `hashCode`, `toString`. Those are 99 of the repeats. An interface does not declare them, so each call site names them on the interface it is calling through, and two different interfaces in one class produce two entries that a reader would call the same call.

The second is a signature polymorphic call, on `java/lang/invoke/VarHandle`, which is 28 of them. A signature polymorphic method has whatever descriptor the call site says it has, so two call sites with the same descriptor produce two entries only when something else about them differs, and the compiler does not look. This is the case where the duplicate is arguably load bearing: the descriptor is the argument.

The scanned images are not identical, and the repeats say so: `apple/security/KeychainStore` is only in `osx-arm64`. That is a platform specific class rather than a platform specific compiler, and it is the reason the counts here are sums over environments rather than one environment's answer.
