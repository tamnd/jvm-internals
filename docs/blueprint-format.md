# The blueprint format

A blueprint is the normative half of this project. A lesson shows somebody a thing happening; a blueprint says what the thing is, precisely enough that a person who has never read the lesson can implement it. The capstones in M11 are built from the blueprints and from nothing else, and every defect a track finds is filed against a clause number and fixed there, so a blueprint that is vague or that blurs the specification into the implementation is the one kind of defect this project cannot absorb.

`bpc` is the blueprint compiler. It is to a blueprint what `tools/build.py` is to a lesson: the source is a directory of hand written sections, the output is one committed page nobody edits, and `bpc check` rebuilds in memory and refuses any difference.

## The directory

```
blueprints/BP-CLASSFILE/
  blueprint.md    front matter, and nothing else
  1-scope.md      one file per section, numbered 1 to 9
  2-structure.md
  ...
  9-provenance.md
docs/blueprints/BP-CLASSFILE.md    generated by tools/bpc.py, committed, never hand edited
```

The slug after the number is for whoever is looking at the directory listing. The number is what decides the section, so renaming a file does not renumber anything and cannot silently move a clause.

## Front matter

`blueprint.md` holds a fenced block and nothing else. The parser is the same small subset of YAML the lesson format accepts: a flat mapping of scalars, `key: [a, b]` lists, and one level of nesting written with two spaces.

```markdown
---
id: BP-CLASSFILE
title: The class file
pin: jdk-27+35
edition: SE25
status: draft
lessons: [B01, B11]
reviews:
  expert: null
---
```

`id` has to match the directory name, `pin` has to match `jdk_tag` in `docs/pin.json` and `edition` has to match `jvms_edition`, so a blueprint written against a tag nobody pinned fails the build rather than shipping. `status` is `draft` or `final`. A draft may have unreviewed clauses and is marked as a draft on its own page; nothing else about the checks is relaxed, because a draft specification that does not typecheck is not a draft, it is a note.

## The nine sections

| | Section | What goes in it |
|---|---|---|
| 1 | Scope | What this blueprint covers and what it deliberately excludes, naming the blueprint that owns each exclusion |
| 2 | Data structures | The layout of the thing: fields, types, sizes, offsets, and what may hold what. Generated wherever a source exists |
| 3 | Operations | What can be done to it, as operations with inputs, outputs and failures |
| 4 | Guarantees | The clauses. 4a is what the JVMS mandates, 4b is what HotSpot chose, 4c is the ordering obligations |
| 5 | Observation | For every clause, how somebody watches it happen and with which tool |
| 6 | Edge cases | Malformed input, resource exhaustion and the concurrent case, at minimum |
| 7 | Configuration | Every flag, version and build time choice that changes any of the above |
| 8 | Conformance | 8.1 what an implementation has to do to claim conformance. 8.2 the checklist |
| 9 | Provenance | Which sections are generated and from what, and what this blueprint does not settle |

The order they are read in is not the order they are written in. Section 6 is written before section 3, because an operation designed without its failures is an operation that will grow them later in the wrong places, and the whole reason this format exists is that the failures are where the JVM actually lives.

Section 7 is its own section rather than a note inside the others because almost everything in this material is configuration dependent. A guarantee that holds under one flag and not another is two facts, and a format that has nowhere to put the second one gets the first one written down as though it were unconditional.

A section may be empty only if it says why, in a single line:

```markdown
# 7. Configuration

<!-- empty: no product flag changes anything in this blueprint, and the two that -->
<!-- look as though they might are in BP-BYTECODE section 7 instead. -->
```

Sections 1 through 6 and section 8 may never be empty. An empty section 4 is a blueprint with no content, an empty section 5 is a set of claims nobody can watch, and an empty section 8 is a specification that cannot be tested, which are the three failures this format exists to prevent.

## Clauses

Sections 4, 5 and 8.2 are lists of numbered clauses. A clause is one line.

```markdown
- **4a.1** The first four bytes of a class file are `0xCAFEBABE` {[JVMS §4.1@SE25]}.
- **4b.4** The argument count is checked against `max_locals` in the parser rather than in the verifier {[HOTSPOT src/hotspot/share/classfile/classFileParser.cpp:2290@jdk-27+35]}.
```

The marker is the one the lessons use, so a clause and a claim ledger entry cite a thing the same way and one grep finds both. The number is permanent. Clauses are numbered in order within their subsection, gaps are allowed and a retired number is never reused, because a capstone's defect report cites `BP-CLASSFILE 4a.7` and a renumbering would silently move what that means.

`bpc check` enforces the split, which is the whole point of the section:

| Subsection | Markers it must have | Markers it may not have |
|---|---|---|
| 4a | At least one `{[JVMS ...]}` | Any `{[HOTSPOT ...]}` |
| 4b | At least one `{[HOTSPOT ...]}` | Any `{[JVMS ...]}` |
| 4c | At least one of either | Neither is forbidden, and a clause with both is a clause about two things |

A 4a clause carrying a source citation is the failure this project is most likely to make and the one that would make it worse than useless, because it reads as "Java guarantees this" and cites a line of C++ that could change next release. The mixed clause everybody wants to write is "the specification leaves this open and HotSpot chose that", and it is two clauses: a 4a one saying what is not mandated, citing the section that does not mandate it, and a 4b one saying what was chosen, citing the line that chose it. Writing it as one is how the distinction gets lost, and the split is the thing this project exists to keep.

4c is the exception because an ordering obligation is a relation between two things, and the two things can come from different sides. A clause saying the constant pool is read before anything that indexes into it is mandated by the specification and also a fact about the parser's loop, and splitting it would produce two half sentences neither of which states the obligation.

## Observation and coverage

A section 5 item names the clauses it observes, then says how, with at least one tool in backticks:

```markdown
- **5.2** 4a.1, 4b.3: patch the first byte and load the class, with `probes/classfile-fuzz` and `javap -v`
```

A behaviour that cannot be watched says so and says why, in the same shape the claim ledger uses:

```markdown
- **5.9** 4b.7: unobservable. The copy happens inside the VM and nothing on either side of it is visible to Java code.
```

A section 8.2 item names the clauses it tests, in the same way, and says what a conforming implementation has to do:

```markdown
- **8.2.4** 4a.1, 4a.2: rejects a file whose first four bytes are anything else, before reading the version
```

Every clause in section 4 has to be named by at least one section 5 item and at least one section 8.2 item. That is the check the reserved `bpc` CI job describes as no coverage item being unowned, and it is why the format numbers clauses at all: a specified behaviour nobody can observe and no harness tests is a sentence, not a specification.

`bpc build` writes every 8.2 item of every blueprint into `docs/generated/conformance.json`, which is what the M11 capstone harness reads. A track reports a pass, a fail or a skip per item id, and a defect it files carries the clause numbers that item covers.

## Generated sections

A generated section is a file with one line in it:

```markdown
<!-- generated: docs/generated/classfile.md -->
```

Writing anything else in that file is an error rather than something ignored. The build would overwrite it, and a hand written paragraph that disagrees with the table above it is exactly the failure the split exists to prevent.

The page it points at declares which blueprint and which section it is in its own first line, and `bpc` refuses it if that line disagrees:

```markdown
# BP-CLASSFILE section 2. The structure of a class file
```

The title after the full stop becomes the section title in the built blueprint, so the two documents cannot drift apart on what the section is called. Every heading in the included body is demoted by one level, and nothing else about it is touched.

A link written inside a section file has to resolve from two places at once, and one rule makes that free. A section file is `blueprints/BP-X/4-guarantees.md` and the page built from it is `docs/blueprints/BP-X.md`, so both are two directories below the repository root, and a relative link that starts `../../` resolves to the same file from either one. So a section links to a generated page as `../../docs/generated/flags.md` and to a lesson as `../../lessons/O01/lesson.py`, the link checker follows it in the source and in the built page, and neither copy needs rewriting at build time. The one link `bpc` writes itself is the note at the top of an included section, which is relative to `docs/blueprints/` because that is the only place it appears.

Nothing hand written may duplicate a generated section. `bpc check` reads the first column of every table in the generated sections, and a hand written section that has a table row whose first cell repeats one of those keys fails. Naming a generated item in a sentence is fine and is often the only way to write a clause. Retyping the table is what gets caught, because a retyped table is the thing that will still say `u2 max_stack` in 2029 when the generated one next to it has moved on.

## What check enforces

Beyond the byte comparison against what is committed:

- Nine section files, numbered 1 to 9, with no gaps and no extras
- Every section starts with `# N. Title`, except a generated one, which starts with its directive
- An empty section is only sections 7 or 9, and it gives a reason of at least forty characters
- Section 4 has 4a, 4b and 4c, each with at least one clause
- The marker and citation split above, per subsection
- Clause ids unique, in order, and inside their own subsection
- Every clause named by a section 5 item and a section 8.2 item, and every 5 and 8.2 item naming a clause that exists
- Section 6 has a paragraph for malformed input, resource exhaustion and the concurrent case, found by heading
- No hand written table row repeating a generated table's key
- No reference to a chapter, a lesson, or an analogy, by the phrase list in `tools/bpc.py`
- The front matter pin and edition agreeing with `docs/pin.json`

The phrase list is short and it is a floor rather than a ceiling. No machine can tell that a paragraph is motivating rather than specifying, so that stays a review question, and the expert review is where it is answered.

## The commands

```
python tools/bpc.py new BP-CONSTPOOL     scaffold a blueprint, nine sections, each saying it is empty
python tools/bpc.py build                compile every blueprint into docs/blueprints/
python tools/bpc.py check                rebuild in memory and fail on any difference
python tools/bpc.py list                 print every blueprint, its sections and its clause count
python tools/bpc.py coverage             print every clause and what observes and tests it
```

`build` also writes `docs/generated/conformance.json`. `check` compares it too, so an 8.2 item added without a rebuild fails in CI rather than leaving the harness reading a checklist that is one item short.

## Why the output is committed

The built page is redundant, in the sense that a script can produce it from the sources at any time. It is committed anyway, for the same reason `notebooks/` is: somebody reading this repository on the web, or a capstone author six months from now, should see the whole blueprint as one document without running anything. The check is what makes that safe, and the rule that the output is never hand edited is what makes the check meaningful.
