## 1. Scope

This blueprint specifies the verifier's type system: the fourteen verification types, the relation that decides which of them may stand where another is expected, the lifting of that relation from one type to a whole frame, and the class file versions that decide whether the relation is consulted at all. An implementation built from this document can answer, for any two verification types and a class hierarchy, whether the first is assignable to the second, and can answer the same question for two frames, which is the question every type rule for every instruction ends in and none of them contains.

It covers three things a reader is likely to expect somewhere else. The first is that answering the question can load a class, throw, or be deferred to a later run, so `assignable` is not a pure function of two types and cannot be tabulated in advance for anything but the atoms. The second is the frame level relation, which BP-STACKMAP explicitly hands over: two frames are compared pointwise, but only after their shapes are compared, and the shape comparison is an equality rather than a bound. The third is which of the machine's two verifiers answers, because a refusal by the one this document describes is not final at every class file version, and a conformance suite that does not know that will record passes it did not earn.

It deliberately excludes four things. The type rule for each individual instruction belongs to BP-BYTECODE: this document says what it means for `int` to be assignable to `top` and says nothing about which instruction asks. The encoding of a frame into bytes belongs to BP-STACKMAP, so the seven frame kinds, the delta arithmetic and the tag of a `verification_type_info` are all out of scope and this document begins with frames already decoded. The dataflow over the code array, which decides which frames are compared with which, belongs to BP-BYTECODE as well. And the inference verifier of JVMS 4.10.2 is out of scope entirely: it appears here only as the place a refused class is sent at one range of versions, and what it does when it gets there is not specified in this document.

Two further boundaries are worth naming because they look like exclusions and are not. Loading is in scope up to the point where the relation needs it: a reference to reference pair that is not settled by name, by `null` or by `java.lang.Object` requires both classes loaded, which makes 4c.2 an ordering obligation of this document rather than a note about somebody else's. And the run time checks that make the accepted half of the relation sound are in scope as an obligation rather than as behaviour: an implementation that accepts what 4a.4 requires it to accept and then omits the check `invokeinterface` makes has built an unsound machine out of a conforming verifier, which is the one way to fail this blueprint by following it.

### What kind of relation this is

Everybody who writes about a type hierarchy assumes an order, and an order is reflexive, transitive and antisymmetric. This one is reflexive on all sixteen types and it is neither of the other two.

It is not transitive. Nine triples have `a` assignable to `b` and `b` assignable to `c` and `a` not assignable to `c`:

- `Object[]` to `Object` to `Runnable`
- `Object[]` to `Cloneable` to `Runnable`
- `Object[]` to `Serializable` to `Runnable`
- `String[]` to `Object` to `Runnable`
- `String[]` to `Cloneable` to `Runnable`
- `String[]` to `Serializable` to `Runnable`
- `int[]` to `Object` to `Runnable`
- `int[]` to `Cloneable` to `Runnable`
- `int[]` to `Serializable` to `Runnable`

It is not antisymmetric. Six unordered pairs are assignable both ways, which closes into one group of types the verifier cannot tell apart:

- `Object`, `Runnable`, `Cloneable`, `Serializable`

So it is a preorder. The largest group has four members and it contains `java.lang.Object`, which is the finding: to the verifier's type system, `Object` and an interface are the same type.

## 3. Operations

There are three public operations. The first is the relation itself, the second lifts it to a whole frame, and the third decides whether either of them is consulted for a given class. The third is listed here rather than left to a configuration note because a machine that answers it wrongly is a machine whose answers to the other two never reach anybody.

**assignable(from, to, context) returns yes or no, or fails.** `from` and `to` are verification types. `context` supplies the class being verified, which is where the loader comes from, and access to class loading. The result is whether a value described by `from` may occupy a location declared to hold `to`. It is not a pure function of its first two arguments: for a pair of distinct reference types it may load a class, and loading a class may fail, in which case the operation does not return an answer at all.

**frameAssignable(from, to) returns yes or no, or fails.** Both arguments are frames, each a locals array, an operand stack and a flag saying whether any local holds `uninitializedThis`. The result is whether the state described by `from` satisfies everything `to` requires. It calls `assignable` once per position and inherits its failure mode.

**verifierFor(major) returns which verifier answers, and whether its refusal is final.** Its input is the class file major version and the configuration. Its output decides whether `assignable` is consulted for the class at all, and whether a refusal from it ends the load. There is no per class file version behaviour anywhere else in this document, and all of it is here.

The steps of `assignable` run in the order given. Each may assume every earlier step did not return.

**3.1 identical, or the target is `top`.** If the two types are equal, the answer is yes, which is where reflexivity comes from. If `to` is `top`, the answer is yes, and these are the only two rules that need neither type to be a reference nor either class to be loaded.

**3.2 one is a primitive.** If either type is `int`, `float`, `long` or `double` and 3.1 did not fire, the answer is no. There is no widening between primitive verification types, so `int` to `long` is refused and so is `float` to `double`, and an implementation that reuses a language level widening table here is wrong on four pairs.

**3.3 either is uninitialized.** `uninitializedThis` and `uninitialized(Offset)` reach `top` by 3.1 and nothing else. In particular neither is assignable to `java.lang.Object`, so an implementation that treats them as references in this operation accepts a frame that reads an unconstructed object as a constructed one.

**3.4 the source is `null`.** If `from` is `null` and `to` is a class type or an array type, the answer is yes. This is the only rule that crosses from an atom into the reference hierarchy.

**3.5 the target is `null`.** If `to` is `null` and 3.1 did not fire, the answer is no. Nothing widens to `null`.

**3.6 both are references, or the answer is no.** If either type is not a class type or an array type, everything above has already decided it, and the answer here is no. Everything below assumes two distinct reference types.

**3.7 the same name.** If the two names are equal, the answer is yes. Whether the two loaders are also compared is 4a.6 and 4b.7, and it is the one place in this operation where the specification and the pinned implementation are describing different objects.

**3.8 the target is `java.lang.Object`.** The answer is yes for every reference type, including every array type. This is decided by name and loads nothing.

**3.9 the target is an interface.** Load the target. If it is an interface, then the answer is yes when `from` is a class type, whatever class it is, and yes when `from` is an array type only if the target is `java.lang.Cloneable` or `java.io.Serializable`. The source is never loaded and its hierarchy is never consulted, and 4a.4 is why. An implementation that checks whether `from` implements the interface here is stricter than this document and does not conform.

**3.10 both are class types.** Load both and answer whether the target is one of the source's superclasses. This is the only step that walks a hierarchy and the only one whose cost is unbounded by the two types alone.

**3.11 both are array types.** Take the component of each and ask `assignable` about the components, with one change: two primitive components are assignable only when identical, so an array of `byte` does not satisfy an array of `int` even though `byte` is described by the verification type `int`. A component that cannot be parsed out of the signature is not an error and makes the answer no.

**3.12 anything else.** The answer is no. An array is not assignable to a class type other than the three of 3.8 and 3.9, a class type is not assignable to an array type, and there is no case left.

The steps of `frameAssignable` run in the order given, and 3.13 and 3.14 both run before any type is compared.

**3.13 compare the widths.** The two locals arrays have to be the same length. This is an equality and not a bound, because the length is fixed for a method by construction, and an implementation that accepts a target with fewer locals has accepted a frame that says nothing about the rest.

**3.14 compare the stack depths.** The two operand stacks have to be the same depth. This is the check the specification states explicitly, on the grounds that the stack is the one part of a frame whose length is not fixed in advance.

**3.15 compare the locals pointwise.** For each position, `assignable` from the source's type to the target's type. Fails at the first position that refuses, and the position it reports is the location index rather than the local variable index, so the second half of a `long` counts.

**3.16 compare the stack pointwise.** The same, over the operand stack.

**3.17 compare the flags.** The source's flags have to be a subset of the target's. A frame in which `this` is still unconstructed is not assignable to one in which it is constructed, and the reverse is allowed, which is what makes a constructor's merge points work.

The steps of `verifierFor` run in the order given.

**3.18 decide whether to verify at all.** A class whose defining loader the configuration excludes is not verified, and none of 3.1 to 3.17 runs for it. This is a configuration question and section 7 is where the answer lives.

**3.19 choose a verifier by class file version.** At major version 50 and above, the type checking verifier described by this document answers. Below 50, it never runs and the inference verifier of JVMS 4.10.2 answers instead, so nothing in this document applies to those files.

**3.20 decide whether a refusal is final.** At major version 51 and above, a refusal ends the load. At 50 exactly, a refusal of kind `VerifyError` or `ClassFormatError` sends the class to the inference verifier, and if that verifier accepts it the class loads and nothing is reported. An implementation with one verifier refuses at 50 as well, which is a difference from the pinned machine that 8.2.19 requires it to state rather than to remove.

Steps 3.1 to 3.17 are the whole of what this document specifies about accepting or refusing. They establish that a value of one type may occupy a location declared to hold another, and they establish nothing about whether the object at run time is of the type the location claims, which is 6.1's subject and the reason `invokeinterface`, `checkcast` and `aastore` all check again.

## 4. Guarantees

### 4a. What the specification mandates

- **4a.1** Assignability is reflexive on every verification type, and `top` is a supertype of every other type, so the pairs in which the two types are equal and the pairs whose target is `top` are settled by two rules that load nothing and examine nothing {[JVMS §4.10.1.2@SE25]}.
- **4a.2** Four of the fourteen type terms, `top`, `oneWord`, `twoWord` and `reference`, denote abstract unions of other types and exist to shorten the rules, and no `verification_type_info` can name any of the four, so a class file can present ten of the fourteen and no more {[JVMS §4.10.1.2@SE25]} {[JVMS §4.7.4@SE25]}.
- **4a.3** The primitive verification types reach `top` and nothing else. `int` and `float` are subtypes of `oneWord`, `long` and `double` of `twoWord`, and no rule relates any two of the four, so there is no widening between primitive verification types and `int` to `long` is refused {[JVMS §4.10.1.2@SE25]}.
- **4a.4** Any class or interface type may be widened to any interface type. The rule that says so leaves the source unbound, so no property of the source is consulted, and the specification states the consequence in prose: there is no requirement that a reference stored by a variable of an interface type refers to an object that actually implements that interface {[JVMS §4.10.1.2@SE25]}.
- **4a.5** The soundness of 4a.4 rests outside this relation, on the check `invokeinterface` makes on its receiver every time it runs, so an implementation that accepts what 4a.4 requires and omits that check has built an unsound machine out of a conforming verifier {[JVMS §4.10.1.2@SE25]} {[JVMS §6.5@SE25]}.
- **4a.6** A class type widens to another class type when the second names a loaded superclass of the first, and separately when the two carry the same name under two different initiating loaders that resolve to the same loaded class, so a verification type is a name together with a loader and two types with equal names are not necessarily the same type {[JVMS §4.10.1.2@SE25]} {[JVMS §5.3@SE25]}.
- **4a.7** An array type widens to exactly three class types, `java.lang.Object`, `java.lang.Cloneable` and `java.io.Serializable`, and only when the class named is the one the bootstrap loader defines, so an array reaches no other interface however many interfaces an array class implements {[JVMS §4.10.1.2@SE25]}.
- **4a.8** Widening between array types is covariant in the component and is defined by a rule that requires the components themselves to widen, and there is no rule for an array whose component is a primitive, so an array of `int` reaches an array of `int` by reflexivity alone and reaches no other array type {[JVMS §4.10.1.2@SE25]}.
- **4a.9** The three uninitialized types are assignable to whatever `reference` is assignable to, and `reference` reaches only `oneWord` and `top`, and no rule makes any of the three assignable to a class type or an array type, so an unconstructed object satisfies no declared reference type at all {[JVMS §4.10.1.2@SE25]} {[JVMS §2.9.1@SE25]}.
- **4a.10** `null` is a subtype of every class type and every array type by two rules of its own, and nothing other than `null` is assignable to `null`, so the relation has a bottom on the reference side and it is not reachable from anywhere else {[JVMS §4.10.1.2@SE25]}.
- **4a.11** The types `byte`, `char`, `short` and `boolean` have no verification type of their own and are all described by `int`, while the array types whose component is one of the four do have verification types of their own, which is the asymmetry that makes 4a.8's silence about primitive components load bearing rather than an oversight {[JVMS §4.10.1.2@SE25]}.
- **4a.12** Widening between references is not reflexive and applies only between two distinct reference types, so it is not the whole relation and an implementation that treats it as the whole relation has lost every pair 4a.1 settles {[JVMS §4.10.1.2@SE25]}.
- **4a.13** Frame assignability is the pointwise lifting of assignability over the locals and over the operand stack, with an explicit check that the two operand stacks have the same length because the stack grows and shrinks, and with the locals lists required to be the same length by the mapping itself {[JVMS §4.10.1.4@SE25]}.
- **4a.14** A frame's flags are either empty or hold the single element `flagThisUninit`, which is present exactly when some local variable holds `uninitializedThis`, and frame assignability requires the source's flags to be a subset of the target's, so a frame in which `this` is unconstructed is not assignable to one in which it is constructed and the reverse is allowed {[JVMS §4.10.1.4@SE25]}.
- **4a.15** A `long` or a `double` occupies two positions in both a locals array and an operand stack, and the two are written in opposite orders: in locals the type comes first and `top` second, and on the stack `top` comes first and the type second, so the pointwise comparison of 4a.13 is over positions and an implementation that compares values has to have expanded them the same way at both ends {[JVMS §4.10.1.4@SE25]}.
- **4a.16** Answering the relation for two distinct reference types requires both classes loaded, and the rules are split between the reference types and everything else so that a query with an atom on either side can be answered without loading anything, which is stated as a goal of the formulation rather than as an optimisation an implementation may skip {[JVMS §4.10.1.2@SE25]} {[JVMS §4.10.1.1@SE25]}.

### 4b. What HotSpot chose

- **4b.1** The entry point carries a comment calling itself the whole point of the type system, and its first line is the whole of 3.1: if the two types are equal or the target is the bogus type, the answer is yes before anything else is looked at {[HOTSPOT src/hotspot/share/classfile/verificationType.hpp:266@jdk-27+35]} {[HOTSPOT src/hotspot/share/classfile/verificationType.hpp:269@jdk-27+35]}.
- **4b.2** HotSpot's verification types include three query types that no class file can name, and the reference query accepts an uninitialized type as well as a reference, which is what lets one function answer both the questions a frame comparison asks and the questions an instruction's type rule asks {[HOTSPOT src/hotspot/share/classfile/verificationType.hpp:280@jdk-27+35]}.
- **4b.3** The four narrow integral component types are verification types in HotSpot and are not in the file format, and an `int` is assignable to each of them, which is the rule that lets a store into an array of `boolean` be accepted {[HOTSPOT src/hotspot/share/classfile/verificationType.hpp:286@jdk-27+35]}.
- **4b.4** Every refusal in the relation reaches one of two bare returns with no record of which test failed, which is why the message a refused class produces names two types and a location and never names the rule that refused {[HOTSPOT src/hotspot/share/classfile/verificationType.hpp:293@jdk-27+35]} {[HOTSPOT src/hotspot/share/classfile/verificationType.cpp:142@jdk-27+35]}.
- **4b.5** Component assignability is the same function with one difference: the four narrow integral types refuse everything they are not equal to, so an `int` standing in for a `byte` is accepted as a value and refused as an array component {[HOTSPOT src/hotspot/share/classfile/verificationType.hpp:301@jdk-27+35]} {[HOTSPOT src/hotspot/share/classfile/verificationType.hpp:312@jdk-27+35]}.
- **4b.6** `null` is assignable to any reference and nothing is assignable to `null`, and both are decided at the top of the reference case before any name is compared and before anything is loaded {[HOTSPOT src/hotspot/share/classfile/verificationType.cpp:104@jdk-27+35]} {[HOTSPOT src/hotspot/share/classfile/verificationType.cpp:107@jdk-27+35]}.
- **4b.7** Two reference types with equal names are assignable in both directions and no loader is compared anywhere in the function, so a verification type here is a symbol rather than a name together with a loader, and the question two loaders raise is answered by the loader constraint machinery outside this relation {[HOTSPOT src/hotspot/share/classfile/verificationType.cpp:109@jdk-27+35]}.
- **4b.8** Any reference, including any array, is assignable to `java.lang.Object`, decided by comparing the target's symbol against a well known one with neither class loaded {[HOTSPOT src/hotspot/share/classfile/verificationType.cpp:113@jdk-27+35]}.
- **4b.9** The interface rule is one `return` statement with a comment over it saying that interfaces are treated as `java.lang.Object`, and the same statement carries the array carve out, so an array reaches an interface only when that interface is `java.lang.Cloneable` or `java.io.Serializable` {[HOTSPOT src/hotspot/share/classfile/verificationType.cpp:74@jdk-27+35]} {[HOTSPOT src/hotspot/share/classfile/verificationType.cpp:80@jdk-27+35]}.
- **4b.10** The interface shortcut is skipped in one case, when the access being checked is of a protected member and the source type is `java.lang.Object`, which puts a rule about who may see a member inside the function that answers about types {[HOTSPOT src/hotspot/share/classfile/verificationType.cpp:74@jdk-27+35]} {[HOTSPOT src/hotspot/share/classfile/verificationType.cpp:55@jdk-27+35]}.
- **4b.11** The target class is resolved before anything about the pair is decided, so asking whether one type is assignable to another can load a class, can run a user supplied loader, and can fail with a linkage error rather than return an answer {[HOTSPOT src/hotspot/share/classfile/verificationType.cpp:62@jdk-27+35]}.
- **4b.12** The source class is loaded only when the target is neither an interface nor `java.lang.Object`, so the commonest reference to reference question in a real class file resolves one class rather than two {[HOTSPOT src/hotspot/share/classfile/verificationType.cpp:83@jdk-27+35]} {[HOTSPOT src/hotspot/share/classfile/verificationType.cpp:88@jdk-27+35]}.
- **4b.13** The class to class case is a walk of the source's superclass chain and nothing else, so the interfaces the source implements are never consulted, which they could not usefully be, since every interface target was already answered yes {[HOTSPOT src/hotspot/share/classfile/verificationType.cpp:94@jdk-27+35]}.
- **4b.14** While a class data archive is being dumped, an unresolvable pair is recorded as a constraint and the answer is yes without the check being made, so a run that dumps an archive accepts assignments a run that does not would have to resolve, and the check is deferred to the run that uses the archive {[HOTSPOT src/hotspot/share/classfile/verificationType.cpp:119@jdk-27+35]} {[HOTSPOT src/hotspot/share/classfile/verificationType.cpp:127@jdk-27+35]}.
- **4b.15** Two array types are compared by component under the rule of 4b.5, and a component that cannot be parsed out of the signature becomes the bogus type rather than an error, which is why the comparison is guarded against a bogus component on either side: without the guard an unparsable component would be assignable to everything {[HOTSPOT src/hotspot/share/classfile/verificationType.cpp:134@jdk-27+35]} {[HOTSPOT src/hotspot/share/classfile/verificationType.cpp:137@jdk-27+35]} {[HOTSPOT src/hotspot/share/classfile/verificationType.cpp:169@jdk-27+35]}.
- **4b.16** The function that turns a class file tag into a verification type handles six tags and calls an abort for everything else, because the two tags that carry a payload are built by the caller out of a constant pool entry or a bytecode offset {[HOTSPOT src/hotspot/share/classfile/verificationType.cpp:37@jdk-27+35]} {[HOTSPOT src/hotspot/share/classfile/verificationType.cpp:46@jdk-27+35]}.
- **4b.17** Frame assignability refuses on a locals width mismatch and on an operand stack depth mismatch before comparing a single type, and the two produce different error contexts, so those two failures are distinguishable in a message where the type failures under them are not {[HOTSPOT src/hotspot/share/classfile/stackMapFrame.cpp:161@jdk-27+35]} {[HOTSPOT src/hotspot/share/classfile/stackMapFrame.cpp:166@jdk-27+35]}.
- **4b.18** The pointwise comparison returns the index of the first position that refused rather than a set, so a frame with three wrong locals is reported as one wrong local at the lowest index and a person fixing them one at a time gets three rounds of the same message {[HOTSPOT src/hotspot/share/classfile/stackMapFrame.cpp:148@jdk-27+35]}.
- **4b.19** Only as many locals as the target declares are compared, on the stated grounds that anything past them is assignable to the bogus type, so a source frame carrying live types beyond the target's declared locals is not refused for carrying them {[HOTSPOT src/hotspot/share/classfile/stackMapFrame.cpp:171@jdk-27+35]} {[HOTSPOT src/hotspot/share/classfile/stackMapFrame.cpp:176@jdk-27+35]}.
- **4b.20** The subset test on the flags is a bit test rather than a list operation and it runs last, after every type in both arrays has been compared, so a frame that is wrong in its types and its flags is reported for its types {[HOTSPOT src/hotspot/share/classfile/stackMapFrame.cpp:191@jdk-27+35]}.
- **4b.21** Two compile time constants decide which verifier answers and whether its refusal is final, and neither has a flag: the first is 50 and lives in an enum beside three other version boundaries, and the second is 51 and is a macro in the implementation file {[HOTSPOT src/hotspot/share/classfile/verifier.hpp:40@jdk-27+35]} {[HOTSPOT src/hotspot/share/classfile/verifier.cpp:66@jdk-27+35]}.
- **4b.22** A class below major version 50 is never offered to the type checking verifier, so none of 4b.1 to 4b.20 runs for it and the relation this document describes has no bearing on whether it loads {[HOTSPOT src/hotspot/share/classfile/verifier.cpp:219@jdk-27+35]} {[HOTSPOT src/hotspot/share/classfile/verifier.cpp:254@jdk-27+35]}.
- **4b.23** The type checking verifier reports failure by returning a symbol rather than by throwing, which is what makes failover possible at all: at major version 50, with no static archive being dumped, a `VerifyError` or a `ClassFormatError` sends the class to the inference verifier, and the only trace outside the log is that the class loaded {[HOTSPOT src/hotspot/share/classfile/verifier.cpp:227@jdk-27+35]} {[HOTSPOT src/hotspot/share/classfile/verifier.cpp:230@jdk-27+35]} {[HOTSPOT src/hotspot/share/classfile/verifier.cpp:233@jdk-27+35]} {[HOTSPOT src/hotspot/share/classfile/verifier.cpp:245@jdk-27+35]}.
- **4b.24** Whether verification runs at all is decided per class from the defining loader by two flags, so in a default configuration the classes of the runtime image are loaded without this relation being consulted about them once {[HOTSPOT src/hotspot/share/classfile/verifier.cpp:117@jdk-27+35]}.

### 4c. Ordering obligations

- **4c.1** The class file major version is known before the relation is consulted for a class, because below one version it is never consulted and at one version a refusal from it is not final, and neither fact can be recovered afterwards {[HOTSPOT src/hotspot/share/classfile/verifier.cpp:219@jdk-27+35]}.
- **4c.2** Both classes are loaded before a pair of distinct reference types that name, `null` and `java.lang.Object` have not already settled can be answered, so the relation cannot be evaluated in an environment that has no loading and cannot be tabulated ahead of the classes it is about {[JVMS §4.10.1.2@SE25]}.
- **4c.3** The target is examined before the source, because whether the target is an interface decides whether the source is loaded at all, and an implementation that resolves the source first has loaded a class it does not need and may throw a linkage error where a conforming machine returns yes {[HOTSPOT src/hotspot/share/classfile/verificationType.cpp:69@jdk-27+35]}.
- **4c.4** The shapes of two frames are compared before any of their types, so a frame that is both the wrong width and holding a wrong type is reported for its width and the type is never reached {[HOTSPOT src/hotspot/share/classfile/stackMapFrame.cpp:161@jdk-27+35]}.
- **4c.5** The flags are compared after every type, so the two failures cannot both be reported and the type one wins, which is the opposite order from 4c.4 and is worth writing down because an implementation that checks the cheap thing first gets both orders wrong {[HOTSPOT src/hotspot/share/classfile/stackMapFrame.cpp:191@jdk-27+35]}.
- **4c.6** The answer for a pair may be produced in one run and checked in another, so the obligation in 4c.2 holds within a single run and not across the two runs an archive spans, and an implementation that caches answers has to know which of the two it is in {[HOTSPOT src/hotspot/share/classfile/verificationType.cpp:119@jdk-27+35]}.

## 5. Observation

Every item below is a procedure rather than a result. The tool named in it is the one that answers the question with the least machinery, and where two tools disagree that disagreement is itself the observation.

Six tools carry this section. `probes/verify/run.py` builds one class file per ordered pair of sixteen verification types, hands each to the pinned JVM, and reports which loaded, which is the only way to obtain this relation as an answer rather than as a reading of somebody's rules. `java.lang.classfile`, on the pinned JDK, writes a stack map frame no compiler would emit, which is what makes a pair askable at all. `javap -v` prints the frames as the platform's own reader understands them, with offsets and pool entries resolved. `java -Xlog:verification=info` names the verifier that ran and says when a class failed over, which is the one question none of the others can answer. `java -Xlog:class+load=info` says which classes loading the relation caused, which is how an ordering obligation is watched from outside. And `probes/classfile-fuzz` breaks one valid class file and records where the machine stopped and in what words.

- **5.1** 4a.1, 4b.1: read the diagonal and the `top` column out of the grid, with `probes/verify/run.py`. All sixteen types are assignable to themselves and all sixteen are assignable to `top`, which is thirty one distinct cells and the largest block of the grid that needs no class loaded.
- **5.2** 4a.2, 4b.16: attempt to write a `verification_type_info` naming `oneWord`, `twoWord`, `reference` or the bare `uninitialized`, with `java.lang.classfile` and `javap -v`. There is no way to express any of the four, because the tags stop at the ten forms the format defines, which is why the grid measures sixteen instantiations of ten terms rather than fourteen.
- **5.3** 4a.3, 4b.3, 4b.5: read the four primitive rows and the four primitive columns out of the grid, then store an `int` into an array of `boolean` and separately declare an array of `byte` where an array of `int` is expected, with `probes/verify/run.py` and `java.lang.classfile`. No primitive is assignable to any other primitive. The store into the array of `boolean` is accepted and the array of `byte` standing in for an array of `int` is refused, which is the same `int` accepted as a value and refused as a component.
- **5.4** 4a.4, 4a.5, 4b.9: build a class that stores a `java.lang.String` into a local its stack map frame declares as `java.lang.Runnable`, add an `invokeinterface` of `run` on that local, run it, then build the control with `java.lang.Thread` where the interface was, with `probes/verify/run.py`. The class verifies, the call verifies, running it throws `IncompatibleClassChangeError`, and the control is refused at verification, so one bit in the target's access flags decides whether the hierarchy is consulted.
- **5.5** 4a.6, 4b.7: define the same class bytes under two class loaders neither of which delegates to the other, and present a frame declaring the type from the first where the type from the second is expected, with `java.lang.classfile` and `java -Xlog:class+load=info`. The specification's rules distinguish the two types and the pinned machine's comparison is of names, so this is the pair on which the two are describing different objects and the observation is which one the machine agrees with.
- **5.6** 4a.7, 4b.8, 4b.13: read the three array rows out of the grid against the `Object`, `Cloneable`, `Serializable` and `Runnable` columns, with `probes/verify/run.py`. Every array reaches the first three and none reaches `Runnable`, which is where all nine of the grid's non transitive triples come from, since each of them goes through a type an array can reach to an interface it cannot.
- **5.7** 4a.8, 4b.15: read the array to array cells out of the grid, then hand the verifier a frame whose type is an array with a component signature that is not a type, with `probes/verify/run.py` and `java.lang.classfile`. An array of `String` is assignable to an array of `Object` and the reverse is refused, an array of `int` reaches no array but itself, and the unparsable component is refused rather than accepted as a wildcard.
- **5.8** 4a.9: read the two uninitialized rows out of the grid, with `probes/verify/run.py`. Each reaches `top` and itself and nothing else, and in particular neither reaches `java.lang.Object`, which is the result most likely to be got wrong by an implementation that files the uninitialized types under references.
- **5.9** 4a.10, 4b.6: read the `null` row and the `null` column out of the grid, with `probes/verify/run.py`. `null` is assignable to all eight reference types measured and to `top` and to itself, and nothing but `null` is assignable to `null`, which is ten cells in one row against two in the column.
- **5.10** 4a.11: declare a local holding a `boolean` as `int` in a frame, then declare an array of `boolean` as an array of `int`, with `java.lang.classfile` and `javap -v`. The first is accepted, because there is no verification type for `boolean` to be refused as, and the second is refused, because there is one for the array.
- **5.11** 4a.12, 4b.4: collect the message from every refused cell of the grid and count the distinct shapes after the type names are replaced, with `probes/verify/run.py`. All 191 refusals come back in one shape, which names two types and a location and no rule, because there is no rule object to name.
- **5.12** 4a.13, 4b.17, 4c.4: present a frame whose locals array is one location wider than the target's, then one whose operand stack is one deeper, then one that is both the wrong width and holding a wrong type, with `java.lang.classfile` and `probes/classfile-fuzz`. The first two are refused with messages about sizes rather than about types, and the third is refused for its size, so the type never enters the message.
- **5.13** 4a.14, 4b.20, 4c.5: build a constructor with a merge point reached once before the chained constructor call and once after, and separately a frame that is wrong in its flags and in one of its types, with `java.lang.classfile` and `javap -v`. Merging the unconstructed state into the constructed one is refused and the reverse is accepted, and the frame that is wrong in both is reported for its type.
- **5.14** 4a.15: print a method holding a `long` in a local and a `double` on the stack at a branch target, with `javap -v`. The locals array shows the type and then `top` and the operand stack shows `top` and then the type, and a reader who assumes one order for both has an off by one in every frame with a category 2 value in it.
- **5.15** 4a.16, 4b.11, 4b.12, 4c.2, 4c.3: ask the relation about a pair of class types neither of which is loaded, once with an interface as the target and once with a class, and watch what loads, with `java.lang.classfile` and `java -Xlog:class+load=info`. The interface case loads the target and never the source. The class case loads both. A pair with an atom on either side loads neither, which is what the split in the rules is for.
- **5.16** 4b.2: build a constructor that reads `this` out of local 0 before chaining, with `java.lang.classfile` and `javap -v`. It verifies, which shows the reference query accepting an uninitialized type, and it is the only way from outside the machine to see a type that has no tag in the file format do any work.
- **5.17** 4b.10: build a class outside `java.lang` whose frame declares a receiver as an interface and which invokes a protected member of `java.lang.Object` on it, with `java.lang.classfile` and `javap -v`. This is the one pair for which the interface shortcut does not fire, so the answer comes from the hierarchy and the class is refused, and an implementation that answers yes here has let a protected member be reached through a type that proves nothing.
- **5.18** 4b.14, 4c.6: verify one class in an ordinary run and again in a run that dumps a static class data archive, with `java -Xshare:dump` and `java -Xlog:verification=info`. A pair the ordinary run resolves is recorded as a constraint in the dumping run and answered yes without resolution, and the log of the run that later uses the archive is where the deferred check is made.
- **5.19** 4b.18, 4b.19: present a frame with three wrong locals at three different indices, then one carrying live types at positions past the target's declared locals, with `java.lang.classfile` and `probes/classfile-fuzz`. The first is reported as one wrong local at the lowest of the three indices, so fixing them one at a time takes three rounds. The second is accepted, because everything past the target's declared locals is assignable to `top`.
- **5.20** 4b.21, 4b.22, 4b.23, 4c.1: write the same wrong frame at class file major versions 49, 50, 51, 52 and 71, each with a correct frame control, and load all ten, with `probes/verify/run.py` and `java -Xlog:verification=info`. At 49 and 50 the wrong frame loads and at 51 and above it does not, every control loads, and at 50 the log says the class failed over to the old verifier while with logging off there is nothing to see at all. This is the item BP-STACKMAP's own 5.19 asked for and it has been performed.
- **5.21** 4b.24: load a class from the boot loader and the same class from an application loader in a default configuration, with `java -Xlog:verification=info`. The first is not verified and the second is, so a table of this relation built by watching a default run of a program is a table of the classes the program brought and not of the several thousand the image did.

## 6. Edge cases

### 6.1 Malformed input

The operation in section 3 takes two verification types and a context, and the interesting malformations are not in the types. A frame carrying a type the format cannot express does not reach this operation, because BP-STACKMAP refused it while decoding, and a frame whose offset is wrong does not reach it either. What reaches it is a well formed pair whose answer cannot be computed, and there are three kinds.

The first is a type whose name is not a type. An array's component is obtained by parsing the signature, and a signature that does not parse yields the bogus type rather than an error {[HOTSPOT src/hotspot/share/classfile/verificationType.cpp:169@jdk-27+35]}. Bogus is `top`, and everything is assignable to `top`, so an implementation that compares components without checking for it has made an unparsable array signature assignable to every array type in the machine. HotSpot guards against exactly that, on both sides, before comparing {[HOTSPOT src/hotspot/share/classfile/verificationType.cpp:137@jdk-27+35]}. This is the one place in this document where a missing check would be a hole rather than a strictness difference, and it is worth writing a test for before anything else in section 8.

The second is a class that cannot be loaded. Answering a reference to reference pair resolves the target, and resolution can fail, so `assignable` has a third outcome that is neither yes nor no. An implementation that returns no on a failed resolution converts a `NoClassDefFoundError` into a `VerifyError` and reports a type error for a class that was never there, which is the commonest confusing failure a person meets when a class path is wrong. The pinned machine propagates the linkage error {[HOTSPOT src/hotspot/share/classfile/verificationType.cpp:62@jdk-27+35]}.

The third is not a malformation and is the reason this blueprint exists. A frame that declares a local as an interface, when the value in it is of a class that does not implement that interface, is well formed input with a wrong claim in it, and 4a.4 requires it to be accepted. The measurement in section 2 finds that the pinned JVM accepts it, that the class loads, that a call through it verifies, and that the failure arrives at run time as an `IncompatibleClassChangeError`. An implementation reading this document is required not to catch it. What it is required to do instead is make the run time check, and a machine that gets both halves of that wrong is a machine on which a wrong frame is never noticed by anything.

One more shape is worth naming because it looks malformed and is not. A frame whose locals array carries live types at positions past the target's declared locals is accepted, because everything past the target is assignable to `top` {[HOTSPOT src/hotspot/share/classfile/stackMapFrame.cpp:171@jdk-27+35]}. A frame whose locals array is a different width from the target's is refused, and the two are not the same condition: the first is about how much of the array carries meaning and the second is about how long the array is.

### 6.2 Resource exhaustion

This operation has no bound of its own and the reason is worth being precise about. Neither argument is a container, so there is no count to overflow and no length to allocate from. What is unbounded is the work: 3.10 walks the source's superclass chain, whose length is bounded by the depth of the hierarchy and by nothing in either type, and 3.11 recurses on components, whose depth is bounded by the number of leading array characters in a signature and therefore by the length of a constant pool entry.

The real cost is class loading. A pair of distinct reference types that 3.7, 3.8 and 3.9 do not settle loads two classes, and loading a class runs a loader, which may load more, and each of those is verified, and verifying them asks this operation again. So a single call can start an unbounded amount of work on the calling thread, and the recursion is not bounded by anything in this document. The specification's own note about the shape of the rules is about this: the rules are split so that a query with an atom on either side never starts climbing a hierarchy {[JVMS §4.10.1.2@SE25]}.

Two properties of the relation keep the common case cheap and both are worth knowing before optimising it. A target that is an interface is answered without loading the source at all {[HOTSPOT src/hotspot/share/classfile/verificationType.cpp:74@jdk-27+35]}, and a target that is `java.lang.Object` is answered by a symbol comparison with neither class loaded {[HOTSPOT src/hotspot/share/classfile/verificationType.cpp:113@jdk-27+35]}. Together those two cover most reference to reference questions a real class file asks, which is why verification does not load the transitive closure of everything a method mentions.

Measurement puts the whole of it in proportion. Across `java.base` on two platforms there are 124,849 methods with code holding 3,902,996 instructions, of which 52,507 are `invokeinterface`. Every one of those is a site where the relation was asked about an interface target and answered yes without loading the source, and every one carries a check made again each time it runs. An implementation that caches answers to make verification cheaper is caching a relation whose commonest answer was already free, and is taking on the invalidation problem 6.3 describes for nothing.

### 6.3 The concurrent case

The relation itself holds no state and needs no lock, and stating that is more useful than it sounds, because everything around it is concurrent. Verification of one class happens on the thread that links it, under the lock that makes linking happen once, so the two frames being compared are private to that thread. Nothing in section 4 is a memory ordering obligation.

The concurrency arrives through class loading. Answering a pair may resolve a class, resolution may run a user supplied loader, and that loader runs on the verifying thread while it holds the link state of the class being verified. A loader that blocks on another thread that is itself loading the class being verified deadlocks, and the deadlock is inside a type check rather than anywhere a person would look for it. An implementation is not free to move that loading off the thread, because the linkage error it may raise has to arrive at the caller.

The second concurrency is that the answer is not stable across runs. A pair answered yes while a class data archive was being dumped was answered without the check being made, and the check is deferred to the run that uses the archive {[HOTSPOT src/hotspot/share/classfile/verificationType.cpp:119@jdk-27+35]}. So the same two types can produce an accepted class in one process and a refused one in another, with the same class files on disk, and neither process is wrong. An implementation that reports which classes it verified reports different sets on two runs of the same program for this reason and for the one in section 7.

The third is redefinition. A class may be redefined while it is running, and a redefinition supplies new code with new frames, so every answer this relation gave about the old body describes nothing in the new one. An implementation that caches assignability answers keyed on a pair of names has a cache whose entries are still true, since the relation is about types and not about methods. One that caches frame comparisons keyed on a method has a cache that is wrong the moment the method changes, and the failure it produces is a class that verified against frames it no longer has.

## 7. Configuration

Nothing in section 4a is configurable, and the switches on 4b divide into two kinds that a reader has to keep apart. One kind decides whether this relation is consulted about a class at all, and the other decides whether an answer it gives is the final word. Neither kind makes the relation stricter or looser, so a table of the relation built by observing a machine in some configuration is either the same table or an empty one.

**Whether the relation is consulted.** `BytecodeVerificationLocal` and `BytecodeVerificationRemote` decide, per class and from the defining loader, whether the class is verified {[HOTSPOT src/hotspot/share/classfile/verifier.cpp:117@jdk-27+35]}. The defaults on the pinned build are false for the boot loader and true for every other loader, so the classes of the runtime image are loaded without this relation being asked about them once. Both flags are diagnostic on the pinned build and need `-XX:+UnlockDiagnosticVMOptions` before either can be set, which is a change from older builds where they were product flags and every guide on the internet still writes them without it.

**The switch that no longer exists.** `-Xverify:none` is rejected on the pinned build. It does not warn and it does not ignore the option: the launcher prints `Unrecognized verification option` and the machine does not start. `-Xverify:all` and `-Xverify:remote` are both still accepted and both correspond to settings of the two flags above. Anything written before this change that turns verification off by that route now fails to launch rather than running unverified, which is the better failure and is worth knowing before reading an old benchmark harness.

**Which verifier answers, which is not configurable.** The two class file versions that decide it, 50 for the type checking verifier and 51 for the end of failover, are compile time constants and there is no flag for either {[HOTSPOT src/hotspot/share/classfile/verifier.hpp:40@jdk-27+35]} {[HOTSPOT src/hotspot/share/classfile/verifier.cpp:66@jdk-27+35]}. A reader who wants a refusal by this relation to be final at every version cannot ask for that, and a reader who wants failover at version 51 cannot ask for that either. The answer is a property of the file, which is why 8.2.19 asks an implementation to state its answer rather than to have a particular one.

**The one thing that suppresses failover.** Dumping a classic or final static class data archive turns failover off, on the grounds that a class verified by the old verifier is excluded from the archive rather than tolerated in it {[HOTSPOT src/hotspot/share/classfile/verifier.cpp:227@jdk-27+35]}. So a class file at major version 50 with a wrong frame loads in an ordinary run and does not load in a dumping run, and that is the only configuration in this document that changes an accept into a refuse.

**What defers an answer instead of changing it.** While an archive is being dumped, a pair whose classes cannot be resolved is recorded as a constraint and answered yes, and the check is made in the run that uses the archive {[HOTSPOT src/hotspot/share/classfile/verificationType.cpp:119@jdk-27+35]}. This is the only setting under which `assignable` returns an answer it has not established, and an implementation with no archive has no equivalent and needs none.

**What changes what is printed and nothing else.** `-Xlog:verification=info` names the verifier that ran and says when a class failed over {[HOTSPOT src/hotspot/share/classfile/verifier.cpp:233@jdk-27+35]}, which is what makes 5.20 and 5.21 performable and changes nothing about which verifier runs. `-Xlog:class+load=info` is what makes 5.15 performable, and `javap -v` resolves a frame's pool indices for the reader and invents nothing.

**Which versions this runtime reads.** The pinned JDK reads class file major versions 45 through 71, so both boundaries in 4b.21 are reachable on it and so is the single version at which a refusal is not final. The pinned specification edition describes versions up to 69. Both numbers are in `docs/pin.json`. The gap matters here only if a future version adds a verification type or changes the relation, and neither has happened since the type checking verifier arrived, which is why 4a is a reading of one section that has been stable since class file version 50 arrived twenty years ago.

## 8. Conformance

### 8.1 What conformance means here

An implementation conforms to this blueprint if, for every pair of verification types it is asked about in a given class hierarchy, it reaches the same yes or no as section 4a requires, and if for every pair of frames it reaches the same decision that the pointwise lifting in 4a.13 and 4a.14 requires. Nothing is said about how a verification type is represented, how much a query costs, what any message says, which instruction asked, or what the implementation does with the answer, which is BP-BYTECODE's subject and not this one's.

Section 4b is not part of that obligation. Those clauses record what HotSpot at the pinned build does, and an implementation may differ from every one of them and conform. Three of them are worth naming as places where differing is the sensible choice: 4b.4, which produces every refusal through one bare return and so cannot say which rule refused, 4b.7, which compares names where the specification compares a name together with a loader, and 4b.18, which reports only the lowest wrong position and makes fixing three wrong locals take three rounds. An implementation that matches HotSpot on those has copied a defect and can say so.

Two clauses are different in kind, and an implementation has to make a decision about each rather than merely differ. 4b.23 says that at one class file version a refusal by this relation is not the end of the load, because the class is offered to a second verifier that does not use this relation at all. An implementation with one verifier refuses where the pinned build accepts, and it conforms, because 4a requires the refusal. What it may not do is leave this unstated, since a conformance run of wrong frames against a machine that has failover will record passes it never exercised, and 8.2.19 exists to make that visible rather than to require either answer. 4b.14 is the other: an implementation may defer an answer to a later run, and one that does has to say so, because a suite that measures resolution behaviour on it is measuring the deferral.

Four consequences are worth stating because they are the ones people get wrong. First, matching a message is never conformance, and 4b.4 is the clause that makes that unavoidable here: there is no message that names a rule, so there is nothing to match against. Second, an implementation that is stricter than 4a requires does not conform, and 4a.4 is the clause this catches: refusing to let a class type stand where an interface is expected is refusing a legal file, and it is the single most natural thing to build, because it is what the source language does and what a reader of "the verifier proves type safety" expects. Third, accepting what 4a.4 requires while omitting the run time check of 4a.5 is not two independent failures but one, and it is the failure that turns a conforming verifier into an unsound machine. Fourth, a linkage error is permitted wherever a class is loaded, so no item below expects a specific error for a pair naming a class that is not there.

The capstone harness reports against 8.2 and against nothing else. An item is passed when a test exists that would fail if the behaviour changed, skipped when the item names a case the harness cannot construct, and failed otherwise. There is no fourth state, and in particular there is no state for an item nobody has looked at.

### 8.2 The checklist

- **8.2.1** 4a.1, 4b.1: answers yes for every type paired with itself and for every type paired with `top`, and reaches both answers without loading any class, which is checked by asking about two class types that do not exist.
- **8.2.2** 4a.2, 4b.16: accepts every verification type the class file format can express and provides no way for a caller reading a class file to name `top`, `oneWord`, `twoWord`, `reference` or a bare `uninitialized`, so the abstract unions cannot enter through a file.
- **8.2.3** 4a.3, 4b.3, 4b.5: refuses every ordered pair of two distinct primitive verification types, in both directions, including `int` to `long` and `float` to `double`, and states whether it has narrow integral types of its own and if so that an `int` satisfies one as a value and does not satisfy one as an array component.
- **8.2.4** 4a.4, 4a.5, 4b.9: accepts a frame declaring a local as an interface the value's class does not implement, accepts an `invokeinterface` through that local, refuses the same frame when the declared type is a class rather than an interface, and throws `IncompatibleClassChangeError` when the call runs rather than allowing the call to dispatch.
- **8.2.5** 4a.6, 4b.7: states whether a verification type carries a loader, and if it does, distinguishes two class types with the same name under two loaders that resolve to different classes, and if it does not, names where the obligation that they be the same class is discharged instead.
- **8.2.6** 4a.7, 4b.8, 4b.13: accepts every array type where `java.lang.Object`, `java.lang.Cloneable` or `java.io.Serializable` is expected, refuses every array type where any other interface is expected including one that an array class does implement, and never consults the source's interfaces when the target is a class.
- **8.2.7** 4a.8, 4b.15: accepts an array of a subclass where an array of a superclass is expected, refuses the reverse, refuses an array of a primitive where any other array is expected, and refuses rather than accepts an array whose component signature does not parse.
- **8.2.8** 4a.9: refuses `uninitializedThis` and `uninitialized(Offset)` everywhere except against `top` and against themselves, and in particular refuses both against `java.lang.Object`, which is checked by presenting a frame that declares an unconstructed local as `java.lang.Object`.
- **8.2.9** 4a.10, 4b.6: accepts `null` where any class type or any array type is expected, refuses everything but `null` where `null` is expected, and reaches both without loading the class named on the other side.
- **8.2.10** 4a.11: accepts a `boolean`, a `byte`, a `short` and a `char` where `int` is expected, since none of the four has a verification type, and refuses an array of any of the four where an array of `int` is expected, since each of those does.
- **8.2.11** 4a.12, 4b.4: reaches the same answer for a pair of identical reference types as for a pair of identical atoms, without entering the widening rules, and either names the rule that refused in its message or states that it does not.
- **8.2.12** 4a.13, 4b.17, 4c.4: refuses two frames whose locals arrays differ in width and two whose operand stacks differ in depth, before comparing any type in either, so a frame that is both the wrong width and holding a wrong type is refused for its width.
- **8.2.13** 4a.14, 4b.20, 4c.5: refuses a frame in which `this` is unconstructed where one in which it is constructed is expected, accepts the reverse, and compares the flags after every type, so a frame wrong in both is refused for its type.
- **8.2.14** 4a.15: expands a `long` and a `double` into two positions in both a locals array and an operand stack, with the type first in locals and `top` first on the stack, and compares positions rather than values so that a frame legal by value count and wrong by position is refused.
- **8.2.15** 4a.16, 4b.11, 4b.12, 4c.2, 4c.3: answers a pair with an atom on either side without loading anything, loads only the target when the target is an interface, loads both when both are class types, and propagates the failure to load rather than converting it into a refusal.
- **8.2.16** 4b.2: accepts a read of a local holding `uninitializedThis` where a reference is expected by an instruction's type rule, or states that it has no query types and answers those questions another way.
- **8.2.17** 4b.10: states what it does when the access being checked is of a protected member of `java.lang.Object` through a receiver declared as an interface, since this is the one pair for which 4a.4 does not decide the answer on the pinned build.
- **8.2.18** 4b.14, 4c.6: states whether it ever answers a pair without establishing it, and if it does, names the mechanism that makes the check later and what happens when that later check fails.
- **8.2.19** 4b.21, 4b.22, 4b.23, 4c.1: states whether a refusal by this relation ends the load, and if it does not, names the exact set of class file versions for which it does not, so that a conformance run of wrong frames can be read as a set of refusals rather than as a set of passes.
- **8.2.20** 4b.18, 4b.19: reports a frame with three wrong locals in a way whose behaviour is stated, either one position at a time or all three, and accepts a source frame carrying live types at positions past the target's declared locals.
- **8.2.21** 4b.24: either consults this relation for every class it loads or names the configuration in which it does not, so that a measurement of how often the relation is asked can be read against the set of classes it was asked about.

## 9. Provenance

Section 2 is generated from [the verifier type system page](../../docs/generated/verify.md), which `tools/gen_verify.py` builds by joining four sources: the pinned specification edition for the relation as Prolog, `verificationType.cpp` for the same relation as C++, `verifier.hpp` and `verifier.cpp` for the two class file versions that decide which verifier answers, and a grid of 256 class files handed to the pinned JVM. It is not written here and editing it here has no effect. The generator stops rather than writes when the sources disagree, and `tools/test_gen_verify.py` holds ninety nine tests, twenty of them one for each way the four sources can drift.

Every clause in 4a quotes JVMS SE25 and every clause in 4b names a file and a line in `jdk-27+35`. `tools/refcheck.py` resolves both against `docs/citations.json` and fails the build when a line has moved, so a clause that has drifted off its evidence is a broken build rather than a stale sentence.

The measurement is one class file per ordered pair of sixteen verification types, 256 in all, built through `java.lang.classfile` and loaded. 65 loaded, 191 were refused with `VerifyError`, and no cell failed for any other reason, which the probe requires: a run in which any cell fails some third way writes no results file. Two environments measured the same 256 cells and agreed on every one. Out of that grid come the three structural findings: the relation is reflexive on all sixteen types, it has nine non transitive triples, and it has six mutually assignable pairs that close into one group holding `java.lang.Object` and three interfaces. That group is the finding this blueprint is arranged around and it is what 4a.4 says in a rule head.

A 256 cell answer from a machine needs its own defence, because nothing in a grid would notice if the harness built the same class 256 times. Three things answer that. Twelve of the cells can be settled on paper from 4.10.1.2 by following the clauses, and `probes/verify/run.py` writes no results file when a measured answer differs from a worked one. The three structural counts are produced twice, once in Java over the map the grid built as it went and once in Python over the cells parsed back out of the results file, by two readers that share no code, and the generator refuses to write a page when they disagree. And the interface hole carries a control, the same class with a class type where the interface was, whose refusal is asserted, so a run in which everything verifies writes nothing. The write up is [the probe's page](../../docs/probes/verify.md).

Nine of the twenty one items in section 5 have been performed and the rest have not. 5.1, 5.4, 5.6, 5.8, 5.9, 5.11 and 5.20 were performed in full by `probes/verify/run.py`, and 5.3 and 5.7 were performed for the cells the grid holds and not for the array component halves. 5.20 is the one worth naming, because it is the item BP-STACKMAP's own 5.19 asked for and left undone: the same wrong frame at five class file versions, each with a correct frame control, cross checked against the two HotSpot constants by a predictor that stops the build when a measured row disagrees, so that table is two independent sources agreeing rather than five numbers from one run.

Five things in 4b were read out of the source and have not been demonstrated by running anything. 4b.10, the one case where the interface rule does not fire, which is 5.17 and is the clause here most worth demonstrating, since an implementation that gets it wrong lets a protected member be reached through a type that proves nothing. 4b.12, that the source class is loaded only when the target is neither an interface nor `java.lang.Object`, which is 5.15 and is a claim about what does not happen. 4b.14, the deferred answer under archive dumping, which is 5.18. 4b.18 and 4b.19, the two properties of the pointwise walk, which are 5.19. And 4b.2, the query types, which have no tag in the class file format and can only be watched doing work indirectly.

Four questions this blueprint raises are open. The largest is the disagreement between 4a.6 and 4b.7: the specification's verification type is a name together with a loader and the pinned machine's is a symbol, the grid was measured under one loader and says nothing about it, and 5.5 is the measurement that would settle which of the two the machine agrees with. 4a.5 is stated as an obligation on an implementation and the specification establishes it by describing what `invokeinterface` does rather than by requiring anything of a verifier, so it is the clause in 4a most likely to be wrong about where the obligation lives. The pinned JDK reads class file version 71 and the pinned specification edition stops at 69, so a verification type added between them would make 4a.2 and the sixteen types of section 2 wrong and nothing here would notice. And one of the twenty two Prolog clauses of 4.10.1.2 does not parse, which the generator reports as a count rather than asserting, so a future edition that fixes it produces a page that stops mentioning it rather than a build that fails.

The reviews field in the front matter is null. Nothing in this blueprint has been read by anybody with production experience of a bytecode verifier, and until it has, the conformance list is one person's reading of one section of the specification against one implementation and not a standard.
