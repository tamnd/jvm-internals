## 1. Scope

This blueprint specifies the class file as an input: a finite sequence of bytes handed to a Java Virtual Machine, and everything the machine does to it between receiving it and having a class it can link. It covers the structure those bytes must have, the checks performed while reading them, which error each failed check produces, and the order the checks happen in. An implementation built from this document can take a byte array and either produce an internal class or refuse it with the error a conforming machine would produce.

It covers three things a reader is likely to expect somewhere else. The first is the split between what the specification requires of every implementation and what HotSpot decided on its own, which is section 4 and is the reason the document exists. The second is the error taxonomy: `ClassFormatError`, `UnsupportedClassVersionError` and `NoClassDefFoundError` are all outcomes of parsing, and which one a given broken file produces is a specified fact for some breakages and an implementation choice for others. The third is the boundary between format checking and verification, which the specification draws in one place and HotSpot draws in another, and where those two lines differ is stated here rather than left for somebody to discover.

It deliberately excludes five things. The meaning of each instruction in the code array belongs to BP-BYTECODE. The individual constant pool entry kinds, their tags and the constraints between them belong to BP-CONSTPOOL. The `StackMapTable` attribute's frames and their inference belong to BP-STACKMAP. The type checking of a method body belongs to BP-VERIFY. Everything that happens after a class exists, meaning loading, linking, preparation, resolution and initialization, belongs to BP-LOAD.

Two further exclusions are worth naming because they look as though they belong here. What a compiler chooses to emit is out of scope: this specifies what a machine must accept, and the set of files a compiler happens to produce is a much smaller set. And the on disk container is out of scope as well, so nothing here says anything about jar files, module images or the class path. The input is a byte sequence and where it came from changes nothing about the answer, with the single exception recorded in 4b.10 and 4b.11, where the route into the machine decides whether the bytes are copied first.

The pinned JDK's class file API models every one of the 30 attributes the specification defines. Everything else it hands back as an `UnknownAttribute`, which is the correct behaviour rather than a gap: an attribute a reader does not recognise has to survive a round trip untouched, and a library that parsed one it did not understand could not promise that.

It also models six more that the specification does not define, `CharacterRangeTable`, `CompilationID`, `ModuleHashes`, `ModuleResolution`, `ModuleTarget`, `SourceID`. Those are the extension mechanism being used rather than described: anybody may define an attribute, the JDK's own tools have, and a reader who meets one in a class file has met somebody else's convention rather than a corrupt file.

Six of the 36 may appear more than once on the same element: `CharacterRangeTable`, `Deprecated`, `LineNumberTable`, `LocalVariableTable`, `LocalVariableTypeTable`, `Synthetic`. Every other one is at most one per element, so a parser that keeps the last of each is right about the rest of the format and wrong about these.

Each one also says what happens to it when a class file is rewritten, which is the question a reader hits the moment they stop reading class files and start producing them. 25 of them hold constant pool references, which a transform has to remap. Five of them hold offsets into a method body, which a transform has to move. Four of them can be copied byte for byte. Two of them cannot be copied safely, so a transform that changes the class drops them.

The unstable ones are `RuntimeInvisibleTypeAnnotations`, `RuntimeVisibleTypeAnnotations`. They carry both constant pool references and offsets into code, so there is no rule that keeps them correct across an edit, and the library says so rather than preserving them and hoping.

Nothing in the scanned code came back as an unknown attribute, so every attribute the JDK's own compiler emitted into its own runtime image is one the JDK's own class file library models.

### 2.4 The access flags

There are four separate flag tables in the specification and they assign different meanings to the same bits, which is the single most common way a hand written class file parser goes wrong. 0x0020 is `ACC_SUPER` on a class and `ACC_SYNCHRONIZED` on a method. 0x0040 is `ACC_VOLATILE` on a field and `ACC_BRIDGE` on a method. 0x0080 is `ACC_TRANSIENT` on a field and `ACC_VARARGS` on a method. ## 3. Operations

There is one public operation and it has one signature. Everything else in this section is a step inside it, named so that section 4 can say when each step happens and what it may assume about the steps before it.

**derive(bytes, name, loader) returns a class, or throws.** `bytes` is a finite sequence with a known length. `name` is the binary name the caller expects, or absent. `loader` identifies the defining loader, and it is an input rather than a decoration because it selects how much checking is done. The result is an internal class, or one of `ClassFormatError`, `UnsupportedClassVersionError`, `NoClassDefFoundError`, `OutOfMemoryError` or a `LinkageError` raised by the steps that precede parsing. `derive` never returns a partially built class, and an implementation that keeps one after a failure has to make it unreachable, because a class that failed to parse is not a class that failed to link.

The steps run in the order given. Each one may assume every earlier step completed and may assume nothing about a later one.

**3.1 read the header.** Consume four bytes of magic, then two of minor version, then two of major version. Fails with `ClassFormatError` if the magic is wrong, and with `UnsupportedClassVersionError` if the version is outside the range the implementation supports. Produces the version, which every later step may need, because the format is versioned and a structure that is legal at one version is not legal at another.

**3.2 read the constant pool.** Consume the count, then that many entries minus one, each tagged by its first byte. Produces a table indexed from 1 whose entries are not yet cross checked. Fails with `ClassFormatError` on a tag the version does not allow, on an entry that runs off the end, or on a count of zero. The individual entry kinds are BP-CONSTPOOL's, and this step's obligation is to consume exactly the bytes each kind occupies and to leave a table the next steps can index.

**3.3 check the pool.** Resolve every index an entry holds against the table, and check that what it points at is of the kind the entry requires. Produces nothing and consumes nothing. It is a separate step from 3.2 because an entry may refer to an entry that comes after it, so no single pass over the bytes can do both.

**3.4 read the class's own items.** Consume access flags, `this_class`, `super_class`, the interface count and that many interface indices. Fails with `ClassFormatError` on an index that is out of range or points at the wrong kind, and with `NoClassDefFoundError` if `this_class` names something other than the expected `name`, or if the access flags say this is a module rather than a class {[JVMS §5.3.5@SE25]}. This is the step where the error class stops being about bytes and starts being about identity.

**3.5 read the fields, then the methods.** Each is a count followed by that many structures, and each structure is flags, a name index, a descriptor index and its own attribute table. Fails with `ClassFormatError` on a duplicate name and descriptor pair, on flags that contradict each other, or on a descriptor that is not well formed. A method's `Code` attribute is read here, which means `max_stack`, `max_locals` and the code length are read here, and so are the constraints stated about them.

**3.6 read the class attributes.** The same shape as 3.5's attribute tables, attached to the class rather than to a member. An attribute whose name the implementation does not recognise is skipped by its declared length and must not be an error.

**3.7 finish.** Check that the stream is exhausted. Fails with `ClassFormatError` if any byte remains, which is the check that makes the class file a description of the whole input rather than of a prefix of it.

Steps 3.1 to 3.7 are format checking as the specification uses the term {[JVMS §4.8@SE25]}. They do not look at the code array beyond its length, they do not resolve any name to another class, and they do not type check anything. An implementation that passes them has a class file it can hold, not a class it can run, and the difference between those is the whole of BP-VERIFY.

One step deliberately has no place in this list. Nothing here reads the code array, walks the instructions or looks at the stack maps, because the machine that will run those bytes may not be the machine that parsed them, and separating the two is what lets a class file be checked once and executed many times. An implementation is permitted to fold verification into parsing for speed. It is not permitted to fold the errors together, and 4c is where that obligation is written down.

## 4. Guarantees

### 4a. What the specification mandates

- **4a.1** The first four bytes are the magic number `0xCAFEBABE`, and a file whose first four bytes are anything else is not a class file {[JVMS §4.1@SE25]}.
- **4a.2** A representation whose major or minor version the implementation does not support is refused with `UnsupportedClassVersionError`, which is a subclass of `ClassFormatError` and exists so that this one cause can be told apart from the rest {[JVMS §5.3.5@SE25]}.
- **4a.3** `constant_pool_count` is one greater than the number of entries, the table is indexed from 1 to `constant_pool_count - 1`, and an index is valid only if it is greater than zero and less than the count {[JVMS §4.1@SE25]}.
- **4a.4** Format checking establishes that the magic number is right, that every predefined attribute has the length its definition gives it, that the file is neither truncated nor followed by extra bytes, and that the constant pool satisfies the constraints stated for it, and it establishes nothing about whether the classes and members named actually exist {[JVMS §4.8@SE25]}.
- **4a.5** An attribute the implementation does not recognise is ignored in silence, and an implementation is prohibited from refusing a class file because it contains one {[JVMS §4.7.1@SE25]}.
- **4a.6** A representation that is not a `ClassFile` structure is refused with `ClassFormatError`, and one that is well formed but names a class other than the one requested, or has `ACC_MODULE` set, is refused with `NoClassDefFoundError` {[JVMS §5.3.5@SE25]}.
- **4a.7** Every bit of `access_flags` that Table 4.1-B does not assign is reserved, should be zero in a generated class file, and should be ignored by an implementation reading one {[JVMS §4.1@SE25]}.
- **4a.8** An interface has `ACC_ABSTRACT` set and `ACC_FINAL`, `ACC_SUPER`, `ACC_ENUM` and `ACC_MODULE` clear, and a class that is not an interface does not have both `ACC_FINAL` and `ACC_ABSTRACT` set {[JVMS §4.1@SE25]}.
- **4a.9** The bytes of a `CONSTANT_Utf8_info` are modified UTF-8 rather than UTF-8, so no byte may be zero and no byte may lie in the range `0xf0` to `0xff`, and a character outside the basic multilingual plane is encoded as a surrogate pair of three byte sequences {[JVMS §4.4.7@SE25]}.
- **4a.10** The format's own field widths are its limits: 65535 constant pool entries, 65535 fields, 65535 methods, 65535 direct superinterfaces, 65535 local variables and 65535 operand stack slots in one frame, and 255 method parameters counted with `long` and `double` as two each {[JVMS §4.11@SE25]}.
- **4a.11** A class file that does not satisfy the static and structural constraints on the code of a method is refused with `VerifyError`, which is a different error from the one a malformed file gets and is raised at a different point in the class's life {[JVMS §5.4.1@SE25]}.

### 4b. What HotSpot chose

- **4b.1** The magic number is checked before anything else is read, and the message names the value it found in decimal rather than in hexadecimal, so a file starting with the letters `PK` is reported as `Incompatible magic value 1347093252` {[HOTSPOT src/hotspot/share/classfile/classFileParser.cpp:5506@jdk-27+35]}.
- **4b.2** The version is checked even when every other format check has been turned off, which makes it the one property of a class file that cannot be waved through {[HOTSPOT src/hotspot/share/classfile/classFileParser.cpp:5515@jdk-27+35]}.
- **4b.3** A major version below the minimum and a major version above the maximum produce two differently worded errors, `was compiled with an invalid major version` for the first and `has been compiled by a more recent version of the Java Runtime` for the second, and only the second one names the version this runtime does support {[HOTSPOT src/hotspot/share/classfile/classFileParser.cpp:4355@jdk-27+35]} {[HOTSPOT src/hotspot/share/classfile/classFileParser.cpp:4365@jdk-27+35]}.
- **4b.4** A minor version of 65535 is accepted only when the major version is exactly this runtime's own and `--enable-preview` was given, and any other non zero minor version at a major version of 56 or above is refused outright {[HOTSPOT src/hotspot/share/classfile/classFileParser.cpp:4387@jdk-27+35]}.
- **4b.5** Class access flag bits that are not recognised are masked off as the two bytes are read, before any check looks at them, so a class file with reserved bits set loads and the bits are gone by the time anything could object to them {[HOTSPOT src/hotspot/share/classfile/classFileParser.cpp:5547@jdk-27+35]}.
- **4b.6** How much of the class file is checked at all is decided per class from the defining loader and a pair of diagnostic flags, so two identical byte arrays loaded by two different loaders are not held to the same standard {[HOTSPOT src/hotspot/share/classfile/verifier.cpp:115@jdk-27+35]}.
- **4b.7** A JVMTI agent that has registered for the class file load hook forces full checking on regardless of the loader, which means attaching an agent can turn a class file that loaded yesterday into a `ClassFormatError` today {[HOTSPOT src/hotspot/share/classfile/classFileParser.cpp:5392@jdk-27+35]}.
- **4b.8** The argument count of a method is checked against its `max_locals` in the parser, immediately after the two numbers are read and before the code array, and the error is a `ClassFormatError` saying `Arguments can't fit into locals` {[HOTSPOT src/hotspot/share/classfile/classFileParser.cpp:2290@jdk-27+35]}.
- **4b.9** The code array is bounded at 65535 bytes by a check rather than by a field width, and the check runs only when the class is being format checked, so the bound is not enforced for every class {[HOTSPOT src/hotspot/share/classfile/classFileParser.cpp:2293@jdk-27+35]}.
- **4b.10** A class defined from a `byte[]` is parsed from a private copy taken before the machine is called, so a concurrent write to the array cannot affect the class that results {[HOTSPOT src/java.base/share/native/libjava/ClassLoader.c:115@jdk-27+35]}.
- **4b.11** A class defined from a direct `ByteBuffer` by a platform class loader is parsed in place, out of the caller's own memory, with no copy anywhere between the call and the parser {[HOTSPOT src/java.base/share/native/libjava/ClassLoader.c:176@jdk-27+35]}.
- **4b.12** An attribute whose name is not recognised is skipped by its declared length, which is the same code path in a class, a field, a method and a `Code` attribute, and an attribute length that runs off the end of the file is caught by the stream rather than by the attribute reader {[HOTSPOT src/hotspot/share/classfile/classFileParser.cpp:1349@jdk-27+35]}.
- **4b.13** Running out of bytes anywhere produces one error with one message, `Truncated class file`, which names neither the structure being read nor the offset it stopped at {[HOTSPOT src/hotspot/share/classfile/classFileStream.cpp:30@jdk-27+35]}.
- **4b.14** The constant pool is allocated at the count the file declares, before a single entry has been read, which is safe only because the count is bounded at 65535 by its field width {[HOTSPOT src/hotspot/share/classfile/classFileParser.cpp:5530@jdk-27+35]}.
- **4b.15** The stack map frames of a method are validated against that method's `max_stack` while the attribute is being read, and a frame that exceeds it is reported through the verifier's class format error path, which is why breaking `max_stack` produces a `ClassFormatError` naming a rule about type array sizes {[HOTSPOT src/hotspot/share/classfile/stackMapTable.hpp:139@jdk-27+35]}.

### 4c. Ordering obligations

- **4c.1** The header is read in the order the structure declares it, magic then minor version then major version then the constant pool count, and no later item may be read before an earlier one, because the earlier ones decide how the later ones are interpreted {[JVMS §4.1@SE25]}.
- **4c.2** The whole constant pool is read before any index into it is resolved, because an entry may refer to an entry that comes after it, and an implementation that checks references as it reads will reject valid class files {[HOTSPOT src/hotspot/share/classfile/classFileParser.cpp:5536@jdk-27+35]}.
- **4c.3** The error for an unrecognised constant pool tag is held back until the access flags have been read and checked, because a file with `ACC_MODULE` set has to fail with `NoClassDefFoundError` rather than with `ClassFormatError`, and the tag error would otherwise get there first {[HOTSPOT src/hotspot/share/classfile/classFileParser.cpp:5561@jdk-27+35]}.
- **4c.4** The two failures that belong to the loader rather than to the bytes come first: a loader already recorded as an initiating loader of this name fails with `LinkageError`, and a derivation already in progress for this name fails with `ClassCircularityError`, both before the representation is parsed {[JVMS §5.3.5@SE25]}.
- **4c.5** Format checking is complete before verification begins, because verification is part of linking and linking happens to a class that already exists {[JVMS §5.4@SE25]}.
- **4c.6** The check that no bytes remain is last, after every attribute of the class has been read, so an implementation cannot report the extra bytes until it has consumed everything it recognises {[HOTSPOT src/hotspot/share/classfile/classFileParser.cpp:5697@jdk-27+35]}.

## 5. Observation

Every item below is a procedure rather than a result. The tool named in it is the one that answers the question with the least machinery, and where two tools disagree that disagreement is itself the observation.

Four tools carry most of this section. `javap -v` prints the structure of a class file as the platform's own reader understands it. `java.lang.classfile`, on the pinned JDK, builds and rewrites class files from a Java program, which is what makes a broken one cheap to produce. `probes/classfile-fuzz` breaks one valid class file 27 named ways and 256 random ways and records where the machine stopped and in what words. And `xxd` is what settles an argument about a byte, because every other tool on this list is showing an interpretation.

- **5.1** 4a.1, 4b.1: patch the first four bytes to anything else and load the file, with `probes/classfile-fuzz` and `xxd`. The error class is the specification's answer and the wording of the message is HotSpot's.
- **5.2** 4a.2, 4b.2, 4b.3, 4b.4: write the major version field down to 44 and up to one past what this runtime writes, then set the minor version to 65535 with and without `--enable-preview`, with `probes/classfile-fuzz` and `java --enable-preview`. Four inputs, four different messages, and one of them is the only check that survives every flag in section 7.
- **5.3** 4a.3, 4c.2: raise `constant_pool_count` by one without adding an entry, then lower it by one, with `java.lang.classfile` and `javap -v`. Any class file javac produced already contains a forward reference from one pool entry to a later one, so the fact that it loads at all is the observation for the ordering half.
- **5.4** 4a.4, 4c.6: append one byte to a class file that loads, and separately cut one byte off the end, with `xxd` and `probes/classfile-fuzz`. Both are refused and the two messages are not the same message.
- **5.5** 4a.5, 4b.12: add an attribute with an invented name and a correct length to a class, a field and a method, and load it, with `java.lang.classfile` and `javap -v`. Nothing happens, which is the whole of the observation, and `javap` shows the attribute is still there.
- **5.6** 4a.6, 4c.3: rename the class in `this_class` without renaming the file, then set `ACC_MODULE` on an ordinary class, with `java.lang.classfile`. Two different error classes for two files that differ in two bytes.
- **5.7** 4a.7, 4b.5: set a reserved access flag bit and load the class, then read the flags back with `Class.getModifiers` and with `javap -v`. The class loads, and the platform's own reader and the reflection API do not agree about what the flags now are.
- **5.8** 4a.8: set `ACC_FINAL` and `ACC_ABSTRACT` together on a class, `ACC_INTERFACE` without `ACC_ABSTRACT`, and `ACC_FINAL` with `ACC_VOLATILE` on a field, with `probes/classfile-fuzz`. All three are refused, and all three messages print the flag word in hexadecimal rather than naming the pair.
- **5.9** 4a.9: put a zero byte inside a `CONSTANT_Utf8_info`, then a byte of `0xf8`, with `probes/classfile-fuzz` and `xxd`. Both are refused, and the same two byte sequences inside a string constant in a source file are not, because what is stored is modified UTF-8 rather than the text.
- **5.10** 4a.10, 4b.9, 4b.14: generate a class with 65535 methods, one with a method body over 65535 bytes, and one whose declared `constant_pool_count` is 65535 with nothing behind it, with `java.lang.classfile` and `java -Xlog:class+load=info`. The first is accepted, the second is refused, and the third is the one that shows what an implementation allocates before it has read anything.
- **5.11** 4a.11, 4b.8, 4b.15: set `max_stack` to zero under a body that pushes two values, and set `max_locals` below the argument count, with `probes/classfile-fuzz`. The specification names `VerifyError` for both and neither one is a `VerifyError`, which is the finding recorded on [the fuzzer's page](../../docs/generated/classfile-fuzz.md).
- **5.12** 4b.6, 4b.7: load the same malformed class file twice, once through the boot class path and once through an ordinary class loader, then load it again under `-javaagent:` with a transformer that returns its input unchanged, with `java -Xbootclasspath/a` and `-XX:+BytecodeVerificationLocal`. The same bytes produce a class in one run and an error in another.
- **5.13** 4b.10, 4b.11: define a class from a `byte[]` while a second thread overwrites the array, then do the same with a direct `ByteBuffer` from a class loader that is not a platform one, with `jshell` and `java.lang.classfile`. The first is a class derived from the array as it was; the second is a copy taken by the platform, so reaching the racing path from Java means going through a loader that the platform trusts.
- **5.14** 4b.13, 4c.1: truncate a class file at eight different offsets, one inside each top level item, with `xxd` and `probes/classfile-fuzz`. Every one of them produces the same sentence, which is what it costs to have one bounds check instead of a check at every read.
- **5.15** 4c.4: define the same class twice through one loader, and write a loader whose `loadClass` asks for the class it is currently defining, with `jshell`. The two errors are different and neither of them is about the bytes.
- **5.16** 4c.5: define a class whose bytes are well formed and whose code does not verify, then wait before using it, with `jshell` and `javap -v`. `defineClass` returns a `Class` object and the `VerifyError` arrives later, which is the observable difference between parsing and verifying.

## 6. Edge cases

### 6.1 Malformed input

Malformed input is the normal case for a parser of this kind, not the exception, because the input is attacker controlled in every deployment that loads a class from anywhere but its own build. An implementation is required to terminate on every input, to produce an error rather than an internal failure, and never to read outside the buffer it was given. HotSpot enforces the last of these in one place, a bounds check inside the stream that every read goes through, and the error it produces is a `ClassFormatError` whose message is `Truncated class file` {[HOTSPOT src/hotspot/share/classfile/classFileStream.cpp:30@jdk-27+35]}.

Three shapes of malformed input behave differently and an implementation has to handle all three. A truncated file runs out of bytes in the middle of a structure. A file with a plausible structure and an impossible value, such as a constant pool index pointing at nothing or a `max_stack` that cannot hold what the code pushes, gets all the way to a semantic check. A file with extra bytes after the last attribute is well formed as far as any reader can tell and is refused anyway {[JVMS §4.8@SE25]}, which means an implementation cannot stop reading when it has what it needs.

The measured behaviour of the third shape is not what a reader expects, and it is recorded rather than assumed. `probes/classfile-fuzz` breaks one valid class file 27 named ways and 256 random ways, and [the resulting page](../../docs/generated/classfile-fuzz.md) shows that two of the 27 produce an error class the specification does not name for them, and that 12 of the 27 produce a message that uses none of the words the rule uses. The two mismatches are both constraints from JVMS 4.9, which 5.4.1 protects with a `VerifyError`, and both arrive as a `ClassFormatError`.

Single bit corruption is the case an implementation is most likely to meet in production and the one it is least able to detect. 40 of 256 single bit flips of a 368 byte class file load and link with nothing said, because most of the bytes in a class file are either payload that nothing validates or a value whose neighbouring values are equally legal. An implementation that reports success on those 40 is conforming. A reader who concludes from that that the format is checked is wrong, and the number is here so the conclusion is available without running anything.

### 6.2 Resource exhaustion

Every count in a class file is read before the thing it counts, which is the property that makes exhaustion possible: a two byte field can ask for 65535 constant pool entries, 65535 fields or 65535 methods before a single one of them has been read {[JVMS §4.11@SE25]}. An implementation that allocates on the declared count is allocating on attacker controlled input. HotSpot does allocate the constant pool at the declared size before parsing a single entry {[HOTSPOT src/hotspot/share/classfile/classFileParser.cpp:5530@jdk-27+35]}, which is a defensible choice because the pool is bounded at 65535 entries by the width of the field, and it is a choice an implementation with a wider field would not be able to copy.

The bounded fields are what makes the format safe to parse eagerly, and the boundedness is the whole of the safety argument. The constant pool, the fields, the methods and the direct superinterfaces are each capped at 65535 by a `u2`. The operand stack and the local variable array of one frame are capped at 65535 the same way. The code array of one method is capped at 65535 by a check rather than by a field, because the field is a `u4` and the limit is smaller than the field, so an implementation that trusts the width gets a method body of up to four gigabytes {[HOTSPOT src/hotspot/share/classfile/classFileParser.cpp:2293@jdk-27+35]}.

That check is one of the ones HotSpot runs only when it is verifying. A class file loaded by the boot loader in a default configuration is not format checked to that depth, so the code length bound is not enforced on it, and the parser instead meets the end of the buffer and reports a truncated file. Neither outcome is a crash, and the difference between them is the difference between a diagnosable error and one that names the wrong thing.

An implementation is permitted to run out of memory here and `OutOfMemoryError` is not a `ClassFormatError`. A conforming machine may throw it at any allocation during derivation, so a harness that asserts on the exact error for a large input is asserting about the machine's heap and not about the class file.

### 6.3 The concurrent case

Parsing is a pure function of the bytes, so there is no concurrency inside it, and every concurrent hazard here is about the buffer rather than about the parser. There is exactly one, and it is decided by which overload of `defineClass` the caller reached for.

The `byte[]` overload copies. The native side allocates its own buffer and copies the array out of the Java heap before the machine sees it {[HOTSPOT src/java.base/share/native/libjava/ClassLoader.c:115@jdk-27+35]}, so a second thread writing to that array while the class is being defined cannot change the class that comes out. The class is derived from the snapshot.

The direct `ByteBuffer` overload does not copy. The address of the buffer's own memory is handed to the machine {[HOTSPOT src/java.base/share/native/libjava/ClassLoader.c:176@jdk-27+35]} and the parser reads it in place {[HOTSPOT src/hotspot/share/prims/jvm.cpp:887@jdk-27+35]}. A second thread writing to that buffer during the call is racing with the parser, and the resulting class is derived from bytes that were never all present at the same instant. The platform's own class loaders take this route, and everybody else's buffer is copied into a confined arena first, so the race is reachable from Java only through a loader that is a `BuiltinClassLoader`, and it is reachable from JNI by anybody.

An implementation is therefore required to specify which of those it does, and a specification that is silent about it is a specification with a security hole in it. The requirement this blueprint states is the weaker and checkable one: the class an implementation derives has to be a class that some single snapshot of the buffer would have derived. Copying first satisfies it. Reading in place does not, and HotSpot does not claim it does.

The other concurrency question people expect here belongs elsewhere. Two threads defining the same name through the same loader, and which of them wins, is a property of loading rather than of parsing, and it is BP-LOAD's to specify.

## 7. Configuration

Nothing in section 4a is configurable, and almost everything in 4b is. Which of the two a given behaviour belongs to is the question this section exists to make answerable, because a guarantee that holds under one flag and not another is two facts and both of them are here.

**How much is checked at all.** `BytecodeVerificationLocal` is off by default and `BytecodeVerificationRemote` is on, and the pair decides, per class, from the defining loader, whether the format checks that section 4b marks as conditional run {[HOTSPOT src/hotspot/share/runtime/globals.hpp:455@jdk-27+35]} {[HOTSPOT src/hotspot/share/runtime/globals.hpp:458@jdk-27+35]}. A class loaded by the boot loader in a default configuration is therefore checked less thoroughly than the same bytes loaded by an application loader. Both flags are diagnostic, which means turning them on takes `-XX:+UnlockDiagnosticVMOptions`, and the supported way to move them is `-Xverify`. The full list of what those flags are and where they came from is in [the flag reference](../../docs/generated/flags.md).

**What an agent does to it.** A JVMTI agent registered for the class file load hook forces checking to full for every class it can see {[HOTSPOT src/hotspot/share/classfile/classFileParser.cpp:5392@jdk-27+35]}. This is the configuration change most likely to surprise somebody, because it is not a flag, it is the presence of a `-javaagent` or a native agent, and it can make a class that has loaded in production for years stop loading in a profiling run.

**Preview features.** `--enable-preview` is what makes a minor version of 65535 acceptable, and it is accepted only at this runtime's own major version, so a preview class file cannot be carried forward to the next release the way an ordinary one can {[HOTSPOT src/hotspot/share/classfile/classFileParser.cpp:4387@jdk-27+35]}.

**Which version this runtime writes and reads.** The pinned JDK writes class file major version 71 and reads everything from 45 up to 71. The pinned specification edition describes versions up to 69. Every clause in 4a is quoted from a document that does not describe the file this JDK produces, because no published edition describes it yet, and both numbers are recorded in `docs/pin.json` so the gap is a fact rather than a surprise.

**The cached class.** A class taken from the AOT cache was parsed and verified when the cache was written, and linking it checks the constraints recorded at that time rather than parsing it again {[HOTSPOT src/hotspot/share/oops/instanceKlass.cpp:1075@jdk-27+35]}. An implementation with a cache of its own inherits the obligation that goes with it, which is that the cached form has to be a form only its own parser could have produced, because nothing downstream will check it again.

Two things that look like configuration are not. `-Xlog:class+load` changes what is printed and nothing about what is accepted. And the `java.lang.classfile` API's own validation is a property of the library that writes a class file rather than of the machine that reads one, so a file it refuses to write may still be a file this specification requires a machine to accept.

## 8. Conformance

### 8.1 What conformance means here

An implementation conforms to this blueprint if, for every finite sequence of bytes offered to `derive`, it reaches the same decision as section 4a requires and reports a failure with the same error class 4a names, and if it performs the steps of section 3 in an order consistent with every clause in 4c. Nothing is said about how long it takes, how much it allocates, what its messages say, or what it does with a class file that section 4a does not describe.

Section 4b is not part of that obligation. Those clauses record what HotSpot at the pinned build does, and an implementation is free to differ from every one of them and still conform. What it is not free to do is differ silently. An implementation that departs from a 4b clause states which clause and what it does instead, in one line, because the value of 4b is that a reader can tell a choice from a requirement, and that value is lost if two implementations disagree without saying so.

Three consequences of this are worth stating because they are the ones people get wrong. First, matching a message is never conformance, so a test that asserts on `Incompatible magic value 1347093252` is testing HotSpot rather than the specification. Second, an implementation that is stricter than 4a requires does not conform, because refusing a class file the specification requires it to accept is a failure in the same way accepting a bad one is, and 4a.5 is the clause this catches most often. Third, `OutOfMemoryError` is permitted at any point and is never evidence of anything, so a checklist item that expects a specific error for a large input is unfalsifiable and is not in the list below.

The capstone harness reports against 8.2 and against nothing else. An item is passed when a test exists that would fail if the behaviour changed, skipped when the item names a case the harness cannot construct, and failed otherwise. There is no fourth state, and in particular there is no state for an item that nobody has looked at.

### 8.2 Checklist

- **8.2.1** 4a.1, 4b.1: refuses every input whose first four bytes are not `0xCAFEBABE`, including the empty input and an input of fewer than four bytes, and does so before interpreting anything else.
- **8.2.2** 4a.2, 4b.2, 4b.3, 4b.4: accepts exactly the major versions it documents, refuses the ones below and above with `UnsupportedClassVersionError`, and treats a minor version of 65535 as a preview class file rather than as an ordinary one.
- **8.2.3** 4a.3, 4b.14, 4c.2: indexes the constant pool from 1 to `constant_pool_count - 1`, resolves an entry that refers to a later entry, and does not allocate on the declared count in a way that a count of 65535 with no entries behind it can exhaust.
- **8.2.4** 4a.4, 4c.6: refuses a truncated file and a file with bytes after the last class attribute, and reaches the second decision only after every attribute it recognises has been consumed.
- **8.2.5** 4a.5, 4b.12: loads a class carrying an attribute with an unrecognised name on the class, on a field, on a method and inside a `Code` attribute, and reports no error and no warning for any of the four.
- **8.2.6** 4a.6, 4c.3: distinguishes the three failures of derivation, `ClassFormatError` for a representation that is not a `ClassFile` structure, `NoClassDefFoundError` for one that names a different class or has `ACC_MODULE` set, and reaches the second of those even when the file also contains a constant pool tag it does not recognise.
- **8.2.7** 4a.7, 4b.5: loads a class file with reserved `access_flags` bits set, and whatever it does with those bits, reports them consistently through every interface it offers.
- **8.2.8** 4a.8: refuses `ACC_INTERFACE` without `ACC_ABSTRACT`, `ACC_FINAL` together with `ACC_ABSTRACT` on a class, and every contradictory flag pair Table 4.1-B forbids on a field and on a method.
- **8.2.9** 4a.9: refuses a `CONSTANT_Utf8_info` containing a zero byte or a byte in the range `0xf0` to `0xff`, and accepts a supplementary character encoded as a surrogate pair of two three byte sequences.
- **8.2.10** 4a.10, 4b.9: accepts a class at each of the format's stated limits, 65535 fields, 65535 methods and 65535 superinterfaces, and refuses a method whose code array exceeds 65535 bytes whatever the width of the field says.
- **8.2.11** 4a.11, 4b.8, 4b.15: reports a violation of a static or structural constraint on a method's code as `VerifyError` rather than as `ClassFormatError`, which is the item the pinned HotSpot build fails for `max_stack` and for the argument count against `max_locals`.
- **8.2.12** 4b.6, 4b.7: documents, for every configuration it offers, which checks are skipped, and either performs every 4a check in every configuration or names the configuration in which it does not.
- **8.2.13** 4b.10, 4b.11: derives, for every entry point that takes a buffer the caller can still write to, a class that some single snapshot of that buffer would have derived, or documents that the entry point is unsafe under concurrent modification.
- **8.2.14** 4b.13: terminates on every input without reading outside the buffer it was given, which is checked by a fuzzer rather than by a test, and reports a diagnosable error for each of the eight top level items a file can be truncated inside.
- **8.2.15** 4c.1: reads magic, then minor version, then major version, then the constant pool count, and does not decide anything about a later item before an earlier one has been read.
- **8.2.16** 4c.4: raises `LinkageError` for a loader already recorded as an initiating loader of the name and `ClassCircularityError` for a derivation already in progress, both before any byte of the representation is parsed.
- **8.2.17** 4c.5: completes format checking before verification begins, so a class whose bytes are well formed and whose code does not verify exists as a `Class` object before the `VerifyError` is raised.

## 9. Provenance

Section 2 is generated from [the class file structure page](../../docs/generated/classfile.md), which `tools/gen_classfile.py` builds from the pinned specification edition and the pinned JDK's own reader. It is not written here and editing it here has no effect.

Every clause in 4a quotes JVMS SE25 and every clause in 4b names a file and a line in `jdk-27+35`. `tools/refcheck.py` resolves both against `docs/citations.json` and fails the build when a line has moved, so a clause that has drifted off its evidence is a broken build rather than a stale sentence.

Three things in this blueprint are measured rather than read. The counts in section 6.1, the 27 named mutations and the 40 single bit flips that load without complaint, come from `probes/classfile-fuzz` against one 368 byte class file, and a different class file would give different numbers. The copy and no copy finding in 6.3 was read out of `ClassLoader.c` and confirmed by following the direct buffer path to the parser, and it has not been demonstrated by observing a race. The message wordings quoted in 4b were taken from the source rather than from a run.

Two questions this blueprint raises are open. The pinned JDK writes class file major version 71 and the pinned specification edition stops at 69, so 4a describes a format slightly older than the one section 2 is generated from, and the gap closes when `docs/pin.json` moves to an edition that covers 71. And 8.2.11 is an item the pinned build fails, which is a finding about HotSpot rather than a defect in the checklist, and it stays in the list until somebody establishes which of the two documents is wrong.

The reviews field in the front matter is null. Nothing in this blueprint has been read by anybody with production experience of a class file parser, and until it has, the conformance list is one person's reading of the specification and not a standard.
