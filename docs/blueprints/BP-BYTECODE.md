## 1. Scope

This blueprint specifies the execution of one method's code array: the state an instruction operates on, how an instruction is encoded and fetched, what an implementation is allowed to do to the array between reading it and running it, and what an observer is guaranteed to see. An implementation built from this document can take a `Code` attribute that has already been parsed and verified and execute it, and can say for any observable difference from HotSpot whether that difference is conforming.

It covers three things a reader is likely to expect somewhere else. The first is the frame, because the local variable array and the operand stack are what almost every instruction reads and writes, and an instruction set table with no frame under it is a list of names. The second is the boundary of undefined behaviour, which the specification draws exactly once and in one sentence, and which is the reason an interpreter is allowed to be as fast as it is. The third is rewriting, meaning the fact that the bytes an implementation executes are permitted to differ from the bytes the class file contained, which is the largest single surprise in this subject and is where a reader's tools stop agreeing with each other.

It deliberately excludes five things. Reading and checking the class file that carries the code array belongs to BP-CLASSFILE. Deciding that a code array is well typed belongs to BP-VERIFY, and the `StackMapTable` attribute it consults belongs to BP-STACKMAP. Turning a constant pool index into a class, a field or a method belongs to BP-CONSTPOOL, so an instruction's operand is specified here as an index and its resolution is not. Everything about when a class is loaded, linked and initialized belongs to BP-LOAD, and this blueprint takes a method that is ready to run as given.

Two further exclusions look as though they belong here. The meaning of each individual instruction is not restated: section 3 is a generated table of every opcode with its length and its stack effect, and the prose describing what each one does is JVMS chapter 6, which is a document this one has no reason to copy and every reason not to. And compiled execution is out of scope, so nothing here says what a compiler that translates a method to machine code while the program runs does with it, beyond the one guarantee that whatever it does is unobservable except through timing. What a compiler may do to make this code faster is M6's subject.

## 2. Data structures

Four structures carry everything in this blueprint: the code array, the frame, the local variable array and the operand stack. The first is in the class file, the other three exist only while a method is running, and the whole of section 3 is instructions that move values between the last two.

**The code array** is the `code` item of a `Code` attribute, preceded in the same structure by `max_stack`, `max_locals` and `code_length` {[JVMS §4.7.3@SE25]}. It is a sequence of bytes with no alignment and no framing: the boundary between one instruction and the next is not marked anywhere and is recovered by decoding from the beginning, which is why the static constraints have to say that the first instruction starts at index 0 and that each one starts where the previous one ended. `code_length` is a `u4` in the file and is required to be greater than zero and less than 65536.

**The frame** is created on each method invocation and destroyed when the invocation completes {[JVMS §2.6@SE25]}. It holds its own local variable array, its own operand stack and a reference to the run-time constant pool of the class of the method it belongs to. The specification permits an implementation to put anything else it likes in there, and every implementation does. The sizes of the two arrays are fixed before the frame exists, which is the property that makes a frame allocatable in one step and is the reason `max_stack` and `max_locals` are in the class file at all.

**The local variable array** is indexed from zero, and one entry holds an `int`, a `float`, a `reference` or a `returnAddress` {[JVMS §2.6.1@SE25]}. A `long` or a `double` occupies two consecutive entries and is named by the lesser index, and the pair is not required to be aligned to any boundary. Nothing in the array is typed at run time, because the type of what is in slot `n` at any given instruction was settled before the method started running, which is BP-VERIFY's whole subject.

**The operand stack** is last in, first out, is empty when the frame is created, and has a maximum depth fixed at compile time {[JVMS §2.6.2@SE25]}. It is where instructions take their arguments and leave their results, and it is also where arguments are assembled for an invocation and where a returned value arrives. A `long` or a `double` occupies two of its units, which is why an operand stack depth is counted in units rather than in values.

**The pc register** belongs to the thread rather than to the frame {[JVMS §2.5.1@SE25]}. It holds the address of the instruction being executed while the current method is a Java method and holds nothing meaningful while the current method is native.

HotSpot's own representation of these is worth stating, because two properties of it are visible from Java and one is visible in every stack dump. A method's bytecodes are stored immediately after the end of the `ConstMethod` structure that describes them {[HOTSPOT src/hotspot/share/oops/constMethod.hpp:42@jdk-27+35]}, so the address of the code array is the address of the header plus its size {[HOTSPOT src/hotspot/share/oops/constMethod.hpp:419@jdk-27+35]} and a bytecode pointer is a raw address into metaspace rather than an offset. The code size is held in a `u2` {[HOTSPOT src/hotspot/share/oops/constMethod.hpp:199@jdk-27+35]}, so the specification's bound of less than 65536 is a limit this implementation could not exceed if it wanted to, and `max_stack`, `max_locals` and the size of the parameter block sit next to it in the same widths {[HOTSPOT src/hotspot/share/oops/constMethod.hpp:205@jdk-27+35]} {[HOTSPOT src/hotspot/share/oops/constMethod.hpp:206@jdk-27+35]} {[HOTSPOT src/hotspot/share/oops/constMethod.hpp:207@jdk-27+35]}.

The interpreter's frame on aarch64 is laid out in a comment at the top of its own header {[HOTSPOT src/hotspot/cpu/aarch64/frame_aarch64.hpp:35@jdk-27+35]}, and three things in it are not what the specification's picture suggests. The expression stack is at the machine stack pointer and grows toward lower addresses {[HOTSPOT src/hotspot/cpu/aarch64/frame_aarch64.hpp:36@jdk-27+35]} {[HOTSPOT src/hotspot/cpu/aarch64/frame_aarch64.hpp:190@jdk-27+35]}, so a push moves down the page while every diagram of an operand stack draws it moving up. The frame holds a pointer to its locals and a bytecode pointer as ordinary slots {[HOTSPOT src/hotspot/cpu/aarch64/frame_aarch64.hpp:44@jdk-27+35]} {[HOTSPOT src/hotspot/cpu/aarch64/frame_aarch64.hpp:42@jdk-27+35]}, which makes the pc a per frame value in the implementation even though the specification gives it to the thread. And the locals are not a fresh array: they are the words the caller pushed as arguments, sitting at the far end of the frame next to the caller's stack pointer {[HOTSPOT src/hotspot/cpu/aarch64/frame_aarch64.hpp:63@jdk-27+35]}, so the parameters arrive already in place and only the remaining locals have to be made.

The three numbers differ for two reasons and neither is a mistake. HotSpot defines 36 codes above the last one the specification names, which it writes into a method's bytecode after the class file has been parsed, so they exist in memory and can never exist in a file. The class file API drops `wide` and `breakpoint` and adds twelve wide forms, which is a different way of modelling the same bytes.

### 3.2 Every opcode a class file may contain

Length is the whole instruction in bytes, opcode included. Stack is what the instruction does to the depth of the operand stack, as HotSpot's own table records it. Seen is how many times it occurs in the scanned code above, which is the column that says which of these a reader will actually meet.

The operands column is HotSpot's format string put into words, and it describes a method already loaded into a VM rather than the bytes on disk. That is why nine of these say native order: HotSpot rewrites those operands when it links the method, replacing the constant pool index the file carries with an index into its own resolved cache, in the byte order of the machine. In the class file itself every one of them is a big endian constant pool index, which is what to write when building one by hand and what `javap` shows. The ones that differ are `getfield`, `getstatic`, `invokedynamic`, `invokeinterface`, `invokespecial`, `invokestatic`, `invokevirtual`, `putfield`, `putstatic`.

## 4. Guarantees

### 4a. What the specification mandates

- **4a.1** An instruction is a one byte opcode followed by zero or more operands, an operand wider than one byte is stored big endian, and the instruction stream is aligned to one byte, with `tableswitch` and `lookupswitch` the only two instructions padded so that some of their operands land on a four byte boundary {[JVMS §2.11@SE25]}.
- **4a.2** A frame is created on each method invocation and destroyed when that invocation completes, normally or abruptly, and it holds its own local variable array, its own operand stack and a reference to the run-time constant pool of the class of its method {[JVMS §2.6@SE25]}.
- **4a.3** The local variable array is indexed from zero, one entry holds an `int`, a `float`, a `reference` or a `returnAddress`, and a `long` or a `double` occupies two consecutive entries named by the lesser index and required to be aligned to nothing {[JVMS §2.6.1@SE25]}.
- **4a.4** The operand stack is last in, first out, is empty when its frame is created, and has a maximum depth that is fixed before the frame exists and supplied with the code {[JVMS §2.6.2@SE25]}.
- **4a.5** Each thread has its own pc register, which holds the address of the instruction being executed when the current method is a Java method and holds nothing defined when the current method is native {[JVMS §2.5.1@SE25]}.
- **4a.6** `code_length` is greater than zero and less than 65536, so a code array is never empty and never larger than a `u2` can measure, whatever the width of the field that carries it {[JVMS §4.7.3@SE25]}.
- **4a.7** Only instructions the specification documents may appear in a code array, the opcodes it reserves may not, and `jsr`, `jsr_w` and `ret` may not appear at class file version 51.0 or above {[JVMS §4.9.1@SE25]}.
- **4a.8** The first instruction begins at index 0, each instruction except the last begins at the index of the previous one plus that instruction's length including its operands, and the last byte of the last instruction is the byte at `code_length - 1` {[JVMS §4.9.1@SE25]}.
- **4a.9** The operand stack has the same depth at an instruction on every execution path that reaches it, never grows deeper than `max_stack`, and is never popped when empty {[JVMS §4.9.2@SE25]}.
- **4a.10** The two local variables holding a `long` or a `double` are never reversed, never split and never operated on individually, and no local variable is read before it has been assigned {[JVMS §4.9.2@SE25]}.
- **4a.11** If a constraint stated in an instruction's own description is not satisfied at run time, the behaviour of the machine is undefined, and it is verification at link time that makes this unreachable rather than any check the instruction performs {[JVMS §6.1@SE25]}.
- **4a.12** Invoking a method whose `ACC_SYNCHRONIZED` flag is set enters a monitor, and that monitor is exited whether the invocation completes normally or abruptly, including when the exception is on its way out of the method {[JVMS §2.11.10@SE25]}.
- **4a.13** Normal completion restores the invoker's frame with its pc advanced past the invocation instruction and the returned value, if there is one, pushed onto the invoker's operand stack {[JVMS §2.6.4@SE25]}, and abrupt completion returns no value to the invoker at all {[JVMS §2.6.5@SE25]}.
- **4a.14** Enforcing structured locking, meaning that every monitor exit in a method matches an earlier entry in that method, is permitted and not required, so a machine that refuses unstructured locking and a machine that allows it both conform {[JVMS §2.11.10@SE25]}.

### 4b. What HotSpot chose

- **4b.1** A method's bytecodes are stored immediately after the end of the `ConstMethod` that describes them {[HOTSPOT src/hotspot/share/oops/constMethod.hpp:42@jdk-27+35]}, so the address of the code array is computed from the address of the header rather than stored {[HOTSPOT src/hotspot/share/oops/constMethod.hpp:419@jdk-27+35]}, and a bytecode pointer is a raw address into metaspace rather than an index.
- **4b.2** The code size is held in a `u2` {[HOTSPOT src/hotspot/share/oops/constMethod.hpp:199@jdk-27+35]}, which makes the specification's bound of less than 65536 a property of the representation here and not a check that could be relaxed.
- **4b.3** `max_stack`, `max_locals` and the size of the parameter block are stored beside it in the same width {[HOTSPOT src/hotspot/share/oops/constMethod.hpp:205@jdk-27+35]} {[HOTSPOT src/hotspot/share/oops/constMethod.hpp:206@jdk-27+35]} {[HOTSPOT src/hotspot/share/oops/constMethod.hpp:207@jdk-27+35]}, so the frame's dimensions are known from six bytes of the method's header.
- **4b.4** The interpreter's frame keeps its bytecode pointer and a pointer to its locals as ordinary slots in the frame {[HOTSPOT src/hotspot/cpu/aarch64/frame_aarch64.hpp:42@jdk-27+35]} {[HOTSPOT src/hotspot/cpu/aarch64/frame_aarch64.hpp:44@jdk-27+35]}, which makes both of them per frame values in an implementation whose specification gives the pc to the thread.
- **4b.5** The expression stack sits at the machine stack pointer and grows toward lower addresses {[HOTSPOT src/hotspot/cpu/aarch64/frame_aarch64.hpp:36@jdk-27+35]} {[HOTSPOT src/hotspot/cpu/aarch64/frame_aarch64.hpp:190@jdk-27+35]}, so a push moves down through memory while every picture of an operand stack draws it moving up.
- **4b.6** The locals and the caller's outgoing arguments are the same words: the argument block the caller assembled becomes the callee's first locals, at the far end of the frame beside the caller's stack pointer {[HOTSPOT src/hotspot/cpu/aarch64/frame_aarch64.hpp:63@jdk-27+35]}, so an invocation does not copy its arguments anywhere.
- **4b.7** Bytecode is not immutable, and the flag that permits this says as much in the text it prints to anybody who asks the machine what its options are {[HOTSPOT src/hotspot/share/runtime/globals.hpp:1111@jdk-27+35]}.
- **4b.8** A second and separate kind of rewriting fuses common pairs of instructions into one, under its own flag {[HOTSPOT src/hotspot/share/runtime/globals.hpp:1114@jdk-27+35]}, and both flags are platform dependent, so their default is a property of the port rather than of the product.
- **4b.9** The link time rewrite happens once per class {[HOTSPOT src/hotspot/share/interpreter/rewriter.cpp:568@jdk-27+35]} and its main work is replacing constant pool indices in the code array with indices into a constant pool cache {[HOTSPOT src/hotspot/share/interpreter/rewriter.cpp:526@jdk-27+35]}, so the operand bytes of a resolving instruction in a running method do not hold the number the class file held.
- **4b.10** A class whose `invokespecial` instructions on interfaces overflow the rewriter's own index space is refused with an `InternalError` saying the class file cannot be loaded {[HOTSPOT src/hotspot/share/interpreter/rewriter.cpp:560@jdk-27+35]}, which is a refusal of a class file that violates no constraint the specification states.
- **4b.11** The pair fusing rewrite happens while the method is executing: the template for `aload_0` reads the following opcode and stores a fused opcode over the `aload_0` it is currently executing {[HOTSPOT src/hotspot/cpu/aarch64/templateTable_aarch64.cpp:939@jdk-27+35]} {[HOTSPOT src/hotspot/cpu/aarch64/templateTable_aarch64.cpp:953@jdk-27+35]}.
- **4b.12** Every in place patch is guarded by a flag test at the top of the patcher {[HOTSPOT src/hotspot/cpu/aarch64/templateTable_aarch64.cpp:168@jdk-27+35]}, so an implementation that turns the flag off has a code array that is constant from the moment the class is linked.
- **4b.13** The fused and fast forms are numbered above every opcode the specification names and each one records the instruction it was rewritten from {[HOTSPOT src/hotspot/share/interpreter/bytecodes.cpp:52@jdk-27+35]}, which is what lets a tool map an executing method back onto the class file it came from.
- **4b.14** When the instruction after an `aload_0` is a `getfield` that has not itself been rewritten yet, the fusing is deferred rather than done {[HOTSPOT src/hotspot/cpu/aarch64/templateTable_aarch64.cpp:947@jdk-27+35]}, so which fused instruction a method ends up holding is a function of the order in which its paths first ran.

### 4c. Ordering obligations

- **4c.1** The pc is calculated and the opcode fetched, then the operands are fetched, then the action is performed, and the number and size of the operands are known only once the opcode is {[JVMS §2.11@SE25]}.
- **4c.2** A frame exists for the whole of its invocation and no longer: the invoker's frame is not resumed until the callee's is gone, which is what makes the return value arrive on the invoker's stack rather than on the callee's {[JVMS §2.6@SE25]}.
- **4c.3** A monitor entered by a synchronized method's invocation is exited before an exception leaves that method, so an implementation may not unwind first and release afterwards {[JVMS §2.11.10@SE25]}.
- **4c.4** Verification of a class's methods happens before those methods are rewritten, and both happen before the methods are linked {[HOTSPOT src/hotspot/share/oops/instanceKlass.cpp:1059@jdk-27+35]} {[HOTSPOT src/hotspot/share/oops/instanceKlass.cpp:1073@jdk-27+35]} {[HOTSPOT src/hotspot/share/oops/instanceKlass.cpp:1079@jdk-27+35]}, so the verifier sees the bytes the class file carried and never sees a rewritten one.
- **4c.5** All three of those happen while the thread holds the class's own initialization lock {[HOTSPOT src/hotspot/share/oops/instanceKlass.cpp:1042@jdk-27+35]}, and the class is marked linked only afterwards {[HOTSPOT src/hotspot/share/oops/instanceKlass.cpp:1118@jdk-27+35]}, which is the whole reason the link time rewrite needs no atomicity.
- **4c.6** The in place fusing happens only after the link time rewrite has finished, because it writes opcodes that name a constant pool cache the first rewrite created {[HOTSPOT src/hotspot/share/interpreter/rewriter.cpp:568@jdk-27+35]} {[HOTSPOT src/hotspot/cpu/aarch64/templateTable_aarch64.cpp:917@jdk-27+35]}, so an implementation cannot fuse first and resolve later.

## 5. Observation

The difficulty in this section is that most of what a frame does is invisible from Java, and the two tools that can see it disagree with each other on purpose. `javap -c` shows the bytes the class file carried. The serviceability agent shows the bytes the machine is executing. Where those two differ is not a fault in either one, it is section 4b, and several items below are procedures for making the difference appear.

Five tools carry this section. `javap -c` and `javap -v` print a method's code array as the class file holds it. `java.lang.classfile` builds a method with the code array of one's choosing, which is what makes an illegal one available without a compiler that refuses to emit it. `jhsdb`, whose command set is the serviceability agent, reads the structures of section 2 out of a live or a dead process. `probes/classfile-fuzz` breaks a class file in named ways and records what came back. And `-XX:+PrintFlagsFinal` answers what the two rewriting flags are set to on the machine at hand, which every item about rewriting depends on.

- **5.1** 4a.1, 4a.8: compile a method containing a `switch` over sparse values and read its code array twice, with `javap -c` for the instruction indices and with `xxd` for the padding bytes between the `tableswitch` opcode and its first operand. The index `javap` prints for each instruction is the index the previous one ended at, and the pad is what breaks that arithmetic exactly once.
- **5.2** 4a.2, 4c.2: write a method that recurses to a given depth and then reads its own stack with `StackWalker`, with `jshell`. One frame per invocation, and the frame of a method that has returned is not there to be walked.
- **5.3** 4a.3, 4a.10: build a method that stores a `double` into slots `n` and `n+1` and then loads an `int` from `n+1`, with `java.lang.classfile`, and load it through an ordinary loader and then through the boot class path. The verifier refuses it and the machine without the verifier does not, and what the second one prints is the low half of a `double` read as an `int`.
- **5.4** 4a.4, 4a.9: build one method whose `max_stack` is one less than its body needs and one whose two branches leave different depths at the same instruction, with `java.lang.classfile` and `probes/classfile-fuzz`. Both are refused, and the second is refused by a rule about paths rather than about depth.
- **5.5** 4a.5: stop a thread inside an interpreted method and again inside a native method and read the bytecode pointer of the top frame, with `jhsdb jstack --mixed`. The first has one and the second does not, which is the specification's undefined pc made visible.
- **5.6** 4a.6: build a method with an empty code array and one with a code array of exactly 65536 bytes, with `java.lang.classfile`. Both are refused and the two messages are not about the same thing.
- **5.7** 4a.7: assemble a method containing the byte `0xdd`, which the specification assigns to nothing, and a method containing `jsr` at class file version 51 or above, with `probes/classfile-fuzz` and `java.lang.classfile`. The first produces a message naming an instruction no class file may contain, which is on [the fuzzer's page](../../docs/generated/classfile-fuzz.md).
- **5.8** 4a.11: take the class from 5.3, put it on the boot class path so nothing verifies it, and run it, with `jshell` and `java -Xbootclasspath/a`. No error arrives and a value does, which is what undefined behaviour looks like when the machine happens to be lucky, and running the same class on a second implementation is the rest of the observation.
- **5.9** 4a.12, 4a.13, 4c.3: call a `synchronized` method that throws, and in the caller's `catch` block ask `Thread.holdsLock` about the receiver, with `jshell`. The lock is already released by the time the caller sees the exception, and the invoking instruction's stack effect on the caller's frame is what `javap -c` shows for the two completion paths.
- **5.10** 4a.14: build a method containing a `monitorexit` with no matching `monitorenter`, and one that enters two monitors and exits them in the same order rather than the reverse, with `java.lang.classfile`. What this machine does with them is what it does, and the item passes either way, which is the point of a permitted and not required rule.
- **5.11** 4b.1, 4b.2, 4b.3: read the `ConstMethod` of a loaded method and its bytecodes out of a running process, with `jhsdb clhsdb`. The code array begins at the address the header ends at, and the sizes read back are the ones `javap -v` printed for `max_stack` and `max_locals`.
- **5.12** 4b.4, 4b.5, 4b.6: disassemble the interpreter's entry for an ordinary instance method and follow where it puts the incoming arguments, with `jhsdb` and the disassembler recorded on [the hsdis page](../../docs/generated/hsdis.md). The locals pointer lands on the words the caller pushed, and the expression stack pointer moves down rather than up as values are pushed.
- **5.13** 4b.7, 4b.8, 4b.12: ask the machine what the two rewriting flags are, then run the same program with each of them off, with `java -XX:+PrintFlagsFinal -version` and `-XX:-RewriteBytecodes`. Both are platform dependent, so the answer on one machine is not the answer on another.
- **5.14** 4b.9: dump the code array of a linked method through the serviceability agent and compare the two operand bytes of a `getfield` with what `javap -c` prints for the same instruction, with `jhsdb clhsdb` and `javap -c`. The class file holds a constant pool index and the running method holds something else.
- **5.15** 4b.10: generate a class with enough `invokespecial` instructions on interface methods to exhaust the rewriter's index space and load it, with `java.lang.classfile`. The error is an `InternalError` rather than any error the specification names, and the class file it refused is a legal one.
- **5.16** 4b.11, 4b.13, 4b.14: run a trivial getter several thousand times, dumping its code array through the serviceability agent before and after, then do it again with the pair fusing turned off, with `jhsdb clhsdb` and `-XX:-RewriteFrequentPairs`. The `aload_0` becomes a fused instruction in the first run, stays an `aload_0` in the second, and which fused instruction it becomes depends on which path ran first.
- **5.17** 4c.1: unobservable. The order in which one instruction's opcode and operands are fetched has no effect any program can detect, because nothing may modify a code array between the two except the rewriting of 4b.11, and that writes an opcode rather than an operand.
- **5.18** 4c.4, 4c.5: load a class whose code does not verify and then read its state and its methods' bytecodes out of the machine, with `java -Xlog:class+init=info` and `jhsdb clhsdb`. The class never reaches the linked state, and its methods still hold the constant pool indices the class file carried, which is what shows that nothing was rewritten before verification ran.
- **5.19** 4c.6: run the getter of 5.16 with `-XX:-RewriteBytecodes` and the pair fusing left on, with `jhsdb clhsdb`. Nothing is fused, because the patcher that would write the fused opcode returns before writing anything, which makes the dependency between the two rewrites visible from outside.

## 6. Edge cases

### 6.1 Malformed input

The code array reaching this blueprint has already been verified, which is what makes an interpreter fast and is also what makes it fragile. The specification states the consequence in one sentence: if a constraint in an instruction's description is not satisfied at run time, the behaviour of the machine is undefined {[JVMS §6.1@SE25]}. An implementation is therefore permitted to read a local variable slot that holds a `reference` as though it held an `int`, and what happens next is not a specified error, it is whatever the machine does.

That sentence is the reason the boundary matters more here than anywhere else in this project. Every check that keeps a code array inside the region where behaviour is defined happens before this blueprint starts, and an implementation that skips one of them has not made itself lenient, it has made itself undefined. The three ways in are a verifier that is turned off, a verifier that has a hole in it, and code that arrives already inside the machine through an entry point that does not verify.

There is one shape of malformed input this blueprint does have to handle, and it is the byte that is not an opcode. Only the instructions the specification documents may appear in a code array, and the codes it reserves may not {[JVMS §4.9.1@SE25]}. HotSpot has 36 codes of its own above the last number the specification assigns, which is what section 3 is counting when it says the two sources disagree about how many opcodes there are, and none of them may appear in a class file. The measured consequence of that overlap is on [the fuzzer's page](../../docs/generated/classfile-fuzz.md): setting one byte to `0xdd`, which the specification leaves unassigned, produces a verifier message naming `fast_iaccess_0`, an instruction that no class file may contain and that a reader will not find in any published table. The error is correct and the diagnostic is a leak of the implementation's private numbering into a message about a file.

### 6.2 Resource exhaustion

The code array is bounded, and everything reachable from it is not. `code_length` is less than 65536 {[JVMS §4.7.3@SE25]}, `max_stack` and `max_locals` are each a `u2`, so one frame is bounded in every dimension before it is created and an implementation can allocate the whole of it in one step. That is the entire safety argument for eager frame allocation, and it holds for one frame only.

The unbounded thing is the number of frames. Nothing in a code array limits how deep invocation may go, and a method that calls itself reaches the end of the thread's stack rather than the end of any counter. The specification names `StackOverflowError` for it and says nothing about when it arrives, so the depth at which a conforming machine throws is a property of the machine, the platform and the frame layout of section 2, and any harness asserting on a particular depth is measuring the build it is running on.

Two smaller limits are worth naming because they are implementation limits with no counterpart in the specification. HotSpot stores the code size in a `u2` {[HOTSPOT src/hotspot/share/oops/constMethod.hpp:199@jdk-27+35]}, so a machine that chose to accept a larger array would need a different structure and not a different check. And rewriting `invokespecial` for interfaces has a capacity of its own, and a class file that exceeds it is refused with an `InternalError` saying it cannot be loaded {[HOTSPOT src/hotspot/share/interpreter/rewriter.cpp:560@jdk-27+35]}, which is a refusal of a class file that satisfies every constraint the specification states.

### 6.3 The concurrent case

The code array is not immutable, and the flag that controls this says so in its own help text {[HOTSPOT src/hotspot/share/runtime/globals.hpp:1111@jdk-27+35]}. There are two kinds of rewriting and they have completely different concurrency properties, and conflating them is the mistake this subsection exists to prevent.

The first kind happens once, at link time, before any thread can execute the method {[HOTSPOT src/hotspot/share/interpreter/rewriter.cpp:568@jdk-27+35]}. It rewrites constant pool indices into constant pool cache indices, it runs inside the class's initialization lock, and the class does not reach the linked state until it has finished, so no thread ever sees a half rewritten method. This kind needs no atomicity at all and gets its safety from ordering, which is 4c.

The second kind happens while the method is running. The template for `aload_0` reads the byte after itself and, if it is a fast field access, stores a single fused opcode over the `aload_0` {[HOTSPOT src/hotspot/cpu/aarch64/templateTable_aarch64.cpp:939@jdk-27+35]} {[HOTSPOT src/hotspot/cpu/aarch64/templateTable_aarch64.cpp:953@jdk-27+35]}. Two threads may be executing the same method while a third is patching it, and the patch is a single one byte store. That is what makes it safe, and the reason is worth spelling out because the fused instruction is not the same length as the one it is written over: `fast_iaccess_0` is four bytes and the `aload_0` it replaces is one. A thread that fetched the old byte executes `aload_0` and then the three byte field access that follows it. A thread that fetched the new one executes the four byte fused form. Both leave the frame in the same state, both advance to the same next instruction, and no thread can see a half written value because one byte is written and nothing else is touched.

An implementation is therefore required to state its own rule, and the rule this blueprint states is the checkable one: a code array may be modified while threads are executing it only if every modification is a single store of one byte, and only if the instruction sequence beginning at that byte before the store and the sequence beginning at it after the store have the same effect on the frame and end at the same index. Anything wider than that needs the threads stopped. HotSpot's second kind satisfies it, and its own guard is a flag check at the top of the patcher, so an implementation that does not want the property at all can turn the writes off {[HOTSPOT src/hotspot/cpu/aarch64/templateTable_aarch64.cpp:168@jdk-27+35]}.

One consequence of the second kind is not obvious and is the thing a reader should take away. Which fused instruction a method ends up holding depends on which path through it ran first, because the rewrite is deferred when the following opcode is a `getfield` that has not itself been rewritten yet {[HOTSPOT src/hotspot/cpu/aarch64/templateTable_aarch64.cpp:947@jdk-27+35]}. The bytes of a method in a running machine are therefore a function of its execution history, and two machines running the same program can hold different bytes for the same method and both be right.

## 7. Configuration

Nothing in section 4a is configurable. Section 4b divides into two halves, and the division is what this section is for: the representation of a method and the layout of a frame are fixed by the build, and every rewrite of a code array is behind a flag that anybody can move.

**The two rewriting flags.** `RewriteBytecodes` permits the link time rewrite and `RewriteFrequentPairs` permits the pair fusing, and both are declared as platform dependent, meaning the product has no default and each port supplies one {[HOTSPOT src/hotspot/share/runtime/globals.hpp:1111@jdk-27+35]} {[HOTSPOT src/hotspot/share/runtime/globals.hpp:1114@jdk-27+35]}. On aarch64 both are true {[HOTSPOT src/hotspot/cpu/aarch64/globals_aarch64.hpp:65@jdk-27+35]} {[HOTSPOT src/hotspot/cpu/aarch64/globals_aarch64.hpp:66@jdk-27+35]}. Neither is diagnostic, so both can be turned off on the command line without unlocking anything, and turning `RewriteBytecodes` off turns the second one off in effect as well, because the patcher every fused instruction goes through checks the first flag rather than the second. What a flag is, which builds have it, and what the platform dependent kind means is [the flag reference](../../docs/generated/flags.md).

**What turning them off changes, and what it does not.** With both off, the code array of a linked method is the code array the class file carried, which makes `javap -c` and the serviceability agent agree and makes 5.14 and 5.16 produce nothing. No observable behaviour of any conforming program changes, which is the claim this blueprint makes and 8.2 tests. Performance changes and is not this document's subject.

**Which engine runs the code.** `-Xint` and `-Xcomp` decide whether a method is interpreted or compiled, and neither one is in scope here: a compiled method has no interpreter frame, no bytecode pointer and no operand stack, and the guarantees of section 4a still hold because a compiled method is required to be indistinguishable from an interpreted one except in how long it takes. The one place the choice becomes visible to this blueprint is 5.16, because a method that was compiled early may never execute the interpreter template that would have fused its instructions.

**Agents.** A JVMTI agent that retransforms a class replaces its methods with methods built from new bytes, so the code array of a running method is not stable across a retransformation, and an implementation that caches a decoded form of it has to invalidate that cache. This is a change to the input rather than a change to the machine, and every guarantee in section 4 applies to the new bytes exactly as it applied to the old ones.

**The cached class.** A class taken from the AOT cache was rewritten when the cache was written, and rewriting it again is a state the machine asserts against rather than a case it handles {[HOTSPOT src/hotspot/share/interpreter/rewriter.cpp:570@jdk-27+35]}. An implementation with a cache of its own inherits the obligation, which is that whatever is cached has to be the post rewrite form, and that the flags in force when the cache was written have to be the flags in force when it is read.

## 8. Conformance

### 8.1 What conformance means here

An implementation conforms to this blueprint if, for every method whose code array satisfies the constraints of section 4a, executing it produces the same observable effects as any other conforming implementation, and if it performs the steps of section 3 in an order consistent with every clause in 4c. Observable means what the program can see: the values it computes, the objects it creates, the exceptions it throws, the locks it holds and the order in which other threads may see its writes. It does not mean what the machine's own diagnostic tools print.

Two limits on that obligation matter more here than in any other blueprint. The first is that it says nothing about a code array that does not satisfy 4a, because for those the specification places no obligation on the machine at all {[JVMS §6.1@SE25]}, and an implementation may return a wrong value, throw anything, or fail in a way no Java program can catch. A conformance item that asserts on the behaviour of an unverified method is therefore not a conformance item, and the one below that touches this asks a different question: whether the implementation documents where its own boundary is.

The second is that the entire contents of section 4b are unobservable by design. The code array a method holds after linking, the layout of a frame, the width of the field that stores a code size and which fused instruction an `aload_0` became are implementation state, and a conforming implementation may make every one of those different. What it may not do is let the difference reach a program, and 8.2.14 and 8.2.17 are the items that test the boundary rather than the choice.

Section 4b clauses are recorded so that a reader comparing two implementations can tell a choice from a requirement. An implementation that departs from one states which clause and what it does instead, in one line. The capstone harness reports against 8.2 and against nothing else, with an item passed when a test exists that would fail if the behaviour changed, skipped when the harness cannot construct the case, and failed otherwise.

### 8.2 Checklist

- **8.2.1** 4a.1, 4a.8: decodes a code array from index 0 by instruction length, reads multi byte operands big endian, pads `tableswitch` and `lookupswitch` operands to a four byte boundary measured from the start of the array, and ends the last instruction at `code_length - 1`.
- **8.2.2** 4a.2, 4c.2: creates one frame per invocation with its own locals, its own operand stack and its own constant pool reference, and destroys it before the invoker resumes, which is checked by walking the stack from inside a recursion.
- **8.2.3** 4a.3, 4a.10: addresses a `long` or a `double` in the local variable array by the lesser of its two indices, at both even and odd indices, and neither requires nor assumes alignment of the pair.
- **8.2.4** 4a.4, 4a.9: starts every frame with an empty operand stack and executes correctly a method whose stack reaches exactly `max_stack` on some path, including a `long` or `double` value at the top of it.
- **8.2.5** 4a.5: gives each thread its own program counter, so two threads executing the same method are at independent points in it, which is checked with two threads in one loop rather than by reading any diagnostic.
- **8.2.6** 4a.6: executes a method whose code array is one byte long and one whose code array is 65535 bytes long, and refuses a class file offering an empty one.
- **8.2.7** 4a.7: executes every opcode the specification documents and refuses, before execution, any code array containing an opcode it does not document, including a machine's own internal codes if it has any.
- **8.2.8** 4a.11: documents which of its own checks are performed at run time and which it relies on verification for, since the specification permits either and a reader cannot tell them apart by testing a machine that is correct.
- **8.2.9** 4a.12, 4c.3: releases the monitor of a `synchronized` method before an exception raised inside it becomes visible to the invoker, checked with `Thread.holdsLock` in the invoker's handler rather than after the stack has unwound further.
- **8.2.10** 4a.13: pushes the returned value onto the invoker's operand stack on normal completion and pushes nothing on abrupt completion, checked for each of the five return instructions and for a `void` method.
- **8.2.11** 4a.14: documents whether it enforces structured locking, and behaves the way it documents for a method that exits a monitor it did not enter and for one that exits two monitors in entry order.
- **8.2.12** 4b.1, 4b.2, 4b.3: documents any limit its own representation of a method imposes beyond the limits section 4a states, and imposes none that is smaller.
- **8.2.13** 4b.4, 4b.5, 4b.6: passes arguments to an invoked method so that they arrive as its first local variables in index order, whatever the direction its stacks grow, checked with a method of eight parameters of mixed widths.
- **8.2.14** 4b.7, 4b.8, 4b.12: produces identical observable behaviour for every program with each of its code rewriting options on and off, which is the item that makes rewriting an implementation detail rather than a semantic.
- **8.2.15** 4b.9, 4c.6: keeps any rewritten operand meaningful only inside the machine, so that reflection, the class file API and any agent see the constant pool index the class file carried and not the rewritten form, and performs no rewrite that depends on a structure it has not yet built.
- **8.2.16** 4b.10: loads and executes every class file that satisfies section 4a, or documents each internal limit that makes it refuse one, since a refusal here is a refusal of a legal program.
- **8.2.17** 4b.11, 4b.13, 4b.14: modifies a code array while threads execute it only by single byte stores after which the instruction sequence beginning at that byte has the same effect and the same end index as before, and reports the original instruction, not the rewritten one, through every interface a program can reach.
- **8.2.18** 4c.1: determines the length of an instruction from its opcode alone, so that no operand of any instruction is fetched before the opcode that gives it meaning.
- **8.2.19** 4c.4, 4c.5: verifies a class's methods before transforming them in any way, and makes the class available to other threads only after both have finished, so no thread can execute a partly transformed method.

## 9. Provenance

Section 3 is generated from [the instruction set page](../../docs/generated/opcodes.md), which `tools/gen_opcodes.py` builds from three sources that check each other: JVMS SE25 chapter 7, `src/hotspot/share/interpreter/bytecodes.cpp` at the pinned tag, and `java.lang.classfile.Opcode` read off the pinned JDK. It is not written here and editing it here has no effect. The counts on it come from `probes/opcodes`, over `java.base` on two platforms, and they are counts of what one compiler emitted for one module rather than facts about the instruction set.

Every clause in 4a quotes JVMS SE25 and every clause in 4b names a file and a line in `jdk-27+35`. `tools/refcheck.py` resolves both against `docs/citations.json` and fails the build when a line has moved.

Everything in this blueprint that concerns a frame's layout was read from the aarch64 port. The three clauses that name `frame_aarch64.hpp` are the ones a different port is most likely to contradict, and they are in 4b rather than in 4a for exactly that reason. Nobody has checked them against x64, and until somebody does, a reader on another architecture should treat 4b.4, 4b.5 and 4b.6 as facts about one port.

The rewriting clauses were read from the source and not demonstrated. The one measured fact here is the fuzzer's, that breaking a byte to `0xdd` produces a message naming `fast_iaccess_0`, which is what proves the internal opcode numbering is reachable from a diagnostic. Nobody has yet watched an `aload_0` turn into a fused instruction in a running process, which is item 5.16 and is the observation this blueprint most needs.

Two things are open. No lesson has been written against this blueprint, so the `lessons` field is empty rather than aspirational. And section 8.2 has an item, 8.2.14, that asserts a property of every program rather than of one input, which no finite harness can establish, so it will be reported as a bounded check over a fixed corpus and the bound will be stated where it runs.
