## 1. Scope

This blueprint specifies the constant pool: the table that occupies more than half of a typical class file, the seventeen kinds of entry it may hold, the constraints between entries, the checks a machine performs while reading them, and what the tag byte becomes once the table is in memory and entries start to resolve. An implementation built from this document can take the bytes between `constant_pool_count` and `access_flags`, produce a table another component can index, and refuse the ones a conforming machine refuses with the error it would produce.

It covers three things a reader is likely to expect somewhere else. The first is that a tag is legal at two different version thresholds and they are different numbers: whether a kind may appear in a pool at all and whether `ldc` may push it are two questions, the specification answers them in two tables, and 4a.3 and 4a.4 keep them apart. The second is the tag byte after parsing, which HotSpot uses as a small state machine with eight values no class file may contain, and which is the only reason a failed resolution can be remembered. The third is what a `CONSTANT_Utf8_info` is for, which the format does not encode at all and which nothing but the entry pointing at it can answer.

It deliberately excludes five things. The surrounding structure, the header, the fields, the methods and the attribute tables belong to BP-CLASSFILE, and so does the decision about which error class a malformed file produces. The instructions that index the pool belong to BP-BYTECODE. What the verifier does with an entry's type belongs to BP-VERIFY, and the frames that name pool entries belong to BP-STACKMAP. The act of resolving a symbolic reference, meaning what it means to find the class or the method a `CONSTANT_Class` or a `CONSTANT_Methodref` names, belongs to BP-LOAD. This document specifies when an entry may change state and what a reader of a changing entry is entitled to see, and not what work the change does.

Two further exclusions look as though they belong here. The `BootstrapMethods` attribute is an attribute rather than a pool entry, so its structure is BP-CLASSFILE's, and the only part of it in scope is 4a.10, that two entry kinds index into it and a class carrying either has to have one. And what a compiler chooses to put in a pool is out of scope: 14,911 class files were measured to write section 2 and none of the numbers in it is a requirement on anybody.

### 2.2 Why constant_pool_count is one more than the number of entries

There is no entry at index 0, and a `CONSTANT_Long` or a `CONSTANT_Double` takes two slots with nothing usable in the second one. Both of those are in the count, and the arithmetic is checkable rather than quotable: over the scanned code, 2,139,699 entries plus 14,951 second slots plus 14,911 missing slot zeroes is 2,169,561, and the sum of every `constant_pool_count` field is 2,169,561. This generator refuses to write the page if those two numbers differ.

The largest pool in the scanned code has 6,022 slots and belongs to `sun/util/resources/cldr/LocaleNames_en`. The 16 bit count is a real limit rather than a theoretical one: a class needs 59,513 more entries than that one has before it stops being expressible, and a generated class or a very large switch gets there.

The version column is the disagreement worth knowing about. Some of them are structure rather than value, and `CONSTANT_InvokeDynamic` is the interesting exclusion, because it names a call site rather than a constant and `invokedynamic` is the only instruction that may refer to one.

### 2.4 What HotSpot puts in the tag byte

The tag byte in a class file has seventeen legal values. The tag byte in memory has more, because HotSpot reuses the field to record where the entry is in its own life cycle. A class is parsed with its class references unresolved, they become resolved as the code that needs them runs, and a resolution that threw keeps the exception rather than being retried. All three of those states are the same byte.

| value | name | what HotSpot calls it | what it is |
|---:|---|---|---|
| 0 | `Invalid` | `Invalid index` | For bad value initialization |
| 100 | `UnresolvedClass` | `Unresolved Class` | Temporary tag until actual use |
| 101 | `ClassIndex` | `Unresolved Class Index` | Temporary tag while constructing constant pool |
| 102 | `StringIndex` | `Unresolved String Index` | Temporary tag while constructing constant pool |
| 103 | `UnresolvedClassInError` | `Unresolved Class Error` | Error tag due to resolution error |
| 104 | `MethodHandleInError` | `MethodHandle Error` | Error tag due to resolution error |
| 105 | `MethodTypeInError` | `MethodType Error` | Error tag due to resolution error |
| 106 | `DynamicInError` | `Dynamic Error` | Error tag due to resolution error |

Every one of those except `Invalid` is at 100 or above and none is past 106, and the format's own tags stop at 20, so a value HotSpot invented can never be mistaken for a tag a class file may contain. `Invalid` is the value a freshly constructed tag has, which is how a partly built pool is distinguishable from a finished one.

Four kinds can fail to resolve, and each one has its own error tag rather than a shared one, so the failure that is remembered is a failure of the right kind: `Dynamic` becomes `DynamicInError`, `MethodHandle` becomes `MethodHandleInError`, `MethodType` becomes `MethodTypeInError`, `UnresolvedClass` becomes `UnresolvedClassInError`. A second attempt to use the entry throws the same exception it threw the first time rather than running the resolution again, which is the behaviour the specification requires and the reason the tag has to carry the error at all.

The predicates that accept more than one tag are the ones worth reading, because each is a question the rest of the VM asks about an entry, and together they are the vocabulary HotSpot has for talking about a pool.

| `is_field_or_method` | `Fieldref`, `Methodref`, `InterfaceMethodref` |
| `is_in_error` | `UnresolvedClassInError`, `MethodHandleInError`, `MethodTypeInError`, `DynamicInError` |

The compiler that built the scanned code emits the first and not the second, which is worth knowing before reading a class file looking for one.

### 2.7 The same constant twice

A pool is supposed to be a set. Nothing in the format requires it to be, and a class file with two entries that mean exactly the same thing is legal, loads, and runs. In the scanned code 89 classes hold at least one repeat, 127 entries in total, which is <0.01% of the pool. The probe finds them by rendering each entry to the thing it means and looking for two that render the same, which is a different test from comparing bytes.

| tag | kind | repeats | for example |
|---:|---|---:|---|
| 10 | `CONSTANT_Methodref` | 28 | `java/lang/invoke/VarHandle.weakCompareAndSet:(Ljava/util/concurrent/ConcurrentLinkedDeque;Ljava/util/concurrent/ConcurrentLinkedDeque$Node;Ljava/util/concurrent/ConcurrentLinkedDeque$Node;)Z` in `java/util/concurrent/ConcurrentLinkedDeque` |
| 11 | `CONSTANT_InterfaceMethodref` | 99 | `java/util/List.toString:()Ljava/lang/String;` in `apple/security/KeychainStore` |

Every repeat in the scanned code is one of two things, and both are the compiler being unable to see that two references are the same. The first is a method `java.lang.Object` declares, called on a receiver whose static type is an interface: `equals`, `getClass`, `hashCode`, `toString`. Those are 99 of the repeats. An interface does not declare them, so each call site names them on the interface it is calling through, and two different interfaces in one class produce two entries that a reader would call the same call.

The second is a signature polymorphic call, on `java/lang/invoke/VarHandle`, which is 28 of them. A signature polymorphic method has whatever descriptor the call site says it has, so two call sites with the same descriptor produce two entries only when something else about them differs, and the compiler does not look. This is the case where the duplicate is arguably load bearing: the descriptor is the argument.

The scanned images are not identical, and the repeats say so: `apple/security/KeychainStore` is only in `osx-arm64`. That is a platform specific class rather than a platform specific compiler, and it is the reason the counts here are sums over environments rather than one environment's answer.

## 3. Operations

There are two public operations. The first turns bytes into a table and is finished before the class exists. The second is how everything else in the machine touches that table for the rest of the class's life, and it exists as an operation rather than as a field access because the answer it gives changes over time and the rules for that change are most of section 4.

**read(bytes, version) returns a pool, or throws.** `bytes` is positioned at `constant_pool_count` and has a known end. `version` is the major and minor version already read by the enclosing parse, and it is an input rather than a constant because which entry kinds are legal is a function of it. The result is a table indexed from 1 whose entries are internally consistent, or a `ClassFormatError`. `read` consumes exactly the bytes the pool occupies and leaves the stream positioned at `access_flags`, which is what makes it callable as a step of BP-CLASSFILE's `derive` rather than as a parser of its own.

**tag_at(pool, index) returns the kind an entry currently has.** The kind is not fixed for the life of the pool. An entry that arrived as a `CONSTANT_Class` may be unresolved, resolved or in error, and an implementation is free to represent those as three states of one entry or as three separate fields, but it is not free to let a reader see a state that never existed. `tag_at` is the operation every clause about ordering and concurrency is written against.

The steps of `read` run in the order given. Each may assume every earlier step completed and may assume nothing about a later one.

**3.1 read the count.** Consume two bytes. A count of zero is refused, because the table has `count - 1` entries and there is no such thing as a table of minus one. A count of one is a pool with no entries and is legal.

**3.2 read the entries.** For each index from 1 up to `count - 1`, consume one tag byte, decide the structure from it, and consume exactly the bytes that structure occupies. Fails with `ClassFormatError` on a tag no version defines, on a tag this version does not allow, or on an entry that runs off the end. No index inside any entry is followed, checked or dereferenced in this step.

**3.3 skip the second slot.** After a `CONSTANT_Long_info` or a `CONSTANT_Double_info`, advance the index by one more. The skipped index counts against the declared count and holds nothing, and an implementation records it as a state distinguishable from every legal entry kind, because a later index that names it is an error rather than a lookup that quietly succeeds. Fails if the skipped index would be past the end, since an eight byte constant cannot be the last entry.

**3.4 stop early if the pool cannot be cross checked.** If step 3.2 met a `CONSTANT_Module` or a `CONSTANT_Package` and recorded it rather than failing, `read` returns here with the pool marked. The enclosing parse needs the access flags to decide which error this is, and the second pass would fail first on something less specific.

**3.5 check every index.** For each entry in turn, resolve each index it holds against the table, and check that the entry it names is of the kind this entry requires: a `CONSTANT_Class` names a Utf8, a `CONSTANT_Fieldref` names a class and a `NameAndType`, a `CONSTANT_MethodHandle`'s `reference_index` names one of a small set decided by its `reference_kind`. Fails with `ClassFormatError` on an index out of range, on an index naming the wrong kind, and on an index naming the second slot of an eight byte constant. This is a separate pass from 3.2 because an entry may name an entry that comes after it, and every class file a compiler has ever produced contains such a reference.

**3.6 check the contents that need a second entry to read.** A name is an unqualified name or `<init>` or `<clinit>` depending on the descriptor its `NameAndType` pairs it with, and a descriptor is well formed or it is not, so both checks need the Utf8 the index names and therefore cannot happen in 3.2. Fails with `ClassFormatError`.

**3.7 rewrite what the implementation stores.** An implementation is permitted to replace an entry's parsed form with a form of its own, and this step exists so section 4 can say when. What it may not do is change which kind an entry is, or make an index that was valid in 3.5 invalid afterwards.

Steps 3.1 to 3.7 are the pool's share of format checking as the specification uses the term {[JVMS §4.8@SE25]}. They establish that the table is internally consistent and they establish nothing at all about whether anything it names exists. A `CONSTANT_Class` naming a class that was deleted last year passes every one of them.

The steps of `tag_at` are not sequential and are stated as three obligations.

**3.8 an entry has one kind at a time.** Every read returns a kind the entry has actually been in, and never a mixture of two, whatever the implementation stores alongside the kind.

**3.9 the kind is what publishes the entry.** A reader that observes an entry in a new state observes everything the transition into that state wrote. This is the obligation that makes the tag a memory barrier rather than a byte.

**3.10 the transition into an error state happens once.** Whichever thread records the failure, every later read sees the error state, and no read after that sees the entry unresolved again.

## 4. Guarantees

### 4a. What the specification mandates

- **4a.1** Every entry begins with a one byte tag, the tag alone decides the structure of the entry and therefore how many bytes follow it, and an entry whose tag is not one of the defined values cannot be skipped because its length is unknown {[JVMS §4.4@SE25]}.
- **4a.2** A `CONSTANT_Long_info` or a `CONSTANT_Double_info` occupies two consecutive entries in the table, the next usable entry follows at the index after next, and the index in between is unusable and must be considered invalid {[JVMS §4.4.5@SE25]}.
- **4a.3** Whether a tag may appear in a pool at all depends on the class file version: `CONSTANT_MethodHandle`, `CONSTANT_MethodType` and `CONSTANT_InvokeDynamic` from 51.0, `CONSTANT_Module` and `CONSTANT_Package` from 53.0, and `CONSTANT_Dynamic` from 55.0 {[JVMS §4.4@SE25]}.
- **4a.4** Whether `ldc`, `ldc_w` or `ldc2_w` may push an entry depends on the class file version as well, and the thresholds are not the same ones: `CONSTANT_Class` becomes loadable at 49.0, `CONSTANT_MethodHandle` and `CONSTANT_MethodType` at 51.0, `CONSTANT_Dynamic` at 55.0, and the five that were loadable from the beginning at 45.3, so a tag that may legally sit in a pool is not thereby a tag an instruction may load {[JVMS §4.4@SE25]}.
- **4a.5** The `length` of a `CONSTANT_Utf8_info` is a count of bytes rather than of characters and is two bytes wide, so the longest representable string is 65535 bytes of modified UTF-8 and a string of 65535 characters may have no representation at all {[JVMS §4.4.7@SE25]}.
- **4a.6** Nothing in a `CONSTANT_Utf8_info` says what it is for, and a class name, a field descriptor, an attribute name and the text of a string literal are the same structure, so an implementation determines the role of a string from the entry or attribute that names it and never from the string itself {[JVMS §4.4.7@SE25]}.
- **4a.7** A `CONSTANT_Fieldref_info` names a class or interface type that has the field, a `CONSTANT_Methodref_info` names a class type and not an interface type, and a `CONSTANT_InterfaceMethodref_info` names an interface type and not a class type, which is why the same reference to the same member is two different tags depending on what declares it {[JVMS §4.4.2@SE25]}.
- **4a.8** A `CONSTANT_NameAndType_info` pairs a name with a descriptor and the descriptor decides which names are legal: with a field descriptor the name is an unqualified name, and with a method descriptor it is an unqualified name or one of the two special names, so neither half can be checked without reading the other {[JVMS §4.4.6@SE25]}.
- **4a.9** A `CONSTANT_MethodHandle_info` has a `reference_kind` in the range 1 to 9, and the kind decides which entry kinds `reference_index` may name, with kinds 6 and 7 permitted to name a `CONSTANT_InterfaceMethodref_info` only from class file version 52.0 and kind 8 requiring the name to be `<init>` {[JVMS §4.4.8@SE25]}.
- **4a.10** A `CONSTANT_Dynamic_info` or a `CONSTANT_InvokeDynamic_info` holds an index into the `BootstrapMethods` attribute rather than into the constant pool, so it is the one entry kind whose first field is not a pool index and a class containing either has to carry that attribute {[JVMS §4.4.10@SE25]}.
- **4a.11** The pool is not required to be free of duplicates, so two entries may denote the same constant and an implementation must accept a class file in which they do, which means entry identity is never constant identity {[JVMS §4.4@SE25]}.
- **4a.12** A `CONSTANT_Module_info` or a `CONSTANT_Package_info` may appear only in the class file of a module declaration, and neither may be the target of any index from any other entry {[JVMS §4.4.11@SE25]}.
- **4a.13** The run time constant pool is derived from the class file pool at class creation, its symbolic references are resolved on first use rather than at creation, and an unresolved reference is not an error until something needs it {[JVMS §5.1@SE25]}.
- **4a.14** If resolution of a symbolic reference fails, every later attempt to resolve that same reference fails with an error of the same class as the first one, and the reference is never re-resolved {[JVMS §5.4.3@SE25]}.

### 4b. What HotSpot chose

- **4b.1** The tag byte in memory has eight values no class file may contain, all of them at 100 or above while the format stops at 20, so an implementation tag and a format tag cannot collide and the same byte can carry both {[HOTSPOT src/hotspot/share/utilities/constantTag.hpp:40@jdk-27+35]}.
- **4b.2** Four entry kinds can fail to resolve and each gets its own error tag rather than one shared error state, so an entry that failed still says which kind it was and therefore what the second attempt has to throw {[HOTSPOT src/hotspot/share/utilities/constantTag.cpp:86@jdk-27+35]}.
- **4b.3** Which entries are loadable is answered by a comparison against the tag alone, with no version anywhere in it, and the answer includes the implementation tag for an unresolved class as well as the format tags {[HOTSPOT src/hotspot/share/utilities/constantTag.hpp:115@jdk-27+35]}.
- **4b.4** The type checking verifier checks `ldc` against a fixed mask of seven tags built without reference to the class file version, on the stated grounds that the parser has already dealt with the method handle kinds {[HOTSPOT src/hotspot/share/classfile/verifier.cpp:2144@jdk-27+35]}.
- **4b.5** The only code in the machine that ties loadability to the class file version is the inference verifier written in C, which adds `CONSTANT_Class` to the loadable set at major version 49 and the two method handle kinds at 51 {[HOTSPOT src/java.base/share/native/libverify/check_code.c:1237@jdk-27+35]} {[HOTSPOT src/java.base/share/native/libverify/check_code.c:246@jdk-27+35]}.
- **4b.6** That verifier is reached only for a class whose major version is below 50, so the version dependent rule is enforced for exactly the versions where it differs from the version independent one, and the arrangement is correct because 49 is less than 50 rather than because anything checks that it is {[HOTSPOT src/hotspot/share/classfile/verifier.cpp:219@jdk-27+35]}.
- **4b.7** A tag the version does not allow is refused while the entry is being read, with one message that names the tag number and the class file for both the method handle threshold and the dynamic constant one {[HOTSPOT src/hotspot/share/classfile/classFileParser.cpp:230@jdk-27+35]} {[HOTSPOT src/hotspot/share/classfile/classFileParser.cpp:253@jdk-27+35]}.
- **4b.8** A `CONSTANT_Module` or a `CONSTANT_Package` at a version that allows the tag is not refused where it is found: it is recorded, its two bytes are consumed, and parsing continues so that the access flags can be read and the failure reported as a missing class rather than as a malformed one {[HOTSPOT src/hotspot/share/classfile/classFileParser.cpp:370@jdk-27+35]}.
- **4b.9** Any other tag ends the parse where it stands, with a message that gives the tag as a decimal number and does not give the index it was found at {[HOTSPOT src/hotspot/share/classfile/classFileParser.cpp:378@jdk-27+35]}.
- **4b.10** The second slot of an eight byte constant is left holding the invalid tag and the second pass checks that it is still invalid, which catches a pool whose entries overlap, and the message names the second index rather than the first one {[HOTSPOT src/hotspot/share/classfile/classFileParser.cpp:469@jdk-27+35]}.
- **4b.11** An eight byte constant at the last index is refused by a bounds check written as part of reading the entry rather than by the loop, because the loop is about to advance past the end and would not notice {[HOTSPOT src/hotspot/share/classfile/classFileParser.cpp:298@jdk-27+35]}.
- **4b.12** Whether the bytes of a `CONSTANT_Utf8_info` are checked for modified UTF-8 legality at all is decided per class by the same setting that decides the rest of format checking, so a class file with a zero byte inside a string is refused from one loader and accepted from another {[HOTSPOT src/hotspot/share/classfile/classFileParser.cpp:337@jdk-27+35]}.
- **4b.13** Every `CONSTANT_Utf8_info` becomes an interned `Symbol` in a table shared by every class in the machine, so the pool stores a pointer rather than the bytes and two classes with the same string share one copy of it {[HOTSPOT src/hotspot/share/classfile/classFileParser.cpp:342@jdk-27+35]}.
- **4b.14** The cross index checks on member references and on `NameAndType` entries are conditional on format checking as well, so an index that names an entry of the wrong kind is an error for some loaders and not for others {[HOTSPOT src/hotspot/share/classfile/classFileParser.cpp:446@jdk-27+35]} {[HOTSPOT src/hotspot/share/classfile/classFileParser.cpp:476@jdk-27+35]}.
- **4b.15** The version condition on method handle reference kinds 6 and 7 is enforced, and the message it fails with says that the target is not a method and never mentions a version, so the one error a reader is most likely to meet from a class file compiled for an older target names the wrong cause {[HOTSPOT src/hotspot/share/classfile/classFileParser.cpp:542@jdk-27+35]}.
- **4b.16** A `reference_kind` outside 1 to 9 ends the parse with a message that does give the index, which makes it the one pool error in this list whose message locates itself {[HOTSPOT src/hotspot/share/classfile/classFileParser.cpp:555@jdk-27+35]}.
- **4b.17** A `CONSTANT_Class` and a `CONSTANT_String` are stored under implementation tags during the first pass and rewritten in the second, so an entry that a reader would call resolved has been through two internal kinds before the class exists {[HOTSPOT src/hotspot/share/classfile/classFileParser.cpp:499@jdk-27+35]} {[HOTSPOT src/hotspot/share/classfile/classFileParser.cpp:508@jdk-27+35]}.
- **4b.18** Every read of a tag is an acquire load and every write of one is a release store, which is what makes the tag the thing that publishes the entry it describes rather than a byte beside it {[HOTSPOT src/hotspot/share/oops/constantPool.hpp:385@jdk-27+35]} {[HOTSPOT src/hotspot/share/oops/constantPool.hpp:130@jdk-27+35]}.
- **4b.19** The error tag is installed with a compare and swap rather than a store, and a thread that loses that race to a thread which resolved the entry successfully discards its own pending exception and uses the resolved class, so two threads reaching the same failing entry can get two different outcomes {[HOTSPOT src/hotspot/share/oops/constantPool.cpp:1043@jdk-27+35]} {[HOTSPOT src/hotspot/share/oops/constantPool.cpp:1050@jdk-27+35]}.

### 4c. Ordering obligations

- **4c.1** The class file version is known before any entry is read, because the tag alone decides the length of an entry and which tags are legal is a function of the version {[JVMS §4.1@SE25]}.
- **4c.2** Every entry is read before any index is resolved, because an entry may name an entry that comes after it, and an implementation that checks indices as it reads will refuse class files that every compiler produces {[HOTSPOT src/hotspot/share/classfile/classFileParser.cpp:434@jdk-27+35]}.
- **4c.3** The error for an unrecognised tag is raised in the first pass and stops the parse there, while the error for a module or package entry is deferred past the access flags, so the second pass runs only when the first found nothing it had to hold back {[HOTSPOT src/hotspot/share/classfile/classFileParser.cpp:424@jdk-27+35]}.
- **4c.4** Nothing in the pool is resolved while the class file is being read, so a class whose pool names a class that does not exist is created successfully and fails later or not at all {[JVMS §5.1@SE25]}.
- **4c.5** The contents of an entry are written before the tag that describes them, so a reader that sees a new tag sees a complete entry and never a half filled one {[HOTSPOT src/hotspot/share/oops/constantPool.hpp:284@jdk-27+35]}.
- **4c.6** A use of an entry already in an error state throws before any attempt is made to resolve it again, which is what makes the failure sticky rather than merely recorded {[HOTSPOT src/hotspot/share/oops/constantPool.cpp:648@jdk-27+35]}.

## 5. Observation

Every item below is a procedure rather than a result. The tool named in it is the one that answers the question with the least machinery, and where two tools disagree that disagreement is itself the observation.

Five tools carry this section. `java.lang.classfile`, on the pinned JDK, builds a pool entry by entry from a Java program, which is the only practical way to produce a pool that a compiler would never emit. `javap -v` prints the pool as the platform's own reader understands it, numbered, which is what makes an index argument settleable. `probes/classfile-fuzz` breaks one valid class file and records where the machine stopped and in what words. `jhsdb clhsdb` reads the tag byte of a live pool, which is the only way to see the eight values no class file may contain. And `xxd` is what settles an argument about a byte, because every other tool on this list is showing an interpretation.

- **5.1** 4a.1, 4b.9: overwrite one entry's tag byte with 13, then with 21, then with 200, and load the file, with `probes/classfile-fuzz` and `xxd`. All three give one message, and the message gives the tag in decimal and does not say which index it was at, so the same three failures are indistinguishable in a log.
- **5.2** 4a.2, 4b.10, 4b.11: build a pool holding a `CONSTANT_Long_info`, then point a later entry's index at the slot after it, then move the long to the last index, with `java.lang.classfile` and `javap -v`. `javap` numbers the entry after a long as the index two further on, and the two malformed files give two different messages, one of which names an index that holds nothing.
- **5.3** 4a.3, 4b.7, 4b.8: put a `CONSTANT_MethodHandle_info` into a class file at major version 50, a `CONSTANT_Dynamic_info` into one at 54, and a `CONSTANT_Module_info` into an ordinary class at 53, with `java.lang.classfile` and `xxd`. The first two give the same sentence with a different number in it. The third gives an error about the class rather than about the file, which is the deferral of 4b.8 visible from outside.
- **5.4** 4a.4, 4b.3, 4b.4, 4b.5, 4b.6: build a class at major version 48 whose code does `ldc` of a `CONSTANT_Class`, load it, then build the same class at 50, with `java.lang.classfile` and `java -Xverify:all`. The specification forbids the first and permits the second, one of the two verifiers enforces that and the other does not, and which one runs is decided by the same version field. This is the observation the rest of the section is arranged around and it is written up on [the probe's page](../../docs/probes/constpool.md).
- **5.5** 4a.5, 4b.12: write a `CONSTANT_Utf8_info` of 65535 bytes, then one containing a zero byte, then one containing `0xf8`, and load each from an application loader and again from the boot loader, with `probes/classfile-fuzz` and `java -Xbootclasspath/a`. The long one is accepted everywhere. The other two are accepted in one configuration and refused in the other, and the bytes are identical.
- **5.6** 4a.6: walk every `CONSTANT_Utf8_info` in a module and record, for each, which entry or attribute names it, with `probes/constpool/Pool.java`. Thirty roles account for all 1,216,114 entries of `java.base`, and two of the thirty are attributes no specification defines, so a checklist built from the format alone ends with strings it cannot name.
- **5.7** 4a.7, 4b.14: point a `CONSTANT_Methodref_info` at a `CONSTANT_Class_info` naming an interface, then point its class index at a `CONSTANT_Utf8_info`, and load both from an application loader and from the boot loader, with `java.lang.classfile` and `java -Xbootclasspath/a`. The second file is a `ClassFormatError` from one loader and a class from the other.
- **5.8** 4a.8: build a `CONSTANT_NameAndType_info` naming `<init>` with a field descriptor, then one naming `<clinit>` with a method descriptor taking arguments, with `java.lang.classfile` and `javap -v`. Neither half of the pair is wrong on its own, which is why 3.6 is a separate step.
- **5.9** 4a.9, 4b.15, 4b.16: build a `CONSTANT_MethodHandle_info` of each reference kind from 0 to 10, and separately give kind 6 an interface target at major version 51 and at 52, with `java.lang.classfile` and `javap -v`. Kind 0 and kind 10 give a message naming the index. The version dependent pair gives a message saying the target is not a method, which is the one wording in this list that names the wrong cause.
- **5.10** 4a.10: build a class containing a `CONSTANT_InvokeDynamic_info` and remove the `BootstrapMethods` attribute, then leave the attribute and raise the entry's index past its end, with `java.lang.classfile`. Both are refused and neither error mentions the constant pool, because the index in that entry is the one index in a pool entry that does not point into the pool.
- **5.11** 4a.11: render every entry of every class in a module to the constant it denotes and compare the renderings rather than the bytes, with `probes/constpool/run.py`. 127 entries in 89 class files repeat a constant the same pool already holds, every one of those classes loads, and comparing bytes would have found none of them because the entries hold different indices.
- **5.12** 4a.12: build a `module-info` and read its pool, then copy its `CONSTANT_Module_info` into an ordinary class, then point a `CONSTANT_Class_info` at a `CONSTANT_Package_info`, with `javap -v` and `java.lang.classfile`. The first is legal and the other two are not, and the third is the one an implementation is most likely to allow by accident.
- **5.13** 4a.13, 4c.4: compile a class referring to a second class, delete the second class, and load the first, with `jshell` and `java -Xlog:class+resolve=debug`. The class is created, the log shows nothing resolved, and the failure arrives when a method that uses the reference is called and not before.
- **5.14** 4a.14, 4b.2, 4c.6: call the failing method of 5.13 twice and catch both throwables, then compare their classes and their messages, with `jshell`. The second is an error of the same class as the first and its stack trace is shorter, because nothing was re-resolved to produce it.
- **5.15** 4b.1, 4b.17: attach to a running machine and print the tag byte of a `CONSTANT_Class_info` before and after the class it names has been used, with `jhsdb clhsdb`. The value moves between numbers no class file may contain, and the entries a class file said were `CONSTANT_Class_info` were never that tag in memory at any point.
- **5.16** 4b.13: load two unrelated classes that both contain the string `toString`, and count the entries in the symbol table before and after each, with `jcmd` and `java -XX:+UnlockDiagnosticVMOptions`. The second class adds fewer symbols than it has distinct strings, which is the sharing in 4b.13 measured rather than asserted.
- **5.17** 4b.18, 4b.19, 4c.5: unobservable. A tag read that is missing its acquire and a tag write that is missing its release differ from correct ones only on a machine that reorders them, and the compare and swap in 4b.19 is a race whose two outcomes are both permitted, so the only instrument that would settle either is a `jcstress` test on weakly ordered hardware, which is recorded in section 9 as not yet run.
- **5.18** 4c.1: take one class file containing a `CONSTANT_MethodHandle_info` and write its major version to 50 and then to 51, changing nothing else, with `xxd` and `probes/classfile-fuzz`. Two bytes decide whether the same table is a pool or an error, which is why the version cannot be read after the entries.
- **5.19** 4c.2: print the pool of any class a compiler produced and find an entry whose index is greater than its own, with `javap -v`. Every class file has one, so an implementation that checks indices during the first pass fails on the first real input it is given.
- **5.20** 4c.3: build a class file that has both a tag no version defines and `ACC_MODULE` set, then one that has a `CONSTANT_Module_info` and `ACC_MODULE` set, with `java.lang.classfile`. The first fails as a malformed file and the second as a missing class, so the deferral is visible only when the two failures are in the same file.

## 6. Edge cases

### 6.1 Malformed input

The pool is the part of a class file most worth attacking, because it is the part every later structure indexes into. A field, a method, an attribute and an instruction all reach their names and their types through a pool index, so an index that is out of range, or in range and pointing at the wrong kind of entry, is a way to make a later reader believe something that is not there. An implementation is required to establish, before anything else reads the table, that every index an entry holds is in range and names an entry of the kind that entry requires.

Four shapes of malformed pool behave differently and an implementation has to handle all four. A tag the version does not allow is caught while the entry is being read, because the tag decides how many bytes follow and there is nothing else to do with it. An index out of range is caught in a second pass, because the entry it names may not have been read yet. An index in range that names the wrong kind is caught in the same second pass and is the one an implementation is most likely to skip, because it costs a table lookup per index rather than a comparison. And an index that names the second slot of a `CONSTANT_Long_info` is in range, names an entry that exists in the count, and names nothing at all.

That last one is why 4b.9 exists. HotSpot leaves the second slot at tag zero and then checks in the second pass that it is still zero, which catches the case where the file declared an eight byte constant near the end of the pool and the entry that followed was written into the slot that should not exist. The message names the second index rather than the first, so a person reading it is looking one entry past the one that is wrong.

Half of the cross index checking is conditional. Whether the member reference and `NameAndType` checks run at all is decided per class from the defining loader, exactly as it is for the rest of format checking {[HOTSPOT src/hotspot/share/classfile/classFileParser.cpp:446@jdk-27+35]}, so a class file whose `CONSTANT_Methodref` points its class index at a `CONSTANT_Utf8_info` is refused when an application loader defines it and is not refused when the boot loader does. An implementation is free to make the same choice and is not free to make it silently, which is what 8.2.12 asks for.

An implementation is not required to reject a pool that is redundant. 127 entries in 89 class files of `java.base` repeat a constant the same pool already holds, and every one of those files loads and runs. A reader who takes the pool for a set of distinct constants has an assumption the format never made, and the two families that produce the duplicates, an `Object` method named through two different interfaces and two `VarHandle` call sites with the same descriptor, are both a compiler unable to see that two references mean the same thing rather than a compiler being careless.

### 6.2 Resource exhaustion

The pool has one bound and it is the two byte count, so a class file may declare at most 65535 entries and the table an implementation allocates on that count is bounded whatever else the file says {[JVMS §4.11@SE25]}. That is the whole of the safety argument for allocating eagerly, and it is the same argument BP-CLASSFILE makes for the pool's own allocation.

The bound on the table is not a bound on the bytes. Every `CONSTANT_Utf8_info` carries its own two byte length, so 65535 entries of 65535 bytes is a pool of about four gigabytes, and an implementation that trusts the count and streams the entries will meet the end of the file long before it meets a limit of its own. The limit that actually stops this is the length of the input, which is BP-CLASSFILE's, and an implementation that reads a pool from something other than a bounded buffer has no limit at all.

The strings do not stay inside the class. Every `CONSTANT_Utf8_info` becomes an interned `Symbol` in a table shared by every class the machine has loaded {[HOTSPOT src/hotspot/share/classfile/classFileParser.cpp:342@jdk-27+35]}, so the memory a pool costs is not proportional to the pool: a class whose strings are all already present costs almost nothing, and a class of 65535 distinct strings adds 65535 entries to a machine wide structure. Over `java.base` this is worth a large factor, 2,675,920 uses of a Utf8 entry against 1,216,114 distinct entries before interning across classes is counted at all.

An implementation that shares strings this way inherits an obligation it did not have before, which is that the sharing has to be invisible. Two classes that hold the same string are not thereby related, and a machine that lets one of them observe how many other classes hold it has leaked something about the rest of the process.

### 6.3 The concurrent case

Reading a class file is a pure function of the bytes and holds no concurrency. Everything in this section is about the pool after it exists, where entries change state under threads that are all entitled to use them, and the tag byte is the only thing that says which state an entry is in.

The tag is therefore a publication mechanism and has to be treated as one. HotSpot reads it with an acquire load and writes it with a release store {[HOTSPOT src/hotspot/share/oops/constantPool.hpp:385@jdk-27+35]} {[HOTSPOT src/hotspot/share/oops/constantPool.hpp:130@jdk-27+35]}, so the writes that fill an entry in are ordered before the write that says the entry is filled in, and a thread that sees the new tag sees the contents. An implementation that stores the tag with an ordinary write has a race that will reproduce on a weakly ordered machine and not on a strongly ordered one, which is the worst way for a defect of this kind to be distributed.

Two threads resolving the same entry both do the work, and this is deliberate. The specification permits resolution to be attempted more than once and requires only that the outcome be consistent, so an implementation is not obliged to hold a lock across the resolution of one entry, and holding one across an operation that can run arbitrary user code is a way to build a deadlock.

Where that becomes visible is failure. When resolution throws, the error tag is installed with a compare and swap rather than a store {[HOTSPOT src/hotspot/share/oops/constantPool.cpp:1043@jdk-27+35]}, and a thread that loses that race to a thread which resolved the entry successfully discards its own pending exception and uses the resolved class {[HOTSPOT src/hotspot/share/oops/constantPool.cpp:1050@jdk-27+35]}. Two threads can therefore reach the same entry, one throws and one does not, and which is which is not determined by anything in the program. An implementation is required to make the failure sticky once it is recorded and is not required to make it deterministic when it is being recorded, and those are two different sentences that a checklist has to keep apart.

Once the error tag is in place the entry is finished. Every later use throws an error of the same class as the first one {[HOTSPOT src/hotspot/share/oops/constantPool.cpp:648@jdk-27+35]}, and this is the requirement of 4a.13 implemented in one byte. It is also why four kinds have four separate error tags rather than one shared one, because the entry still has to say what it was in order to say what the second attempt should throw.

## 7. Configuration

Nothing in section 4a is configurable and a good deal of 4b is. The clauses this section exists for are the conditional ones, because a check that runs for some classes and not others is not one guarantee with a footnote, it is two behaviours, and an implementation that documents only the stronger of them has documented the case its users are not in.

**How much of the pool is checked at all.** `BytecodeVerificationLocal` is off by default and `BytecodeVerificationRemote` is on, and the pair decides per class, from the defining loader, whether the checks marked conditional in 4b run {[HOTSPOT src/hotspot/share/runtime/globals.hpp:455@jdk-27+35]} {[HOTSPOT src/hotspot/share/runtime/globals.hpp:458@jdk-27+35]}. Three things in this blueprint are on that switch: the modified UTF-8 legality of a `CONSTANT_Utf8_info`, the kind check on a member reference's two indices, and the kind check on a `NameAndType`. A class loaded by the boot loader in a default configuration therefore gets its pool read but not cross checked, and the class that results is one whose indices point wherever the file said.

**What is not on that switch.** The tag itself, the version conditions on which tags may appear, the bounds check on an eight byte constant's second slot and the reference kind range are checked for every class in every configuration. The dividing line is not obvious from the source and it is worth stating in one sentence: a check that needs only the entry in front of it is unconditional, and a check that needs a second entry is not.

**Which errors an agent can create.** A JVMTI agent registered for the class file load hook forces checking to full for every class it can see, which is BP-CLASSFILE's 4b.7 and applies here without change. A pool that has loaded in production for years can become a `ClassFormatError` in a profiling run, and the three conditional checks above are the ones it will fail.

**The shared symbol table.** 4b.13 is not configurable and the size of what it shares is. `-XX:+UnlockDiagnosticVMOptions` makes the table readable through `jcmd`, which is how 5.16 is performed, and reading it changes nothing about what is in it. What does change it is the AOT cache: a class taken from the cache has its symbols already in a region mapped from the archive rather than allocated, so the counts 5.16 produces on a run using the default cache are not the counts the same classes would produce without one {[HOTSPOT src/hotspot/share/oops/instanceKlass.cpp:1075@jdk-27+35]}.

**Which version this runtime reads.** The pinned JDK reads class file major versions 45 through 71, so every version threshold in 4a.3 and 4a.4 is reachable on it, including the ones below 50 that 4b.6 depends on. The pinned specification edition describes versions up to 69. Both numbers are in `docs/pin.json`, and the gap matters here more than it does elsewhere, because a version threshold added above 69 would be a rule this document's 4a does not contain.

Two things that look like configuration are not. `-Xlog:class+resolve` changes what is printed and nothing about when an entry resolves, which is what makes it usable in 5.13. And the `java.lang.classfile` API refuses to write some pools this specification requires a machine to accept, so a file it will not produce is not thereby a file a machine may refuse, and 5.2, 5.7 and 5.20 all need the low level entry builders rather than the checked ones.

## 8. Conformance

### 8.1 What conformance means here

An implementation conforms to this blueprint if, for every constant pool offered to `read`, it reaches the same decision as section 4a requires and reports a failure with the error class 4a names, if the table it produces answers the same questions about every index that 4a requires, and if `tag_at` obeys every clause in 4c for the life of the pool. Nothing is said about how the table is laid out, how much it costs, what its messages say, or what an implementation does with a pool section 4a does not describe.

Section 4b is not part of that obligation. Those clauses record what HotSpot at the pinned build does, and an implementation may differ from every one of them and conform. What it may not do is differ silently, and the clauses where that matters most are the conditional ones: an implementation whose cross index checking depends on where the class came from has to say so, because a reader who assumes 3.5 always runs will build a component on top of a table that was never checked.

Three consequences are worth stating because they are the ones people get wrong. First, matching a message is never conformance, so a test asserting on the wording of 4b.15 is testing HotSpot rather than the specification, and 4b.15 is the clause where the wording is misleading anyway. Second, an implementation that is stricter than 4a requires does not conform, and 4a.11 is the clause this catches most often, because deduplicating a pool on read is a natural optimisation and it changes the indices a later structure holds. Third, `OutOfMemoryError` is permitted at any allocation, so no item below expects a specific error for a large pool.

The capstone harness reports against 8.2 and against nothing else. An item is passed when a test exists that would fail if the behaviour changed, skipped when the item names a case the harness cannot construct, and failed otherwise. There is no fourth state, and in particular there is no state for an item nobody has looked at.

### 8.2 Checklist

- **8.2.1** 4a.1, 4b.9: refuses every entry whose tag is not one of the seventeen defined values, at every index including the first and the last, and does not attempt to skip such an entry by any assumed length.
- **8.2.2** 4a.2, 4b.10, 4b.11: places the entry after an eight byte constant at the index two further on, refuses any index that names the slot in between, and refuses an eight byte constant declared at the last index.
- **8.2.3** 4a.3, 4b.7: accepts each tag at the lowest class file version that permits it and refuses it at the version below, for all four thresholds, and reports the refusal as a malformed class file rather than as an unsupported version.
- **8.2.4** 4a.4, 4b.3, 4b.4, 4b.5, 4b.6: refuses an `ldc` of a `CONSTANT_Class_info` at a class file version below 49.0 and accepts it at 49.0 and above, whichever of its verifiers runs, which is the item the pinned HotSpot build passes only because the two version thresholds involved happen not to overlap.
- **8.2.5** 4a.5: accepts a `CONSTANT_Utf8_info` of 65535 bytes, treats its length as a byte count rather than a character count, and does not truncate or re-encode a string containing a supplementary character on the way in or out.
- **8.2.6** 4a.6: determines the role of every `CONSTANT_Utf8_info` from the entry or attribute that names it, and never from the bytes, which is checked by presenting the same string as a class name in one class and as a literal in another and observing that both are accepted.
- **8.2.7** 4a.7, 4b.14: checks that each of the three member reference kinds names a `CONSTANT_Class_info` and a `CONSTANT_NameAndType_info` of the right kinds, and either performs that check in every configuration or names the configuration in which it does not.
- **8.2.8** 4a.8: refuses a `CONSTANT_NameAndType_info` whose name is special and whose descriptor does not permit it, and reaches that decision after both halves have been read rather than while either is being read.
- **8.2.9** 4a.9, 4b.15, 4b.16: refuses a `reference_kind` outside 1 to 9, enforces the entry kind each of the nine requires, and permits kinds 6 and 7 to name a `CONSTANT_InterfaceMethodref_info` at class file version 52.0 and above and not below.
- **8.2.10** 4a.10: refuses a `CONSTANT_Dynamic_info` or a `CONSTANT_InvokeDynamic_info` whose bootstrap method index has no matching entry, including the case where the class carries no `BootstrapMethods` attribute at all.
- **8.2.11** 4a.11: accepts a pool containing two entries that denote the same constant, at every entry kind, and does not merge them in a way that changes what any index names.
- **8.2.12** 4a.12, 4b.8, 4c.3: refuses a `CONSTANT_Module_info` or a `CONSTANT_Package_info` outside a module declaration, refuses any index that names one, and reports a file that contains one together with the module access flag as a missing class rather than as a malformed one.
- **8.2.13** 4a.13, 4c.4: creates a class whose pool names a class, a field or a method that does not exist, and resolves no entry of the pool during creation.
- **8.2.14** 4a.14, 4b.2, 4c.6: throws an error of the same class on every use of a reference whose resolution failed, for each of the entry kinds that can fail, without attempting the resolution again.
- **8.2.15** 4b.1, 4b.17: keeps whatever internal states it needs for an entry in a representation no class file can produce, so that no byte sequence in a class file can put an entry into a state parsing alone should not reach.
- **8.2.16** 4b.12: documents, for every configuration it offers, which checks of section 3 are skipped, and either performs every 4a check in every configuration or names the configuration in which it does not.
- **8.2.17** 4b.13: if it shares string storage between classes, derives the same class from the same bytes whether or not another class holding the same strings has been loaded first, and exposes no way for one class to observe that another holds a string it holds.
- **8.2.18** 4b.18, 4b.19, 4c.5: publishes an entry's contents before the kind that describes them, so that no thread observes an entry in a state whose contents are not yet written, and records a resolution failure exactly once however many threads reach it together.
- **8.2.19** 4c.1, 4c.2: reads the class file version before the first entry and every entry before the first index is resolved, which is checked by presenting a pool whose first entry names its last one.

## 9. Provenance

Section 2 is generated from [the constant pool page](../../docs/generated/constpool.md), which `tools/gen_constpool.py` builds by joining four sources: the pinned specification edition, the JDK's own `classfile_constants.h.template` for the tag numbers, `constantTag.hpp` and `constantTag.cpp` for the byte as HotSpot holds it, and the pinned JDK's `java.lang.classfile` for the two kinds too rare to find an example of. It is not written here and editing it here has no effect. The generator stops rather than writes when any two of the four disagree, and `tools/test_gen_constpool.py` holds twenty tests, one for each way they can drift.

Every clause in 4a quotes JVMS SE25 and every clause in 4b names a file and a line in `jdk-27+35`. `tools/refcheck.py` resolves both against `docs/citations.json` and fails the build when a line has moved, so a clause that has drifted off its evidence is a broken build rather than a stale sentence.

Four things here are measured rather than read. The 1,216,114 Utf8 entries and their thirty roles, the 127 duplicate entries in 89 class files, the 2,675,920 uses against 1,216,114 entries, and the arithmetic that ties the entry counts to the sum of every `constant_pool_count` field come from `probes/constpool` over `java.base` on two platforms. A different module would give different numbers and none of them is a requirement on anybody. The write up is [the probe's page](../../docs/probes/constpool.md).

The finding in 4b.5 and 4b.6 was read out of four files and has not been demonstrated by running anything. It says that the version dependent loadability rule is enforced in exactly one place, that the place is reachable only below class file version 50, and that this is correct because the lowest threshold in the rule is 49. Producing a class file at version 48 with an `ldc` of a `CONSTANT_Class` would settle it, which is 5.4, and it is the observation in this section most worth doing before anybody relies on the clause.

Three questions this blueprint raises are open. 5.17 is the only unobservable item and it covers the three clauses about memory ordering, which means 8.2.18 is currently a reading of the source rather than a tested property, and closing it needs a `jcstress` test on weakly ordered hardware that has not been written. The pinned JDK reads class file version 71 and the pinned specification edition stops at 69, so a version threshold added between them would be missing from 4a.3 and 4a.4 and nothing here would notice. And 4a.6 is stated as an obligation on an implementation without a clause in the specification that says it in those words, because the specification establishes it by defining every referring structure rather than by prohibiting anything, so it is the clause in 4a most likely to be wrong about what is mandated.

The reviews field in the front matter is null. Nothing in this blueprint has been read by anybody with production experience of a constant pool implementation, and until it has, the conformance list is one person's reading of the specification and not a standard.
