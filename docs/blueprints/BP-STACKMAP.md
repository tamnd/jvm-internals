## 1. Scope

This blueprint specifies the `StackMapTable` attribute: the nine verification types, the seven kinds of frame, the 119 first bytes that mean nothing, the arithmetic that turns a chain of deltas into bytecode offsets, and the checks a machine performs while turning those bytes into frames. An implementation built from this document can take the bytes of one attribute together with the method's `max_locals`, `max_stack` and code array, produce the sequence of frames a type checker consumes, and refuse the attributes a conforming machine refuses.

It covers three things a reader is likely to expect somewhere else. The first is the first frame, which is not in the attribute: it is computed from the method descriptor, and `entries[0]` describes the second frame of the method, so 4a.4 and 4a.5 keep the arithmetic for the first entry apart from the arithmetic for every other one. The second is what the absence of the attribute means, which is not that the method was unchecked but that it needs no frames, and which changed meaning at class file version 50.0. The third is the second half of a `long` or a `double`, which the format never writes down and which every reader has to invent, and which HotSpot invents under two names of its own.

It deliberately excludes four things. The surrounding structure belongs to BP-CLASSFILE: this document begins at the attribute's `number_of_entries` and assumes `attribute_length`, `max_locals`, `max_stack` and the code array have already been read. The verification algorithm belongs to BP-VERIFY, so what it means for one frame to be assignable to another, what happens at a branch target and how an exception handler is checked are all out of scope, and this document specifies only what a frame says rather than what is done with it. The instructions the offsets point at belong to BP-BYTECODE. And the `CONSTANT_Class_info` an `Object_variable_info` names belongs to BP-CONSTPOOL, of which only 4a.8 is in scope here, that the index has to name one.

Two further boundaries are worth naming because they look like exclusions and are not. The attribute is inert until something verifies the method, so everything a class file parser does with it is bounds checking, and 4b.2 says so; an implementation that decodes frames during parsing is doing work no conforming machine has to do and is reporting errors at a point where a conforming machine reports none. And what a compiler chooses to emit is out of scope: 14,911 class files were measured to write section 2, the most useful thing found in them is that every frame is written in the smallest form the encoding allows, and 4a.16 records that nothing requires this of anybody.

### 2.1 The nine verification types

A verification type is a one byte item number and then nothing, an index, or an offset. It describes the type of one location, where a location is a single local variable or a single operand stack entry, except that `ITEM_Long` and `ITEM_Double` describe two.

| item | structure | after the byte | what it is | in locals | on stack | share |
|---:|---|---|---|---:|---:|---:|
| 0 | `Top_variable_info` | nothing | a location holding nothing a verifier will let you read | 26,349 | 0 | 2.46% |
| 1 | `Integer_variable_info` | nothing | an `int`, and also a `boolean`, a `byte`, a `short` and a `char` | 337,095 | 13,251 | 32.72% |
| 2 | `Float_variable_info` | nothing | a `float` | 1,150 | 58 | 0.11% |
| 3 | `Double_variable_info` | nothing | the first of the two locations a `double` occupies | 5,362 | 154 | 0.52% |
| 4 | `Long_variable_info` | nothing | the first of the two locations a `long` occupies | 36,145 | 1,002 | 3.47% |
| 5 | `Null_variable_info` | nothing | the `null` reference, which is assignable to every reference type | 0 | 68 | <0.01% |
| 6 | `UninitializedThis_variable_info` | nothing | `this`, inside a constructor that has not chained yet | 244 | 226 | 0.04% |
| 7 | `Object_variable_info` | `u2 cpool_index` | a reference to an instance of the class the index names | 620,545 | 28,280 | 60.59% |
| 8 | `Uninitialized_variable_info` | `u2 offset` | an object the `new` at that offset made and no constructor has run on | 0 | 908 | 0.08% |

The last three columns are 1,070,837 verification types in the scanned code. They are counted separately by side because the format allows every item in both places and a compiler does not use them that way, and a reader who has only ever seen the common half will write a parser that rejects a legal file.

The zeros in those two columns are the point of having two columns. `ITEM_Top` never appears on an operand stack; `ITEM_Null` never appears in a locals array; `ITEM_Uninitialized` never appears in a locals array. None of those is a rule. The probe builds a class that puts `ITEM_Uninitialized` and `ITEM_UninitializedThis` in both a locals array and an operand stack, hands the 316 bytes to the pinned JVM's own verifier, and this page is not written unless the JVM accepts it. So those cells are what a compiler emits and not what a machine will take.

`ITEM_Long` and `ITEM_Double` are the trap. Each describes two locations, the second of which has the verification type `top`, and that second `top` is not written down: one item covers both. The counts say so. There are 41,507 of the two of them in locals arrays and only 26,349 `ITEM_Top`, and a format that wrote the implied one would need at least as many of the second as of the first. Every `ITEM_Top` in the scanned code is a local variable slot that is genuinely unusable at that offset rather than the tail of a wide value.

### 2.2 The seven kinds of frame

Every frame starts with one byte, and that byte decides both what kind of frame it is and, for the two commonest kinds, how far along the code it applies. A frame is a delta against the frame before it, which is why no frame can be read on its own and why the order of the entries is part of the meaning.

| first byte | structure | after the byte | says | seen | share |
|---|---|---|---|---:|---:|
| 0-63 | `same_frame` | nothing | the same locals as the frame before, and an empty stack | 97,644 | 47.50% |
| 64-127 | `same_locals_1_stack_item_frame` | `verification_type_info stack[1]` | the same locals as the frame before, and one thing on the stack | 25,262 | 12.29% |
| 247 | `same_locals_1_stack_item_frame_extended` | `u2 offset_delta`, `verification_type_info stack[1]` | the same again, for a jump too far to fit in the first byte | 122 | 0.06% |
| 248-250 | `chop_frame` | `u2 offset_delta` | the frame before with its last `k` locals dropped, and an empty stack | 19,284 | 9.38% |
| 251 | `same_frame_extended` | `u2 offset_delta` | the same locals again, for a jump too far to fit in the first byte | 1,826 | 0.89% |
| 252-254 | `append_frame` | `u2 offset_delta`, `verification_type_info locals[frame_type - 251]` | the frame before with locals added, and an empty stack | 39,844 | 19.38% |
| 255 | `full_frame` | `u2 offset_delta`, `u2 number_of_locals`, `verification_type_info locals[number_of_locals]`, `u2 number_of_stack_items`, `verification_type_info stack[number_of_stack_items]` | every local and every stack entry, written out | 21,598 | 10.51% |

The offset delta comes from a different place in different rows, and that is the distinction to hold on to: `SAME` takes it from the first byte itself, `SAME_LOCALS_1_STACK_ITEM` takes it from the first byte, minus 64, and every other kind writes it out as a `u2`. The extended forms exist for exactly that reason. A jump of more than 63 bytes cannot be said in one byte, so the same frame has to be written a longer way.

That is not a rare case. 7,182 of the 205,580 frames in the scanned code sit more than 63 bytes past the frame before them, and the largest gap is 19,995 bytes.

`CHOP` and `APPEND` both encode a count in the first byte, and both count against the same constant: a chop drops 251 - `frame_type` locals and an append adds `frame_type` - 251. 251 is `SAME_FRAME_EXTENDED`, which sits between the two ranges, so the arithmetic is one subtraction from the middle in either direction. Neither can move more than three locals, which is why a method whose locals change by four at a branch target pays for a `full_frame`.

### 2.3 The 119 first bytes that mean nothing

[§4.7.4](https://docs.oracle.com/javase/specs/jvms/se25/html/jvms-4.html#jvms-4.7.4) says, in one sentence of prose and in no table at all, that tags in the range 128 to 246 are reserved for future use. That is 119 of the 256 values a first byte can hold, 46% of the encoding space, unusable and unnamed. HotSpot gives the range a name that the specification does not: `RESERVED_START` and `RESERVED_END` in `src/hotspot/share/classfile/stackMapTable.hpp`, which is the only place either boundary is a constant rather than a sentence.

The other 137 values are all in use, and that is a measurement rather than an inference: every one of the 137 legal first bytes occurs at least once in the scanned code. There is no first byte that is legal and unused, so a parser cannot be tested against real files into believing it handles the whole range.

A parser therefore needs one branch for the reserved range and it needs to reject rather than skip, because a reserved byte carries no length and there is no way to find the next frame past it. That is the difference between this attribute and most of a class file: an unknown attribute can be skipped by its length, and an unknown frame type cannot be skipped at all.

### 2.4 What the verifier holds in the same byte

The item number in a class file has nine legal values. The item number inside HotSpot's verifier has more, because the verifier tracks types the format has no way to write down. `int` in a stack map covers `boolean`, `byte`, `short` and `char`, and the verifier keeps them apart anyway so that an array store can be checked. A `long` occupies two locations and the format writes one item, and the verifier gives the second location a name.

| value | name in `verificationType.hpp` |
|---:|---|
| 9 | `ITEM_Boolean` |
| 10 | `ITEM_Byte` |
| 11 | `ITEM_Short` |
| 12 | `ITEM_Char` |
| 13 | `ITEM_Long_2nd` |
| 14 | `ITEM_Double_2nd` |

Every one of those is above 8, which is the largest item number the format defines, so a value the verifier invented can never be mistaken for one a class file may contain. That is the same discipline the constant pool tag byte follows, and for the same reason: one field, two vocabularies, and no overlap between them.

### 2.5 The offset arithmetic

A frame says where it applies as a distance from the frame before it, and the rule has an exception in it. The bytecode offset is the previous frame's offset plus `offset_delta` plus 1, unless the previous frame is the method's initial frame, in which case it is `offset_delta` exactly. The initial frame is not in the attribute at all: it is computed from the method descriptor and the access flags, so the first entry in the table describes the second frame of the method.

The `+ 1` is what makes two frames at the same offset impossible to write, so a verifier gets sortedness and uniqueness from the encoding rather than having to check for them. It is also the single rule in this attribute most likely to be implemented wrongly, because the exception applies to one frame per method and a test suite of small methods will not notice.

It is checked here rather than quoted. 122,906 of the 205,580 frames in the scanned code carry their own delta in the first byte, so the rule can be applied to the offset the pinned JDK resolved and the two compared. They agree on every one, and this generator refuses to write the page if they stop agreeing.

### 2.6 What the encoding buys, and what it costs

Six of the seven frame kinds are a compression of the seventh. Written entirely as `full_frame`, the same 205,580 frames would take 4,198,203 bytes instead of 1,390,250, so the compressed forms save 2,807,953 bytes, which is 67% of the attribute and 4.8% of every class file byte in the scanned code.

What it costs is that the attribute is 1,390,250 bytes against 7,537,707 bytes of bytecode, so a class file carries 18 bytes of proof for every hundred bytes of code, and 2.4% of the whole file. That is the price of verifying by type checking instead of by inference, and it is paid on disk and in memory by every class ever loaded.

Every frame in the scanned code is written in the smallest form that could express it. The probe works out, from the decoded frame and the one before it, which first byte the format would have allowed and takes the cheapest, and the answer differs from what was written for none of the 205,580 frames. The encoding is therefore canonical in practice without being canonical by rule: nothing in [§4.7.4](https://docs.oracle.com/javase/specs/jvms/se25/html/jvms-4.html#jvms-4.7.4) requires the smallest form, a file using `full_frame` everywhere is legal and loads, and no such file is in the scanned code.

That has a use. Two compilers that agree about the types at every branch target will produce byte identical `StackMapTable` attributes, so a difference in these bytes is a difference in what was proved rather than a difference in how it was written down.

One last number for a reader dating a class file. The attribute arrived at class file version 50.0, which is Java SE 6, and from that version on a `Code` attribute without one is treated as having an empty one rather than as having no stack map. So the absence of this attribute is itself a claim, and which claim it is depends on the version field at the top of the file.

## 3. Operations

There are two public operations and the first exists because the second cannot start without it. The attribute is a chain of differences, every link of which is a difference against the link before, and the first link is a difference against a frame that is not in the file. So an implementation computes that frame from the method's own declaration and then reads the attribute against it.

**initial(class, method) returns the frame the first entry is a delta against.** It reads nothing from the attribute. Its inputs are the method's descriptor, its access flags, the class it is declared in and its `max_locals`, and its output is a locals array and an empty operand stack. This is the frame that applies at bytecode offset 0, and it is the one frame of every method that no class file contains.

**read(bytes, method, initial) returns the frames in order, or throws.** `bytes` is the attribute's contents positioned at `number_of_entries` and bounded by `attribute_length`. `method` supplies `max_locals`, `max_stack`, the code array and the constant pool. The result is a sequence of frames, each carrying a bytecode offset, a locals array and an operand stack, in increasing order of offset with no two at the same offset. `read` is the whole of this blueprint's contract and it establishes nothing about whether the frames are correct, only that they are frames: a method whose every frame says the wrong thing passes all of it and fails in BP-VERIFY.

The steps of `initial` run in the order given.

**3.1 decide whether there is a `this`.** A static method has no `this` and its locals begin with the first argument. An instance method other than `<init>` begins with the declaring class. An `<init>` method other than `Object`'s begins with the verification type `uninitializedThis` and sets a flag that stays with the frame until a constructor is chained. `Object`'s own `<init>` begins with `Object` itself.

**3.2 expand the argument types.** Each parameter of the descriptor contributes its verification type, and a parameter of type `long` or `double` contributes that type followed by `top`, because the second of its two locations is a location and has a type. A `boolean`, a `byte`, a `short` and a `char` all contribute `int`.

**3.3 pad to the declared width.** Append `top` until the locals array is `max_locals` long. Fails if the types from 3.1 and 3.2 are already longer than `max_locals`, which is a malformed method rather than a malformed attribute and is reported as one.

The steps of `read` run in the order given. Each may assume every earlier step completed and may assume nothing about a later one. Steps 3.5 to 3.11 repeat once per entry.

**3.4 read the count.** Consume two bytes. A count of zero is legal and describes a method whose only frame is the one 3.1 to 3.3 produced. There is no upper bound to check here beyond the one `attribute_length` already imposes.

**3.5 read the frame type.** Consume one byte. That byte alone decides the kind of the frame, and therefore how many bytes follow it and what they mean. A byte in the reserved range is refused here, and it is refused rather than skipped, because a frame carries no length and there is no way to find the next one past it.

**3.6 find the offset delta.** For a `same_frame` the delta is the frame type itself and no further bytes are consumed. For a `same_locals_1_stack_item_frame` it is the frame type minus 64 and no further bytes are consumed. For every other kind it is a `u2` consumed here. An implementation that reads those two bytes before it has decided the kind has read past the end of a one byte frame.

**3.7 apply the offset arithmetic.** If this is the first entry, the frame's bytecode offset is the delta. Otherwise it is the previous frame's offset plus the delta plus one. The exception applies to exactly one entry per method and to the first one, and an implementation that has not written a separate branch for it is wrong by one on every frame of every method.

**3.8 build the locals array.** A `same_frame`, a `same_locals_1_stack_item_frame` and either extended form take the previous frame's locals unchanged. A `chop_frame` removes the last k local variables, where a local variable of type `long` or `double` counts as one variable and occupies two locations. An `append_frame` adds k local variables to the end, read as `verification_type_info` items, each of which occupies one location or two. A `full_frame` reads a `u2` count and then that many items, and replaces the array. Fails if a chop would leave fewer than zero locals, or if the result is wider than `max_locals`.

**3.9 build the operand stack.** A `same_frame`, a `same_frame_extended`, a `chop_frame` and an `append_frame` all have an empty stack. The two `same_locals_1_stack_item` forms have one `verification_type_info` item, which occupies one location or two. A `full_frame` reads a `u2` count and then that many items. Fails if the result is deeper than `max_stack`.

**3.10 check every verification type as it is read.** An item whose tag is above the largest defined one is refused. An `Object_variable_info`'s index has to be in range and has to name a `CONSTANT_Class_info`. An `Uninitialized_variable_info`'s offset has to be inside the code array and has to be the offset of a `new` instruction. Fails on any of the three.

**3.11 check the offset.** The frame's bytecode offset has to be inside the code array and has to be the offset at which an instruction starts. A frame in the middle of an instruction is not a frame that could ever apply, and it is refused here rather than left for the type checker to trip over.

**3.12 check the count.** When the declared number of entries has been read, the attribute has to be exhausted, and when the attribute is exhausted the declared number has to have been read. Those are two failures and an implementation checks both, because a count that is too small leaves trailing bytes and a count that is too large runs off the end.

Steps 3.4 to 3.12 are all the checking this attribute gets before verification. They establish that the frames are well formed, in order, one per instruction offset, and within the widths the method declared. They establish nothing whatever about whether any frame describes the state the code actually reaches, which is the entire subject of BP-VERIFY and none of this blueprint's.

## 4. Guarantees

### 4a. What the specification mandates

- **4a.1** There may be at most one `StackMapTable` attribute in the attributes table of a `Code` attribute, and it lives on the `Code` attribute rather than on the method, so a method with no code has nowhere to put one {[JVMS §4.7.4@SE25]}.
- **4a.2** In a class file of version 50.0 or above, a `Code` attribute with no `StackMapTable` has an implicit stack map attribute equivalent to one whose `number_of_entries` is zero, so the absence of the attribute is a claim that the method needs no frames rather than a claim that it was not checked {[JVMS §4.7.4@SE25]}.
- **4a.3** The order of the frames in the `entries` table is significant and each frame relies on the previous one for some of its semantics, so no entry can be read, moved, inserted or removed on its own {[JVMS §4.7.4@SE25]}.
- **4a.4** The first stack map frame of a method is implicit and computed from the method descriptor by the type checker, so the entry at index 0 describes the second frame of the method and the attribute never contains the state at bytecode offset 0 {[JVMS §4.7.4@SE25]} {[JVMS §4.10.1.5@SE25]}.
- **4a.5** The bytecode offset at which a frame applies is the previous frame's offset plus `offset_delta` plus 1, unless the previous frame is the method's initial frame, in which case it is `offset_delta` exactly {[JVMS §4.7.4@SE25]}.
- **4a.6** The delta encoding is what makes the frames sorted by definition and the `+ 1` is what makes duplicates impossible to write, so a reader obtains both properties from the arithmetic and neither has to be checked separately {[JVMS §4.7.4@SE25]}.
- **4a.7** Every frame's offset has to be the offset at which an instruction starts, because merging the frames with the instructions is undefined unless every frame offset has a corresponding instruction offset and the offsets are monotonically increasing {[JVMS §4.10.1.5@SE25]}.
- **4a.8** A verification type is a one byte tag followed by zero or more bytes, and two of the nine carry anything at all: an `Object_variable_info` carries a `u2` index that has to name a `CONSTANT_Class_info`, and an `Uninitialized_variable_info` carries a `u2` offset that has to be the offset of the `new` instruction that created the object {[JVMS §4.7.4@SE25]}.
- **4a.9** A `Long_variable_info` or a `Double_variable_info` describes the first of two locations, the second location has verification type `top` and is not written down anywhere, and the first location may not be the highest numbered local variable or the topmost operand stack entry {[JVMS §4.7.4@SE25]}.
- **4a.10** The first byte of a frame decides its kind, and for the two commonest kinds it also carries the offset delta: `frame_type` for a `same_frame` and `frame_type - 64` for a `same_locals_1_stack_item_frame`, with no further bytes read in either case {[JVMS §4.7.4@SE25]}.
- **4a.11** Tags in the range 128 to 246 are reserved for future use, which is 119 of the 256 values a first byte can hold, and a reserved tag cannot be skipped because a frame carries no length of its own {[JVMS §4.7.4@SE25]}.
- **4a.12** A `chop_frame` drops the last k local variables of the previous frame, k is `251 - frame_type` and is therefore 1, 2 or 3, and it is an error if k is larger than the number of local variables the previous frame has {[JVMS §4.7.4@SE25]}.
- **4a.13** An `append_frame` adds k local variables, k is `frame_type - 251` and is therefore 1, 2 or 3, the item at index 0 is the first additional local variable, and an item that is a `Long_variable_info` or a `Double_variable_info` advances the local variable index by two rather than one {[JVMS §4.7.4@SE25]}.
- **4a.14** It is an error for any entry of `locals` to represent a local variable whose index exceeds the method's maximum, or for any entry of `stack` to represent a stack entry beyond the method's maximum operand stack size, and the rule is stated separately for `append_frame` and for `full_frame` in the same words {[JVMS §4.7.4@SE25]}.
- **4a.15** The initial frame's locals are the `this` type where there is one, followed by the argument types with every two location type followed by `top`, padded with `top` to the method's declared width, and its operand stack is empty {[JVMS §4.10.1.5@SE25]}.
- **4a.16** Nothing requires a frame to be written in the smallest kind that could express it. A `full_frame` may appear anywhere, a `same_frame_extended` may be used wherever a `same_frame` would do, there is no canonical form and no shortest form rule, and a class file that takes the longer option everywhere is legal {[JVMS §4.7.4@SE25]}.

### 4b. What HotSpot chose

- **4b.1** The reserved range has a name in HotSpot and none in the specification: `RESERVED_START` and `RESERVED_END` sit in the same enum as the seven frame kinds, and that enum is the only place either boundary of the range is a constant rather than a sentence {[HOTSPOT src/hotspot/share/classfile/stackMapTable.hpp:156@jdk-27+35]} {[HOTSPOT src/hotspot/share/classfile/stackMapTable.hpp:157@jdk-27+35]}.
- **4b.2** The attribute is not decoded while the class file is read. Its bytes are bounds checked against `attribute_length` and copied verbatim, and nothing inside it is looked at until the verifier asks for a frame {[HOTSPOT src/hotspot/share/classfile/classFileParser.cpp:1760@jdk-27+35]}.
- **4b.3** A `StackMapTable` whose `attribute_length` is zero is dropped where it is found and the method records no attribute, so a file that declares the attribute and gives it no `number_of_entries` field is accepted and behaves as one with no attribute at all {[HOTSPOT src/hotspot/share/classfile/classFileParser.cpp:1752@jdk-27+35]} {[HOTSPOT src/hotspot/share/classfile/stackMapTable.cpp:179@jdk-27+35]}.
- **4b.4** A `StackMapTable` in a class file below major version 50 is not recognised as one: the test that matches the attribute name is guarded by the version, so those bytes fall through to the branch that skips attributes nobody knows and are never read again {[HOTSPOT src/hotspot/share/classfile/classFileParser.cpp:2408@jdk-27+35]} {[HOTSPOT src/hotspot/share/classfile/classFileParser.cpp:2420@jdk-27+35]}.
- **4b.5** Two `StackMapTable` attributes in one `Code` attribute end the parse with a message that names the class file and does not name the method or the attribute index {[HOTSPOT src/hotspot/share/classfile/classFileParser.cpp:2412@jdk-27+35]}.
- **4b.6** The decoder reads the `u2 offset_delta` before it decides whether the frame type is reserved, so on a reserved first byte it has consumed two bytes it had no business reading, and what saves it is that the next thing it does is throw {[HOTSPOT src/hotspot/share/classfile/stackMapTable.cpp:310@jdk-27+35]} {[HOTSPOT src/hotspot/share/classfile/stackMapTable.cpp:312@jdk-27+35]}.
- **4b.7** There is a second reserved frame type error at the bottom of the same function and it is unreachable, because the branches above it cover 0 to 63, 64 to 127, everything below 247, 247, 248 to 251, 252 to 254 and 255, which is every value a `u1` can hold {[HOTSPOT src/hotspot/share/classfile/stackMapTable.cpp:474@jdk-27+35]}.
- **4b.8** The exception for the first entry is not written once. Each of the five branches that can decode the first entry carries its own pair of assignments, one for the first frame and one for every other, selected by a flag the branch then clears {[HOTSPOT src/hotspot/share/classfile/stackMapTable.cpp:258@jdk-27+35]} {[HOTSPOT src/hotspot/share/classfile/stackMapTable.cpp:265@jdk-27+35]}.
- **4b.9** The first entry copies the initial frame's locals rather than aliasing them, on the stated grounds that the verifier updates that array in place, so the frame the type checker computed survives being read past {[HOTSPOT src/hotspot/share/classfile/stackMapTable.cpp:261@jdk-27+35]} {[HOTSPOT src/hotspot/share/classfile/stackMapTable.cpp:272@jdk-27+35]}.
- **4b.10** A frame whose offset is past the end of the code, or which does not land on the first byte of an instruction, is reported as a verify error rather than a format error, and the test is a lookup in a byte array the verifier filled in while walking the code {[HOTSPOT src/hotspot/share/classfile/stackMapTable.cpp:51@jdk-27+35]}.
- **4b.11** `number_of_entries` is compared against the number of frames actually decoded twice, once before each frame as a floor and once at the end for equality, and the two failures give the same message, so a count that is too small and a count that is too large are indistinguishable in a log {[HOTSPOT src/hotspot/share/classfile/stackMapTable.cpp:58@jdk-27+35]} {[HOTSPOT src/hotspot/share/classfile/stackMapTable.cpp:65@jdk-27+35]}.
- **4b.12** A chop counts local variables and not locations. It walks backwards through the previous frame's expanded array and steps two positions rather than one whenever it lands on the second half of a category 2 value {[HOTSPOT src/hotspot/share/classfile/stackMapTable.cpp:188@jdk-27+35]}.
- **4b.13** A chop that would run off the front of the locals array returns a negative length, which is caught by the same bounds check that catches a frame wider than the method's maximum, so the specification's separate error for chopping too far arrives with the message for an array of the wrong size {[HOTSPOT src/hotspot/share/classfile/stackMapTable.cpp:193@jdk-27+35]} {[HOTSPOT src/hotspot/share/classfile/stackMapTable.hpp:141@jdk-27+35]}.
- **4b.14** After a chop the frame's flags are recomputed from the surviving locals rather than inherited from the previous frame, because the local variable holding `uninitializedThis` may be one of the ones that was dropped {[HOTSPOT src/hotspot/share/classfile/stackMapTable.cpp:364@jdk-27+35]}.
- **4b.15** An append frame's locals array is allocated at two positions per appended item before any item is read, and a full frame's arrays the same way, because the decoder cannot know which items are category 2 until it has read them {[HOTSPOT src/hotspot/share/classfile/stackMapTable.cpp:397@jdk-27+35]} {[HOTSPOT src/hotspot/share/classfile/stackMapTable.cpp:432@jdk-27+35]}.
- **4b.16** The second location of a category 2 value is materialised as a verification type of its own, under two names from an enum whose comment says these are not found in class files, and the six values that enum holds begin at 9, above the eight the format defines, so a verifier type can never be mistaken for a file type {[HOTSPOT src/hotspot/share/classfile/verificationType.hpp:64@jdk-27+35]} {[HOTSPOT src/hotspot/share/classfile/verificationType.hpp:65@jdk-27+35]}.
- **4b.17** A tag below 6 becomes a verification type by table lookup with no range check of its own, which is safe because the table covers every value below 6, and only a tag above the largest defined one reaches the error {[HOTSPOT src/hotspot/share/classfile/stackMapTable.cpp:202@jdk-27+35]} {[HOTSPOT src/hotspot/share/classfile/stackMapTable.cpp:232@jdk-27+35]}.
- **4b.18** An `Object_variable_info` whose index is out of range, or which names an entry that is neither a resolved nor an unresolved class, is a stack map format error, while an `Uninitialized_variable_info` whose offset does not point at a `new` instruction is a class format error raised through the verifier rather than through the stream, so two malformations of the same kind arrive by two different routes {[HOTSPOT src/hotspot/share/classfile/stackMapTable.cpp:208@jdk-27+35]} {[HOTSPOT src/hotspot/share/classfile/stackMapTable.cpp:226@jdk-27+35]}.
- **4b.19** Whether the attribute is read at all is decided per class from the defining loader, by the same pair of flags that decides the rest of verification, so a class from the boot loader in a default configuration has its stack map copied into memory and never decoded {[HOTSPOT src/hotspot/share/classfile/verifier.cpp:117@jdk-27+35]}.
- **4b.20** At major version 50 exactly, a class the type checking verifier rejected with a verify error or a class format error is handed to the inference verifier, which ignores the attribute entirely, so an attribute that fails every check in section 3 can still produce a class that loads and runs {[HOTSPOT src/hotspot/share/classfile/verifier.cpp:219@jdk-27+35]} {[HOTSPOT src/hotspot/share/classfile/verifier.cpp:228@jdk-27+35]} {[HOTSPOT src/hotspot/share/classfile/verifier.cpp:230@jdk-27+35]}.

### 4c. Ordering obligations

- **4c.1** The class file version is known before the attribute is recognised, because below major version 50 these bytes are an attribute nobody knows and at 50 and above they are a stack map, and nothing but the version field distinguishes the two {[HOTSPOT src/hotspot/share/classfile/classFileParser.cpp:2408@jdk-27+35]}.
- **4c.2** The method's maximum locals and maximum operand stack size are known before the first frame is decoded, because every frame is checked against both as it is built and neither can be inferred from the attribute {[JVMS §4.7.4@SE25]}.
- **4c.3** The code array has been walked before the frames are decoded, because a frame's offset is checked against the set of instruction starts and an `Uninitialized_variable_info`'s offset against the presence of a `new` at that offset, and neither question can be answered from the bytes of the attribute {[HOTSPOT src/hotspot/share/classfile/stackMapTable.cpp:224@jdk-27+35]}.
- **4c.4** The initial frame is computed before the first entry is read, and the first entry is a delta against it, so a reader that starts at the first entry with an empty frame is wrong for every method that takes an argument and right for every method that takes none {[JVMS §4.10.1.5@SE25]}.
- **4c.5** Each frame is complete before the next one begins, because the next frame's locals, its operand stack and its offset are all expressed relative to it, so there is no order in which the entries can be decoded other than the order they are written in {[JVMS §4.7.4@SE25]}.
- **4c.6** A failure inside the attribute does not necessarily end the load where it is raised. It is reported through the verifier's error mechanism rather than by throwing, and that mechanism may return so that the class can be offered to a second verifier, which is a possibility every step of section 3 has to tolerate {[HOTSPOT src/hotspot/share/classfile/stackMapTable.hpp:146@jdk-27+35]}.

## 5. Observation

Every item below is a procedure rather than a result. The tool named in it is the one that answers the question with the least machinery, and where two tools disagree that disagreement is itself the observation.

Six tools carry this section. `java.lang.classfile`, on the pinned JDK, assembles a class frame by frame from a Java program, which is the only practical way to produce a stack map no compiler would emit. `javap -v` prints the frames as the platform's own reader understands them, with the offsets already resolved, which is what makes an argument about the arithmetic settleable. `xxd` is what settles an argument about a byte, because every other tool on this list is showing an interpretation and this attribute's whole subject is which byte was written. `probes/classfile-fuzz` breaks one valid class file and records where the machine stopped and in what words. `probes/stackmap` walks every class file of `java.base` twice, once through the class file API and once as raw bytes, and it is the only item here that produces a number rather than an outcome. And `java -Xlog:verification=info` says which verifier ran, which is the one question none of the others can answer.

- **5.1** 4a.1, 4b.5: build a `Code` attribute carrying two `StackMapTable` attributes, the second of them empty, and load it, with `java.lang.classfile` and `xxd`. The parse ends with a message that names the class file and nothing inside it, so a person reading the failure knows the file has two and not which method they are in.
- **5.2** 4a.2, 4b.3: take a method with branches, delete its `StackMapTable` attribute, and separately keep the attribute and set its `attribute_length` to zero, with `xxd` and `javap -v`. The first is refused, because the method needs frames it no longer has. The second is accepted, and the attribute that declares itself and gives no `number_of_entries` at all behaves exactly as though it had been deleted.
- **5.3** 4a.3, 4c.5: take a method with four frames, exchange the first two entries, and separately delete the first entry and lower `number_of_entries` by one, with `probes/classfile-fuzz` and `xxd`. Neither file loads, and neither failure mentions the entry that was moved, because every offset after it is now a different number and the first thing that fails is whichever one falls off an instruction boundary first.
- **5.4** 4a.4, 4a.15, 4c.4: print the frames of an instance method taking a `long` and an `Object` and compare the first entry's resolved offset against its `offset_delta`, with `javap -v`. The two are equal, which they are for no other entry, and the locals the first frame inherits are four wide before any entry has been read: `this`, the `long`, its `top`, and the `Object`.
- **5.5** 4a.5, 4a.6, 4b.8: apply the arithmetic to the 122,906 frames of `java.base` that carry their own delta in the first byte, and compare against the offsets the pinned JDK resolved, with `probes/stackmap/run.py`. They agree on every one, no two frames of any method share an offset, and every method's frames come out sorted without anything sorting them.
- **5.6** 4a.7, 4b.10: move one frame's offset one byte forward, into the middle of the instruction it used to point at, with `xxd` and `probes/classfile-fuzz`. The failure is a verify error rather than a format error, which is the one place in this blueprint where a malformed attribute is reported as though the code were wrong.
- **5.7** 4a.8, 4b.18: build an `Object_variable_info` whose index is past the end of the pool, then one naming a `CONSTANT_Utf8_info`, then an `Uninitialized_variable_info` whose offset is past the end of the code, then one pointing at an instruction that is not a `new`, with `java.lang.classfile`. All four are refused and they do not all arrive as the same class of error, because two of them go through the stream and two through the verifier.
- **5.8** 4a.9, 4b.12, 4b.15, 4b.16: count the `Long` and `Double` items in locals arrays against the `Top` items across `java.base`, then chop a frame whose last local is a `long`, with `probes/stackmap/run.py` and `javap -v`. There are 41,507 of the first and 26,349 of the second, which a format writing the implied second half could not produce, and chopping one local variable off a `long` removes both of its locations.
- **5.9** 4a.10, 4a.16: work out, for every frame in `java.base`, the smallest first byte that could have expressed it given the frame before, and compare against what was written, with `probes/stackmap/run.py` and `javap -v`. The answer differs for none of the 205,580 frames, and nothing in the specification asks for that. This is the observation the rest of the section is arranged around and it is written up on [the probe's page](../../docs/probes/stackmap.md).
- **5.10** 4a.11, 4b.1, 4b.6, 4b.7: overwrite one frame's first byte with 128, then with 200, then with 246, and load each, with `xxd` and `probes/classfile-fuzz`. All three give one message. Watching where the stream stopped shows two bytes consumed past the offending one, which is the read that happens before the rejection.
- **5.11** 4a.12, 4a.13, 4b.13: build a frame chopping one, two and three locals, an append frame adding one, two and three, and a chop of three from a frame that has two, with `java.lang.classfile` and `javap -v`. The six legal ones behave as the formulas say. The seventh is refused with a message about an array size, which names neither the chop nor the count that was too large.
- **5.12** 4a.14: build a `full_frame` whose locals array is one location wider than the method's declared maximum, then one whose operand stack is one deeper, with `java.lang.classfile`. Both are refused, and the wider case is worth building with a `long` in it, since a locals array that is legal by item count and illegal by location count is the shape an implementation counting items rather than locations will accept.
- **5.13** 4b.2, 4b.19: define a class whose `StackMapTable` is filled with random bytes but whose `attribute_length` is right, without linking it, then link it, then load the same bytes through a loader for which verification is off, with `java.lang.classfile` and `java -XX:+UnlockDiagnosticVMOptions -XX:-BytecodeVerificationRemote`, which is two flags on the pinned build because the second is diagnostic there. Defining it succeeds in every case, linking fails in the first and not the third, and the bytes were copied into memory in all of them.
- **5.14** 4b.4, 4c.1: take one class file with a `StackMapTable` and write its major version to 50 and then to 49, changing nothing else, with `xxd` and `java -Xlog:verification=info`. At 50 the attribute is a stack map and at 49 the same bytes are an attribute nobody knows, and the log names a different verifier in the two runs.
- **5.15** 4b.9: unobservable. The choice to copy the initial frame's locals rather than alias them is invisible from outside the machine, because the only difference it makes is whether a later in place update by the verifier reaches an array the reader still holds, and a machine that got it wrong would produce a wrong verification result rather than a distinguishable one.
- **5.16** 4b.11: set `number_of_entries` one lower than the frames present, then one higher, with `probes/classfile-fuzz` and `xxd`. Both are refused, both give the same sentence, and the sentence does not say in which direction the count was wrong.
- **5.17** 4b.14: build a constructor that holds `uninitializedThis` in a local variable, chops it away at a branch target, and then attempts to chain a constructor, with `java.lang.classfile`. The class is refused, and it is refused for chaining on something that is not uninitialized rather than for anything about the chop.
- **5.18** 4b.17: build one frame for each verification type tag from 0 to 8 and then one with tag 9, with `java.lang.classfile` and `javap -v`. The nine are accepted, the tenth is refused, and there is no tag below 9 for which the reader has to consult anything but a table.
- **5.19** 4b.20, 4c.6: take a class whose `StackMapTable` has been corrupted so that the type checking verifier refuses it, and load it at major version 50 and then at 51, with `xxd` and `java -Xlog:verification=info`. At 51 it fails. At 50 the log says the class failed over to the old verifier, the attribute is never looked at again, and the class loads.
- **5.20** 4c.2: lower a method's `max_locals` by one without touching its frames, with `xxd` and `probes/classfile-fuzz`. The failure names the array size rather than the frame, which is the check of 3.8 firing on a number that came from outside this attribute.
- **5.21** 4c.3: build an `Uninitialized_variable_info` whose offset is a valid instruction offset holding something other than `new`, with `java.lang.classfile` and `javap -v`. It is refused, and the only way to reach that decision is to have walked the code first, since the attribute contains nothing that says what is at that offset.

## 6. Edge cases

### 6.1 Malformed input

This attribute is the part of a class file with the least redundancy in it. A frame carries no length, no offset and no name: it carries one byte that decides how many bytes follow, and then those bytes. So there is no such thing as resynchronising after a bad frame, and an implementation that tries to skip one and continue is inventing a length the format never wrote down. That is the reason 4a.11 is stated as a prohibition rather than as a range: a reserved first byte is not an unknown frame, it is the end of the attribute.

Four families of malformed attribute behave differently and an implementation has to handle all four. A reserved or undefined first byte is caught the moment the byte is read, because nothing else can be done with it. A count that disagrees with the frames present is caught either partway through, when more frames have been parsed than were declared, or at the end, when the stream is exhausted and the count is not. An offset that does not land on an instruction is caught against a map of the code that the attribute contributed nothing to. And a verification type whose payload is wrong, an index past the end of the pool or an offset that is not a `new`, is caught while the item is being read and needs two structures outside the attribute to catch it.

The second family is the one an implementation is most likely to get half right. HotSpot checks the count twice, once as a floor before each frame and once for equality at the end, and gives both failures the same words {[HOTSPOT src/hotspot/share/classfile/stackMapTable.cpp:58@jdk-27+35]} {[HOTSPOT src/hotspot/share/classfile/stackMapTable.cpp:65@jdk-27+35]}. An implementation that checks only the second has a bug that never fires, because a count that is too small means the stream still has bytes in it and the loop has already stopped. An implementation that checks only the first accepts trailing garbage.

One malformation is not a malformation. A `StackMapTable` whose `attribute_length` is zero has no `number_of_entries` field, which the structure in section 2 requires, and HotSpot accepts it and treats the method as having no attribute at all {[HOTSPOT src/hotspot/share/classfile/classFileParser.cpp:1752@jdk-27+35]}. That is not the implicit empty stack map of 4a.2, which is about the attribute being absent, and it is the one case in this blueprint where the pinned build is more permissive than the structure it is reading.

The most surprising case is that a malformed attribute is sometimes not an error. At major version 50 exactly, a class the type checking verifier rejected is handed to the inference verifier, which does not read this attribute at all {[HOTSPOT src/hotspot/share/classfile/verifier.cpp:228@jdk-27+35]}. So an attribute that fails every check in section 3 produces a class that loads and runs, provided the code is type safe by inference. An implementation is not required to offer a second verifier and is required to say whether it does, because a test suite of malformed attributes written against a machine that does will record dozens of passes it did not earn.

### 6.2 Resource exhaustion

The attribute has two bounds and neither is where a reader expects. `number_of_entries` is two bytes, so a method has at most 65535 frames. Every count inside a frame is also two bytes, so a `full_frame` may declare 65535 locals and 65535 stack entries, which is exactly the range `max_locals` and `max_stack` can hold and therefore no bound at all beyond what the method already declared.

What is not bounded by any of those is the allocation. A `full_frame` declaring 65535 locals is seven bytes long before its first item, and HotSpot allocates two verification types per declared item before reading any of them, because it cannot know which are category 2 until it has read them {[HOTSPOT src/hotspot/share/classfile/stackMapTable.cpp:432@jdk-27+35]}. Seven bytes therefore buy an array of 131,070 entries. The amplification is real and it is bounded, because the read of the items runs off the end of the attribute a moment later and the frame is refused, so a file gets one such allocation rather than one per frame. An implementation that allocates lazily has a smaller constant and the same worst case, and an implementation that allocates one entry per declared item and grows on meeting a category 2 value has a copy instead.

The honest bound on the whole attribute is `attribute_length`, which is four bytes wide and is BP-CLASSFILE's to enforce, and after that the length of the file. Nothing in this blueprint imposes a smaller one. An implementation reading frames from a stream it has not bounded has no limit at all, which is the same conclusion BP-CONSTPOOL reaches about the pool and for the same reason.

Measurement puts all of this a very long way from the limits. Across the 14,911 class files of `java.base` the widest locals array in any frame is 35 and the deepest operand stack in any frame is 11, against a field width of 65535 for each. The largest offset delta anywhere is 19,995. An implementation that sizes its buffers from the field widths allocates about two thousand times what the largest real frame needs, and one that sizes them from these measurements fails on a generated class file.

### 6.3 The concurrent case

Decoding this attribute holds no concurrency and that is worth stating rather than assuming. Verification happens once per class, on the thread that links it, under the lock that makes linking happen once, so the reader in section 3 sees a byte array nothing else is writing to and produces frames nothing else can see. An implementation is not required to make `read` thread safe and gains nothing by it.

The concurrency this attribute actually has is retroactive. A class may be redefined while it is running, and the redefinition supplies a new code array with new offsets, so the frames that were correct for the old body describe nothing in the new one. HotSpot's reader names the redefinition machinery as a friend for exactly that reason {[HOTSPOT src/hotspot/share/classfile/stackMapTable.hpp:109@jdk-27+35]}, and the bounds check on a frame's arrays carries a comment saying the failure it is guarding against is somebody rewriting a method and not knowing to update the stack map {[HOTSPOT src/hotspot/share/classfile/stackMapTable.hpp:141@jdk-27+35]}. The obligation that falls out of this is that the attribute is decoded again for the new body and never carried across, and an implementation that caches decoded frames on the method has to invalidate that cache on redefinition.

The other thread that reads this attribute is an agent's. A JVMTI agent registered for the class file load hook sees the bytes before the machine does and may rewrite the code array, and an agent that does so without rewriting the frames produces a class that was valid on disk and is not valid in memory. That failure surfaces as a verify error naming an offset the person reading it cannot find in their source, and it is indistinguishable from a compiler bug unless the agent is known about.

Nothing in section 4 is a memory ordering obligation, which makes this blueprint unusual among the class file ones. There is no published state, no tag byte that both describes and publishes an entry, and no field any two threads write. If an implementation finds it needs a barrier anywhere in section 3, it has shared something section 3 does not require it to share.

## 7. Configuration

Nothing in section 4a is configurable and the switch on 4b is unusually blunt: it does not change how the attribute is read, it changes whether it is read at all. That makes this blueprint's configuration section shorter than most and its consequences larger, because a check that never runs cannot be made stricter or looser, and a table built by observing a machine in its default configuration will be a table of things that did not happen.

**Whether the attribute is decoded.** `BytecodeVerificationLocal` and `BytecodeVerificationRemote` decide, per class and from the defining loader, whether the class is verified {[HOTSPOT src/hotspot/share/classfile/verifier.cpp:117@jdk-27+35]}. Verification is the only thing that decodes this attribute, so for a class the pair says no to, the bytes are copied into memory by 4b.2 and never looked at again. The default answer is no for the boot loader and yes for every other loader, which means the several thousand classes of `java.base` that section 2 counts have their stack maps read by the class file API and not by the machine that loaded them.

**Whether the attribute is decoded a second time.** A class taken from the AOT cache that has already been rewritten is not eligible for verification at all, on the grounds that its bytecodes now hold cache indices the verifier cannot read {[HOTSPOT src/hotspot/share/classfile/verifier.cpp:143@jdk-27+35]}. Such a class was verified when the cache was built, so this is not a hole, but it does mean that whether a given class's stack map is decoded in a given run depends on whether that run is using a cache. An implementation that reports which classes it verified will report different sets on two runs of the same program.

**Which verifier runs, which is not configurable.** The two class file versions that decide it, 50 for the type checking verifier and 51 for the end of failover, are compile time constants and there is no flag for either {[HOTSPOT src/hotspot/share/classfile/verifier.cpp:219@jdk-27+35]}. A reader who wants a malformed stack map to be tolerated cannot ask for that, and a reader who wants it not to be tolerated cannot ask for that either: the answer is a property of the file. The one thing that does suppress failover is dumping a static class data archive, because a class verified by the old verifier is excluded from the archive rather than tolerated in it {[HOTSPOT src/hotspot/share/classfile/verifier.cpp:227@jdk-27+35]}.

**What an agent can change.** A JVMTI agent registered for the class file load hook sees the bytes before the machine does, and an agent that rewrites the code array without rewriting this attribute produces a class that was valid on disk and is not valid in memory. This is not a setting anybody turns on deliberately for this attribute, and it is the commonest way a stack map failure appears in production, which is why 6.3 states it as an obligation on the agent rather than as a warning.

**What changes what is printed and nothing else.** `-Xlog:verification=info` names the verifier that ran and says when a class failed over {[HOTSPOT src/hotspot/share/classfile/verifier.cpp:233@jdk-27+35]}, which is what makes 5.14 and 5.19 performable, and it changes nothing about which one runs. The same is true of `javap -v`, which resolves the offsets for the reader and shows a frame nobody wrote down at index 0 of nothing.

**Which versions this runtime reads.** The pinned JDK reads class file major versions 45 through 71, so both sides of the version 50 boundary in 4b.4 and 4b.20 are reachable on it, and so is the single version at which failover applies. The pinned specification edition describes versions up to 69. Both numbers are in `docs/pin.json`. The gap matters less here than it does for the constant pool, because this attribute's structure has not changed since it arrived, and it matters at all only if a future version adds a frame kind out of the reserved range that 4a.11 currently describes as empty.

## 8. Conformance

### 8.1 What conformance means here

An implementation conforms to this blueprint if, for every `StackMapTable` attribute offered to `read` together with the method it belongs to, it reaches the same accept or refuse decision as section 4a requires, and if the frames it produces for an accepted attribute carry the same bytecode offsets, the same locals and the same operand stack as 4a requires. Nothing is said about how a frame is represented, how much it costs, what any message says, or what an implementation does after it has the frames, which is BP-VERIFY's subject and not this one's.

Section 4b is not part of that obligation. Those clauses record what HotSpot at the pinned build does, and an implementation may differ from every one of them and conform. Three of them are worth naming as places where differing is the sensible choice: 4b.3, which accepts an attribute the structure in section 2 does not describe, 4b.6, which reads two bytes before deciding it should not have, and 4b.11, which gives two opposite failures the same words. An implementation that matches HotSpot on those has copied a defect and can say so.

One clause of 4b is different in kind and an implementation has to make a decision about it rather than merely differ. 4b.20 says that at one class file version a rejected attribute is not fatal, because the class is offered to a second verifier that does not read the attribute at all. An implementation that has no second verifier will refuse files the pinned build accepts, and it conforms, because 4a requires the refusal. What it may not do is leave this unstated, since a conformance suite of malformed attributes run against a machine that has failover will pass items it never exercised, and 8.2.19 is written to make that visible rather than to require either answer.

Four consequences are worth stating because they are the ones people get wrong. First, matching a message is never conformance, and 4b.11 and 4b.13 are the two clauses where the message is actively misleading. Second, an implementation that is stricter than 4a requires does not conform, and 4a.16 is the clause this catches: refusing a `full_frame` where a `same_frame` would have done is refusing a legal file, and it is a natural thing to build if the only files you have ever tested against are the ones a compiler produced. Third, an implementation is not permitted to skip a frame it does not understand, and any implementation that resynchronises after a bad frame has invented a length. Fourth, `OutOfMemoryError` is permitted at any allocation, so no item below expects a specific error for an attribute that declares more than it contains.

The capstone harness reports against 8.2 and against nothing else. An item is passed when a test exists that would fail if the behaviour changed, skipped when the item names a case the harness cannot construct, and failed otherwise. There is no fourth state, and in particular there is no state for an item nobody has looked at.

### 8.2 Checklist

- **8.2.1** 4a.1, 4b.5: refuses a `Code` attribute carrying two `StackMapTable` attributes, whether or not the second one is empty, and accepts a `Code` attribute carrying one.
- **8.2.2** 4a.2, 4b.3: treats a `Code` attribute with no `StackMapTable`, at class file version 50.0 and above, as having one with no entries, and states whether it also accepts an attribute whose `attribute_length` is zero, which the structure does not describe.
- **8.2.3** 4a.3, 4c.5: decodes the entries in the order they are written, produces different frames when two adjacent entries are exchanged, and does not accept a file in which an entry has been removed without the count changing.
- **8.2.4** 4a.4, 4a.15, 4c.4: computes the initial frame from the method descriptor and the access flags before reading any entry, places `this` first for an instance method and `uninitializedThis` first for a constructor, follows every `long` and `double` argument with `top`, pads to the declared width with `top`, and starts with an empty operand stack.
- **8.2.5** 4a.5, 4a.6, 4b.8: applies `offset_delta` exactly for the first entry and `offset_delta + 1` for every other one, which is checked by presenting a method whose first entry has a non zero delta and a second entry with delta zero, and produces frames in strictly increasing offset order without sorting them.
- **8.2.6** 4a.7, 4b.10: refuses a frame whose offset is past the end of the code array and a frame whose offset falls inside an instruction rather than at its start, and reaches both decisions before the frame is used for anything.
- **8.2.7** 4a.8, 4b.18: refuses an `Object_variable_info` whose index is out of range or names an entry that is not a `CONSTANT_Class_info`, and an `Uninitialized_variable_info` whose offset is out of range or does not name a `new` instruction, in all four cases.
- **8.2.8** 4a.9, 4b.12, 4b.15, 4b.16: treats a `Long_variable_info` or a `Double_variable_info` as occupying two locations of which only the first is written, refuses one that is the highest numbered local or the topmost stack entry, and counts local variables rather than locations when a `chop_frame` drops one.
- **8.2.9** 4a.10, 4a.16: takes the offset delta of a `same_frame` from the first byte and of a `same_locals_1_stack_item_frame` from the first byte minus 64, consuming no further bytes for either, and accepts a class file in which every frame is written as a `full_frame`, producing the same frames it would from the compressed forms.
- **8.2.10** 4a.11, 4b.1, 4b.6, 4b.7: refuses every first byte in the range 128 to 246, at every position in the attribute including the first and the last, and does not attempt to skip such a frame by any assumed length.
- **8.2.11** 4a.12, 4a.13, 4b.13: drops the last one, two or three local variables for a `chop_frame` and adds one, two or three for an `append_frame`, advances the local variable index by two for an appended `long` or `double`, and refuses a chop of more local variables than the previous frame has.
- **8.2.12** 4a.14: refuses a frame whose locals occupy more locations than the method's maximum, or whose operand stack is deeper than the method's maximum, counting locations rather than items so that a frame legal by item count and illegal by location count is refused.
- **8.2.13** 4b.2, 4b.19: defines a class whose `StackMapTable` contents are arbitrary bytes of the declared length without reading them, and either decodes the attribute for every class or names the configuration in which it does not.
- **8.2.14** 4b.4, 4c.1: reads the class file version before deciding what the attribute is, and either recognises a `StackMapTable` below major version 50 or ignores it as an unknown attribute, saying which.
- **8.2.15** 4b.9: does not let a frame produced by `read` alias state that a later caller may modify in place, so that decoding the whole attribute and then walking the frames gives the same answer as decoding and using them one at a time.
- **8.2.16** 4b.11: refuses an attribute whose `number_of_entries` is smaller than the frames present and one whose `number_of_entries` is larger, and reports the two distinguishably or states that it does not.
- **8.2.17** 4b.14: recomputes whether a frame holds `uninitializedThis` after a `chop_frame`, rather than inheriting the answer, which is checked by chopping away the only local variable that held it.
- **8.2.18** 4b.17: accepts every verification type tag from 0 to 8 in both a locals array and an operand stack where the format permits it, and refuses every tag above 8.
- **8.2.19** 4b.20, 4c.6: states whether a rejected `StackMapTable` ends the load, and if it does not, names the exact set of class file versions for which it does not, so that a conformance run of malformed attributes can be read as a set of refusals rather than as a set of passes.
- **8.2.20** 4c.2: obtains the method's maximum locals and maximum operand stack size before decoding the first frame, which is checked by lowering `max_locals` in a file whose frames are otherwise valid and observing a refusal.
- **8.2.21** 4c.3: determines the instruction boundaries of the code array before decoding the frames, which is checked by presenting an `Uninitialized_variable_info` whose offset is a valid instruction offset holding something other than a `new`.

## 9. Provenance

Section 2 is generated from [the stack map table page](../../docs/generated/stackmap.md), which `tools/gen_stackmap.py` builds by joining four sources: the pinned specification edition for what the attribute is, the JDK's own `classfile_constants.h.template` for the item numbers as numbers rather than as comments on a structure, `stackMapTable.hpp` with `verificationType.hpp` for the frame type ranges and for what the verifier holds in the same byte, and the pinned JDK's `java.lang.classfile` for the two verification types no scan of real class files can find an example of. It is not written here and editing it here has no effect. The generator stops rather than writes when any two of the four disagree, and `tools/test_gen_stackmap.py` holds seventy five tests, sixteen of them one for each way the four sources can drift.

Every clause in 4a quotes JVMS SE25 and every clause in 4b names a file and a line in `jdk-27+35`. `tools/refcheck.py` resolves both against `docs/citations.json` and fails the build when a line has moved, so a clause that has drifted off its evidence is a broken build rather than a stale sentence.

Five things here are measured rather than read, all of them from a walk of `java.base` on two platforms. The 205,580 frames in 1,390,250 bytes and the two independent readers that agree on that byte count. The 122,906 frames whose offset arithmetic could be checked against the offsets the pinned JDK resolved, none of which disagreed. The 41,507 `Long` and `Double` items in locals arrays against 26,349 `Top` items, which is what makes 4a.9 a count rather than a quotation. The 137 first byte values that occur at least once, which is all of them that are legal. And the finding behind 4a.16 and 5.9, that every one of the 205,580 frames is written in the smallest form the encoding allows. A different module would give different numbers and none of them is a requirement on anybody. The write up is [the probe's page](../../docs/probes/stackmap.md).

The zero in that last finding is the one measurement here that needed its own defence, because a zero out of a function nobody has watched return anything else is not a measurement. Two things answer that. The probe assembles six frames whose smallest encoding can be worked out on paper, one per compressible kind, and refuses to write a results file if its own encoder gets any of them wrong. And the byte total is produced twice, once by adding up the widths of decoded frames and once by reading `attribute_length` out of the attribute header, which is a number nothing else in the probe computed. Both are asserted in the unit tests and both are enforced by the generator.

Four things in 4b were read out of the source and have not been demonstrated by running anything. 4b.6, that two bytes are consumed before a reserved frame type is rejected. 4b.7, that the second reserved frame type error is unreachable, which was established by reading the branches above it and checking that they partition a `u1`. 4b.9, that the first entry copies rather than aliases the initial frame's locals, which 5.15 records as unobservable from outside. And 4b.20, that a malformed attribute is survivable at exactly one class file version, which is the clause in this blueprint most worth demonstrating before anybody relies on it, since it decides whether a conformance run of malformed attributes means anything. 5.19 is that demonstration and it has not been performed.

Three questions this blueprint raises are open. 4a.7 is stated as a requirement on frame offsets and the specification establishes it by defining the merge of frames and instructions to be undefined otherwise, rather than by prohibiting anything in the attribute's own section, so it is the clause in 4a most likely to be wrong about where the obligation lives. The pinned JDK reads class file version 71 and the pinned specification edition stops at 69, so a frame kind allocated out of the reserved range between them would make 4a.11 and the count of 119 in section 2 wrong and nothing here would notice. And the six frames of the encoder self check are the only place the smallest form rule is worked out independently of the code that measures it, which makes them a fixture of six rather than a proof.

The reviews field in the front matter is null. Nothing in this blueprint has been read by anybody with production experience of a class file verifier, and until it has, the conformance list is one person's reading of the specification and not a standard.
